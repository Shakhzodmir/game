# Инструменты уровней: проверка, боты, подбор ходов

Всё на чистом Lua и работает на LuaJIT (быстро) и Lua 5.1. Ядро используется только через публичный API `core/game.lua` (`core.load_level`, `core.new`, методы игры, `clone{reseed}`, `set_timing`). Команды запускаются из корня репозитория. Результаты на обеих ВМ совпадают до последнего знака (проверяет тест).

| Файл | Что делает |
|---|---|
| `tools/levels.lua` | проверка уровней, статистика, ASCII-превью |
| `tools/bot/bot.lua` | боты `greedy` (средний игрок) и `strong` (опытный) |
| `tools/bot/run.lua` | одна партия бота: результат, `moves_to_win`, след по ходам |
| `tools/bot/tune.lua` | подбор ходов по распределению `moves_to_win`, отчёт, `--write` |
| `tools/bot/common.lua` | общие функции: чтение уровней, замена `moves`, JSON, генератор бота, разбор командной строки |
| `tools/lib/json.lua` | чужой JSON-разбор (rxi/json.lua), без правок |

**Командная строка.** Неизвестный `--ключ`, ключ без значения, нечисловое значение и неверный список уровней — ошибка с кодом выхода 2 и подсказкой (раньше опечатка вроде `--level 5` молча выбирала все уровни, а с `--write` переписала бы их все). Значение можно писать и как `--ключ=значение`; `--help` печатает строку использования. Список уровней — `5`, `12-15`, `1,3,5-7` (обратный диапазон `15-12` — ошибка).

## Проверка уровней

```sh
luajit tools/levels.lua validate              # все content/levels/level_*.json
luajit tools/levels.lua validate 5 12-15      # выбранные уровни (или пути к файлам)
luajit tools/levels.lua validate --strict     # замечания по плану считаются ошибками
luajit tools/levels.lua stats                 # сложности, звёзды, элементы по уровням (--json)
luajit tools/levels.lua preview 25            # поле по JSON (координаты с нуля, как в файле)
luajit tools/levels.lua preview 30 --seed 3   # стартовая доска, которую ядро строит для сида
```

Везде можно указать `--dir <каталог>` (по умолчанию `content/levels`).

- `validate` грузит каждый файл через `core.load_level` (все правила 2.1 `core-rules.md`) и печатает ошибки ядра; ещё проверяет, что `id` совпадает с номером в имени файла. Код выхода 1, если есть ошибки (испорченный JSON — тоже ошибка уровня, а не падение скрипта).
- Замечания по `levels-plan.md` (не ошибки): сложность по «пиле» (1–100), число цветов по диапазону уровней, ходы вне 20–35. Если проверяется весь каталог (без списка уровней) — ещё номера из 1–100, для которых нет файла (`level files missing: 71-100`). С `--strict` все замечания становятся ошибками, поэтому `validate --strict` на всём каталоге проходит только когда есть все 100 файлов.
- `stats`: число уровней каждой сложности, сумма звёзд (easy и medium — 1, hard — 2, super_hard — 3, как `C.STARS` ядра; по плану к 100-му уровню 126), таблица «размер, цвета, ходы, цели, элементы», первое появление каждого элемента. Элементы считаются как правило 2.1.6 ядра, в том числе `mic`: он есть при цели `deliver`, блоке `mic` или стартовом микрофоне.
- Превью: каждая клетка — 4 символа. Первый — содержимое (`r o y g b p` — цвет фишки, `+` — случайная фишка, `R/S/B/D` — Рифф/Сабвуфер/Пташка/Диско-шар, `M` — микрофон, `X` — коробка, `K` — тумба, `N` — помехи, `A` — шарик, `C` — колонка). Второй — подробность (hp, цвет шарика, ось Риффа `-`/`|`, `e` — стойка; hp 10–12 колонки пишется как `a`–`c`, чтобы клетка оставалась в 4 символа). Третий — плитка танцпола (`_` hp 1, `=` hp 2). Четвёртый — провода (`w` hp 1, `W` hp 2). `v` над столбцом — спавнер (при явном списке спавнеров — в самой клетке, вторым символом), `.` — пустота. Файл, который нельзя нарисовать (нет `size` или `cells`), даёт сообщение и код 1.

## Боты

```sh
luajit tools/bot/run.lua 25                          # одна партия, сид 1, жадный бот
luajit tools/bot/run.lua 25 --seed 7 --bot strong    # сильный бот
luajit tools/bot/run.lua 25 --games 20               # 20 партий подряд (сиды 1..20) и скорость
luajit tools/bot/run.lua 25 --json                   # запись партии в JSON (при --games N — массив)
luajit tools/bot/run.lua 25 --turbo                  # настоящая игра тоже в турбо (быстрее, для отладки)
```

Опции: `--seed` (сид игры, 1..2147483646), `--bot-seed` (сид бота, по умолчанию равен сиду игры; в серии `--games` растёт вместе с сидом игры), `--budget` (бюджет ходов, не меньше 5, по умолчанию 200), `--games`, `--dir`.

**Как бот выбирает ход.** В покое бот перебирает:
- все пары `game:moves()`, включая свапы со спецфишками и свапы двух спецфишек (комбо);
- тапы по свободным спецфишкам (не закреплённым и не в движении).

Порядок кандидатов: сначала свапы в порядке `moves()`, потом тапы в порядке `pieces()`.

Каждый ход проверяется на своём клоне: `game:clone{reseed = k}` → `set_timing("turbo")` → команда → до покоя. Клон пересеян, поэтому будущие цвета настоящей игры боту неизвестны (17.3); все кандидаты одного решения видят одно и то же случайное будущее клона (общие случайные числа), а у разных решений оно разное (сид клона свёрнут из сида игры, счётчика ходов и сида бота). Настоящая игра при просмотре не меняется (тест сверяет хеш).

Оценка хода (план, стр. 26): прогресс целей × 10 + созданные спецфишки × 3 + волны каскада, плюс бонус за комбо. Если целей несколько, прогресс каждой считается долей от цели: единица цели весит `(средний размер целей) / (размер этой цели)` очков прогресса, так что маленькая цель (`deliver 3`) весит за единицу больше большой (`collect 45`), а при одной цели вес единицы 1.
- `greedy`: с вероятностью 70% берёт лучший ход, иначе равновероятно один из трёх лучших (лучший тоже входит, так что лучший ход берётся примерно в 80% решений). Случайность — свой генератор бота (MINSTD), независимый от потоков игры.
- `strong`: всегда лучший ход. Победа +1000, комбо весят больше, крупные спецфишки и спецфишки рядом с целями (≤ 2 клеток до плитки, блокера цели или микрофона) — тоже. Для трёх лучших ходов есть второй ход: только свапы, которые по доске создают спецфишку или комбо (не больше трёх клонов на ветку, то есть не больше 9 лишних клонов на решение; тест проверяет границу).
- При равенстве берётся ход, который раньше в списке. Очки целые, поэтому бот детерминирован при заданных (уровень, сид игры, сид бота) на обеих ВМ.
- Бустеры бот не использует. Последствия каждого хода (каскады, спецфишки) он знает точно, чего живой игрок не делает, поэтому подобранные ходы скорее занижены для людей (см. «Что не покрыто»).

**Настоящая игра** идёт в обычных таймингах (решение №5 журнала; турбо — только в просмотре ходов), если нет `--turbo`.

**Неограниченный бюджет** нужен, чтобы получить `moves_to_win` — сколько ходов понадобилось боту. Уровень грузится из своего же JSON, где заменено только значение `moves` на `min(бюджет, 60)` (схема допускает 5..60). Дальше при `out_of_moves` бот посылает публичную команду `continue {moves = n}`, пока бюджет не кончится. Ядро читает `moves_left` только в проверке «ходы кончились» (и в отказе от хода при нуле) и в финальном концерте. Поэтому первые 60 ходов совпадают с партией при любом лимите M ≤ 60, и победа при лимите M — это ровно `moves_to_win ≤ M`. Проверено на 8 уровнях × 4 сида × лимитах 8, 15, 25, 40 (128 партий, ноль расхождений) и закреплено тестом `tools bot: the documented behaviour`: если кто-то в ядре начнёт читать `moves_left` иначе, тест упадёт. Единственное теоретическое исключение — перемешивание, которое в последнем ходу партии без лимита убирает последнюю помеху запасным вариантом 12.2 (в партии с лимитом M там уже `out_of_moves`, перемешивания нет); на практике не встречается.

**Запись партии** (`Run.play`, `--json`):

| Поле | Что значит |
|---|---|
| `won`, `moves_used`, `duration` | итог первой попытки с лимитом уровня; длительность в тиках до победы или до последнего хода |
| `moves_to_win` | ходов до победы при бюджете; `nil`, если победы нет |
| `ending` | `won` \| `stuck` (нет ходов и продолжения) \| `budget` \| `timeout` |
| `remaining[k]` | доля оставшихся целей после хода k: среднее по целям `осталось / было`, 0 — всё выполнено |
| `specials[k]`, `waves[k]`, `ticks[k]` | спецфишки хода, наибольшая волна каскада хода, тик покоя после хода (у победного хода — тик победы) |
| `specials_total`, `cascades` | за первую попытку; `cascades` — ходы с волной ≥ 2 |
| `evals` | сколько клонов просчитал бот |

## Подбор ходов

```sh
luajit tools/bot/tune.lua --n 100 --jobs 3                  # пробный прогон всех уровней
luajit tools/bot/tune.lua --levels 21-30 --n 300 --jobs 3   # часть уровней
luajit tools/bot/tune.lua --n 300 --jobs 3 --work /tmp/glow_tune --write   # записать подобранные ходы в файлы
```

Опции:
- `--n` — партий на уровень (по умолчанию 100); `--jobs` — рабочих процессов (по умолчанию 1);
- `--bot greedy|strong` (по умолчанию `greedy`);
- `--budget` (по умолчанию 120: вдвое больше предела 60, этого хватает для любого M; не меньше 60);
- `--levels` — список уровней; номера без файла пропускаются с сообщением, а если файлов нет совсем — код 1;
- `--dir` (по умолчанию `content/levels`);
- `--work <каталог>` — каталог результатов; хранится между запусками и работает как кэш (см. ниже). Без него для `--jobs > 1` берётся временный каталог, который удаляется;
- `--fresh` — игнорировать кэш; `--force` — разрешить `--write` при `--n` меньше 100;
- `--md`, `--json` — пути отчётов; `--no-report` — без отчётов;
- `--vm` — интерпретатор рабочих процессов (по умолчанию `luajit`); с `--vm` рабочий процесс запускается и при `--jobs 1`;
- `--quiet` — без строк о ходе работы (в том числе у рабочих процессов).

**Как считается.**
1. Для каждого уровня играются N партий: сиды игры и бота 1..N, одинаковые для всех уровней и прогонов (общие случайные числа). Бюджет ходов фактически неограничен.
2. Доля побед с первой попытки при лимите M = доля партий с `moves_to_win ≤ M`. Одно распределение сразу даёт кривую для всех M.
3. M ищется в 5..60, чтобы доля побед была ближе всего к центру коридора: easy 90% (85–95), medium 68% (60–75), hard 42% (35–50), super_hard 25% (20–30).
4. Если на эту кривую ложится целая «полка» одинаковых M:
   - полка на цели или выше — берётся её наименьший M;
   - полка ниже цели — наибольший (настоящая кривая растёт по полке);
   - если полка ниже цели тянется до 60 и лежит в коридоре, берётся её наименьший M: лишние ходы ни разу не помогли;
   - если две полки одинаково далеки от цели, одна выше и одна ниже, берётся верхняя (легче).
5. Для выбранного M считаются:
   - ожидаемое число попыток `1/p`;
   - доля близких проигрышей: среди проигрышей при M — те, у кого после M ходов осталось ≤ 20% целей (правило 4 плана);
   - медиана ходов у победителей.

**Флаги:**
- `too_hard` — даже при 60 ходах ниже коридора (M = 60);
- `too_easy` — даже при 5 ходах выше коридора;
- `off_corridor` — кривая перепрыгивает коридор (мало партий или ступенька);
- `outside_band` — M вне 20–35 ходов плана;
- `near_miss_low` — близких проигрышей меньше половины;
- `stuck_games` — хотя бы одна партия кончилась тупиком (нет хода и перемешивание не помогло) или зависла (`timeout`); счётчики по исходам партий (`won`, `budget`, `stuck`, `timeout`) лежат в JSON-отчёте (`endings`). Это либо особенность уровня, либо проблема ядра — смотреть `tools/bot/run.lua <id> --seed <k>`;
- `invalid` — уровень не загружается, партия упала с ошибкой ядра (в тексте — сид и команда для повтора) или рабочий процесс умер, не дойдя до уровня.

У целей из нескольких штук (например, `deliver 3`) один оставшийся предмет — это уже больше 20%, поэтому `near_miss_low` там ожидаем.

**Параллельность и устойчивость.** `--jobs K` запускает K рабочих процессов (`luajit tools/bot/tune.lua --worker ...` через `io.popen`) на непересекающихся наборах уровней. Наборы уравнены по оценке стоимости: сложность × площадь поля (на уровнях 1–70 это на 5% хуже идеального разбиения). Каждый рабочий процесс записывает результат каждого готового уровня отдельным файлом в каталог результатов (атомарно: временный файл и переименование), главный процесс читает их, когда рабочие закончили. Поэтому смерть рабочего процесса (убит, нет памяти, ошибка вне партии) стоит не больше одного уровня: остальные берутся из файлов, у потерянного будет строка `invalid: no result` и код выхода 1. Строки о ходе работы идут в stderr с номером рабочего и счётчиком `k/K`.

**Каталог результатов как кэш.** С `--work <каталог>` результат уровня используется повторно, если те же: текст уровня без цифр `moves`, бот, `--budget` и исходники `core/*.lua` и `tools/bot/*.lua` (их контрольная сумма). Партия k зависит только от сида k, поэтому:
- повторный запуск той же команды после обрыва доигрывает только недостающее;
- результат из N0 партий отдаёт любое меньшее N (первые N партий) и достраивается до большего N (играются только новые сиды): пробный проход `--n 100` делает итоговый `--n 300` на треть дешевле;
- правка уровня, ядра или ботов делает старый результат недействительным автоматически; смена только лимита `moves` — нет (на игры он не влияет).

**Запись.** Без `--write` файлы уровней не меняются. С `--write` в каждом файле уровня заменяются только цифры значения `"moves"`, остальной файл остаётся байт в байт:
- перед записью текст проверяется через `core.load_level`, запись атомарная;
- файл, изменившийся после того, как его сыграли (контрольная сумма текста без цифр `moves`), пропускается с сообщением, а не перезаписывается устаревшим ответом;
- `--write` требует `--n` не меньше 100 (при меньшем N лимит шумит), иначе код 2; для репетиций есть `--force`;
- уровни с `invalid` не пишутся; уровни с `too_hard`/`too_easy` получают 60/5 ходов (ближайшее к коридору), их нужно чинить правкой уровня;
- итог — строка `--write: N level file(s) changed, M skipped`.

**Отчёты.** Таблица `docs/levels/tuning.md` (id, сложность, ходы было → стало, доля побед при M и при старом лимите, попытки, близкие проигрыши, медиана, время, флаги) и машиночитаемый `docs/levels/tuning.json` пишутся при каждом прогоне, если не указан `--no-report`. Файл JSON больше не кладётся в `content/levels/` (весь `/content` входит в сборку Defold как `custom_resources`). Если `--dir` не `content/levels`, отчёты по умолчанию не пишутся (репетиция на копии не должна затирать настоящий отчёт): их нужно назвать явно через `--md` и `--json`. Код выхода: 0 — всё сыграно, 1 — есть `invalid` или потерянный рабочий, 2 — неверная командная строка.

## Скорость и время полного прогона

Замеры на LuaJIT 2.1, Xeon 2,1 ГГц, 4 ядра, 70 уровней по 100 партий жадным ботом (7000 партий, все выиграны, тупиков и зависаний нет); во время замеров машину делили с другими задачами (нагрузка 3–14). Время — процессорное (`os.clock`), оно почти не зависит от соседей; настенное растёт пропорционально нагрузке (при нагрузке около 10 три процесса получали около трети ядра каждый).

| Уровни | с на партию | клонов на партию | ходов на партию |
|---|---:|---:|---:|
| поле до 8×8 | 0,10 (0,05–0,18) | 230 | 10 |
| 9×8–9×9 | 0,12 (0,05–0,27) | 270 | 17 |
| 9×10 | 0,17 (0,08–0,30) | 360 | 23 |
| 9×11 | 0,22 (0,10–0,39) | 420 | 25 |
| easy / medium | 0,11 / 0,18 | 245 / 375 | 14 / 20 |
| hard / super_hard | 0,21 / 0,31 | 400 / 560 | 28 / 38 |

Стоимость партии почти целиком определяется числом просмотренных ходов (корреляция с числом клонов 0,97): около 18 клонов на ход, около 0,44 мс на клон вместе с просчётом хода до покоя. LuaJIT примерно в 2,2 раза быстрее Lua 5.1 (17,6 против 8,0 партий/с на маленькой доске).

- **JIT.** Под LuaJIT инструменты расширяют пределы JIT (`maxtrace=8000`, `maxmcode=32768`, `common.jit_opts`). Со стандартными 512 КБ машинного кода JIT постоянно сбрасывается: на одной и той же нагрузке 18,4 с против 7,3 с с настройкой и 9,6 с вообще без JIT. Другие параметры (`maxside`, `maxsnap`, `hotloop`, `loopunroll`, размер областей) и настройки сборщика мусора (`setpause`, `setstepmul`) разницы в пределах шума (±10% при общей машине) не дали.
- **Где время.** Профиль (`jit.p`): около 47% — `deepcopy` внутри `game:clone()` (клонируется всё состояние поля: около 180 таблиц и 2500 полей), около 18% — сборщик мусора, остальное — шаги ядра (`move`, `find_groups`, `match_at` и т. д. по 2–4%), собственный код ботов — каждая функция меньше 1%. Ускорить заметно можно только изнутри ядра. Микротест клона (поле 9×11, середина партии, хеш копии тот же): универсальный `deepcopy` 120 мкс; копия числовых массивов одним `unpack` 100 мкс; объекты поля (150 таблиц по 19 полей) одним конструктором таблицы 65 мкс, то есть клон почти вдвое быстрее, а весь подбор примерно на 20–25% (полный прогон 100 уровней около 20 минут вместо 25). Общий `deepcopy` с предвыделением таблиц (`table.new`) и с обходом через `next` выигрыша не дал: время уходит на создание таблиц. В `core/` это не внесено (другая зона), а в инструменты такая подмена не вставлена, чтобы не привязывать их к устройству состояния. Число клонов на ход сократить без изменения результата нельзя: счёт хода требует прогона до покоя, а равные по эффекту ходы не повторяются.
- **Оценка полного прогона.** Сумма с/партию по 70 имеющимся уровням 10,2 с; для 71–100 по плану (12 easy, 9 medium, 6 hard, 3 super_hard) ещё около 5,1 с. Итого для 100 уровней:

| Прогон | Процессорное время | Настенное, 3 процесса | 4 процесса |
|---|---:|---:|---:|
| пробный `--n 100` | 25 мин | 8–9 мин | 6–7 мин |
| полный `--n 300` с нуля | 76 мин | 25–27 мин | 19–20 мин |
| `--n 300` после пробного `--n 100` (кэш) | 51 мин | 17–18 мин | 13 мин |

  Это меньше порога в 90 минут, ускорять ботов не пришлось. Цифры взяты из процессорного времени замеров (оно с запасом: на свободной машине примерно на 15% меньше) и верны, пока каждому процессу хватает ядра; на машине с нагрузкой около 10 те же прогоны шли втрое дольше. Для настоящего прогона лучше дождаться, пока другие тесты и сборки не заняты.

**Рекомендуемый порядок для 100 уровней** (после того как все файлы уровней готовы):

```sh
# 1. пробный проход: отчёт и флаги (около 8 минут)
luajit tools/bot/tune.lua --n 100 --jobs 3 --work /tmp/glow_tune
# 2. после правок флагованных уровней: итоговый проход, только недостающие партии (около 17 минут)
luajit tools/bot/tune.lua --n 300 --jobs 3 --work /tmp/glow_tune
# 3. запись: всё берётся из кэша, секунды; меняются только цифры "moves"
luajit tools/bot/tune.lua --n 300 --jobs 3 --work /tmp/glow_tune --write
```

Если оборвать любой шаг, повторить ту же команду — доиграются недостающие уровни. Долгие запуски запускать в фоне (`... &` или инструментом фоновых задач) и следить за stderr.

**Репетиция на копии** (проверка, что подмножество и `--write` работают, ничего не трогая в настоящих уровнях):

```sh
cp -r content/levels /tmp/levels_copy
luajit tools/bot/tune.lua --dir /tmp/levels_copy --levels 1-5 --n 20 --jobs 2 --force --write --no-report
diff -r content/levels /tmp/levels_copy      # различаются только цифры moves уровней 1-5
```

## Что не покрыто

- Подобранные ходы — оценка по жадному боту. Он видит каскады каждого хода и всегда играет лучшим из них в 80% случаев, так что он сильнее обычного казуального игрока; реальным людям, скорее всего, понадобится больше ходов. Сравнить можно прогоном `--bot strong` (верхняя граница): на уровнях 1–70 ему нужно в среднем на 12% меньше ходов (16,3 против 18,5, по 4 партии), партия на треть дороже. Окончательные цифры даст плейтест.
- Бот не использует бустеры и не планирует доставку микрофонов и нужные ходы заранее (всего один ход вперёд плюс второй у `strong`).
- У первых десяти уровней подобранный M — 6–14 при 20 в файле (флаг `outside_band`, как и ещё у 14 уровней до 70-го: 11, 13, 15, 17, 20, 22, 23, 27–29, 40, 49, 50, 66): их цели слишком малы для правила плана «20–35 ходов»; чинить нужно цели уровней, а не бота.

## Тесты

`tests/tools/*_test.lua` запускаются общим раннером: `./tools/test.sh --filter tools` (обе ВМ). Что проверяется:
- детерминизм ботов и совпадение партий на Lua 5.1 и LuaJIT (тест запускает обе ВМ); лимит M как начало партии без лимита; границы клонов у `greedy` и `strong`; веса целей; доля лучшего хода у `greedy`;
- математика долей побед и выбор M по коридору, кэш результатов (ключи, достройка и обрезка по сидам, повреждённые файлы, потерянные уровни), флаги, отчёты;
- `--write` не трогает ничего, кроме `moves`, пропускает изменившиеся файлы и значения вне схемы;
- командные строки `tune.lua` (на копии каталога: подмножество, `--write`, рабочие процессы, умерший рабочий, кэш, отчёты, опечатки и плохие числа), `run.lua` и `levels.lua` (коды выхода, повреждённые файлы, превью);
- общие функции (`common_test.lua`): разбор аргументов, JSON, контрольные суммы, поток случайных чисел бота;
- замер скорости: печатает партии/с на текущей ВМ на маленькой и на большой доске.
