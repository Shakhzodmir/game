Цель. Аккаунты и облачное сохранение: три пути входа, прогресс сохраняется и переносится между устройствами.

Слова продюсера: «Добавить аккаунты, чтобы сохранить процесс. Регистрация или просто войти через Google. Есть три пути: как гость, но процесс не сохраняется; и логин через Google, или через ID и пароль. Если зашёл через ID и пароль, можно привязать свой gmail через подтверждение в почте».

Контекст. Игра — статичная HTML5-сборка на GitHub Pages (`.github/workflows/ci.yml`, `web/` шаблон), сервисы-заглушки в `client/services/` (`analytics`, `ads`, `iap`: образец интерфейса с моком), сохранение `meta/save.lua` + `client/save_io.lua` (два слота, контрольная сумма), код сохранения из WP-0 (если слит), настройки `gui/settings.lua`, план сервисов `docs/plan-v2.md` раздел 3 (облачные сохранения). Игра остаётся играбельной без интернета и без входа (гость).

Что сделать
1. Сначала решение (запиши в `docs/design/decisions.md` отдельным пунктом и в записку): какой бэкенд. Сравни Firebase (Auth + Firestore/Realtime DB, бесплатный уровень), Supabase и свой сервер по: Google-вход, e-mail/пароль, подтверждение почты, привязка Google к существующему аккаунту, стоимость, простота для HTML5 из Defold (JS-мост `html5.run`/JsToDef), безопасность (правила доступа: игрок видит только своё сохранение), приватность (согласие, удаление аккаунта по требованию). Рекомендация по умолчанию: Firebase Auth + Firestore. «ID и пароль» без e-mail реализуется как e-mail-аккаунт с синтетическим адресом вида `<id>@id.glow.invalid` (подтверждения почты нет) с возможностью привязать настоящий Gmail через подтверждение письмом; опиши ограничения (восстановление пароля возможно только после привязки почты) и предупреди игрока в интерфейсе. Пароли хранит только провайдер, своей криптографии не писать.
2. Клиент против интерфейса `client/services/auth.lua` с моком (в тестах и в сборке без ключей) и реальной JS-реализацией в шаблоне HTML5 (`web/`), конфигурация провайдера в одном файле `web/auth_config.js` с публичными идентификаторами (apiKey, authDomain, projectId — публичные, не секреты; поля пустые, пока продюсер не создал проект; без конфигурации игра работает как гость и честно пишет «вход пока недоступен»).
3. Интерфейс: при первом запуске окно выбора («Играть как гость», «Войти через Google», «Войти по ID и паролю», «Создать аккаунт»), в настройках раздел «Аккаунт» (кто вошёл, «Привязать Google/почту», «Выйти», «Удалить аккаунт и данные»). Гость видит мягкое напоминание «прогресс не сохранится на другом устройстве» после N уровней. Все тексты ru/en (ko от WP-3).
4. Синхронизация: при входе сравнить облачное и локальное сохранение; правило «прогресс не уменьшается»: если локальный прогресс больше облачного, предложить загрузить его в облако, если облачный больше, предложить взять облачный, если разошлись (разные ветки), показать окно выбора с итогами («уровень N, монеты, звёзды») и класть проигравшее в слот previous; фоновая синхронизация (после уровня и раз в минуту), ошибки сети не мешают игре, ретраи, индикатор «сохранено в облаке». Конфликт двух устройств решается по прогрессу, а не по времени.
5. Тесты: мок-провайдер, все сценарии синхронизации на чистой Lua, подделка данных, офлайн, смена аккаунта на том же устройстве (чужое сохранение не смешивается), удаление.
6. Что нужно от продюсера: создать проект провайдера, включить методы входа, добавить домен `shakhzodmir.github.io` в разрешённые, положить публичный конфиг в `web/auth_config.js` и правила доступа (текст правил и пошаговая инструкция со скриншотами-описанием в `docs/handoff/WP-10.md`, по-русски, для человека без опыта).
Нельзя: хранить секреты в репозитории, писать свою криптографию паролей, терять локальный прогресс при любой ошибке сети, ломать формат сохранения (облако хранит тот же код сохранения WP-0).
