# Рабочие на ключе продюсера (очередь задач)

Зачем. Большая часть работы идёт не на тарифе сессии, а на API-ключе продюсера: каждая задача из `queue.json` выполняется отдельным запуском `claude -p` («рабочим») в своей ветке `agent/<id>` и своей рабочей копии. После рабочего runner сам прогоняет проверки (тесты на обеих ВМ, `check_refs`, `gen_defold --check`, `check_syntax`), при необходимости возвращает задачу рабочему на исправление и сливает ветку в `agent/integration`. Сессия-оркестратор забирает `agent/integration`, проверяет, делает PR, ждёт CI и сливает.

## Как подключить ключ

1. Console → Workspaces → создать Workspace «glow-agents» с месячным лимитом расходов → API keys → создать ключ в нём. Полный ключ показывается один раз.
2. Меню облачного окружения в заголовке сессии → Edit → добавить секрет или переменную `WORKER_API_KEY` (НЕ `ANTHROPIC_API_KEY`: эту переменную читает сама сессия). Ключ в чат не вставлять.
3. Новая сессия подхватывает переменную; старая нет.

Рабочий получает ключ как `ANTHROPIC_API_KEY` только внутри своего процесса; переменные родительской сессии (`ANTHROPIC_*`, `CLAUDE*`, `GITHUB_*`, `GH_*`) ему не передаются. С неверным ключом рабочий падает с «Invalid API key», а не уходит на тариф сессии (проверено).

## Модели

Только Claude Sonnet 5.5 (`claude-sonnet-5-5`) и Claude Haiku 5.5 (`claude-haiku-5-5`): так решил продюсер. Runner не даёт запустить очередь с любой другой моделью (проверка до первого расхода), под-агентам рабочего задан Sonnet 5.5. По умолчанию все задачи на Sonnet 5.5, Haiku 5.5 у `check-key` и у задачи WP-12.

## Команды

```
python3 tools/agents/run_queue.py check-key            # один маленький вызов: работает ли ключ (центы)
python3 tools/agents/run_queue.py run --max-wave 1 --parallel 2 --budget-usd 60 --push > /tmp/glow-agents/run.log 2>&1   # из сессии: Bash с run_in_background
python3 tools/agents/run_queue.py status               # таблица задач и расходов
python3 tools/agents/run_queue.py stop                 # новые задачи не стартуют; идущие дойдут до конца
python3 tools/agents/run_queue.py stop --now           # убить идущих рабочих
python3 tools/agents/run_queue.py reset WP-3           # задача снова «pending» (ветка и копия удаляются)
python3 tools/agents/run_queue.py final-check          # все проверки на agent/integration
python3 tools/agents/run_queue.py selftest             # проверка самого runner-а на подставном claude
```

Состояние (рабочие копии, журналы, отчёты рабочих, `state.json`) лежит в `$AGENT_STATE_DIR` (по умолчанию `/tmp/glow-agents`). Отчёт рабочего по задаче: `reports/<id>.md`; журнал проверок: `logs/<id>.verify.*.log`. Расход по каждой задаче считается из `total_cost_usd` ответа `claude`; у каждой задачи свой потолок (`max_budget_usd`), у запуска общий (`--budget-usd`): когда он исчерпан, новые задачи не стартуют.

## Обрыв (перезапуск контейнера)

`run` кладёт `run.lock` с PID: второй запуск при живом первом не стартует. Если запуск умер (контейнер пересоздан, `kill -9`), следующий `run` сам возвращает задачи «running» в очередь и оставляет их рабочие копии; новый рабочий получает пометку «продолжение прерванной работы» и дорабатывает недоделанное. Расход оборванного запуска в `state.json` не попадает (ответ `claude` приходит только в конце): реальную цифру показывает Console. Сессия-оркестратор должна сама просыпаться и перезапускать очередь (`ORCHESTRATOR.md`).

## Статусы

`pending` ждёт; `running`; `merged` слита в `agent/integration`; `failed` рабочий упал или превысил бюджет и время; `verify_failed` проверки runner-а не прошли и после исправления; `conflict` слияние не удалось (список файлов в `note`; конфликты в `client/assets_index.lua` решаются перегенерацией сами); `skipped` зависимость не слита.

## Волны

`wave` в `queue.json` задаёт порядок: 0 срочное и безопасное, 1 геймплей и язык, 2 музыка, карта, комнаты, 3 песня-блокнот, 4 аккаунты, чарт и группа. `--max-wave N` запускает волны до N. Зависимости (`depends_on`) соблюдаются всегда. Сначала запускай волну 0, потом смотри результат.

## Как сохранить работу, если сессия упрётся в лимит

Контейнер сессии временный. `--push` после каждого слияния пушит `agent/integration` и ветку задачи в origin (нужно разрешение продюсера на пуш веток `agent/*`; без него результаты живут только в контейнере, пока он не освобождён). Из `agent/integration` потом можно открыть PR из любой сессии.

## Что делает оркестратор (сессия)

Подробная инструкция для сессии, которая ведёт очередь: `tools/agents/ORCHESTRATOR.md`. Короткая версия:

1. `check-key`, затем `run` в фоне; следит за `status` и `reports/`.
2. Когда задачи слиты: `final-check`, затем полный `tools/qa/web_screens.mjs` для задач, которые касаются экранов; сам смотрит снимки.
3. Перенос `agent/integration` в ветку сессии, PR, CI, слияние, проверка деплоя (см. `docs/STATUS.md`, как публикуется сборка).
4. По слову продюсера «всё» ставит `stop`.
