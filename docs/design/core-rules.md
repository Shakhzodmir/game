# Правила доски GLOW — точная спецификация ядра (v3.1)

Этот документ — контракт для ядра `core/` (чистый Lua), ботов и клиента. Здесь нет «примерно»: любая ситуация на доске должна однозначно следовать из правил ниже. Если код и документ расходятся, это баг одного из них; исправление фиксируется в обоих. Имена и id — по глоссарию из `decisions.md`. Изменения относительно v2 перечислены в `decisions.md`, раздел 7.

---

## 0. Основы

- **Тик.** Симуляция идёт фиксированными тиками, 60 в секунду. Всё время в ядре измеряется в тиках. Точная семантика времени — раздел 15.1.
- **Единицы.** 1 клетка = 3600 единиц. Все координаты, смещения и скорости — целые числа. Бесконечностей и дробей в состоянии нет.
- **Координаты API.** `x` — колонка, 1..W слева направо; `y` — ряд, 1..H сверху вниз. Индекс клетки `i = (y-1)*W + x`. В JSON уровня координаты считаются с нуля (раздел 2), загрузчик переводит их в 1-базовые.
- **Порядок обхода.** Везде, где порядок влияет на результат, обход идёт по возрастанию индекса клетки, если не сказано иное.
- **Цвета.** Глобальный порядок: `red`=1, `orange`=2, `yellow`=3, `green`=4, `blue`=5, `purple`=6. Ничьи между цветами решаются в пользу меньшего номера.
- **Детерминизм.** Результат однозначно определяется уровнем, сидом, уровнем помощи, бустерами перед уровнем, режимом таймингов, флагом `input_lock` и списком принятых команд с номерами тиков (раздел 17).
- **Правила кода ядра** (проверяются линт-тестом):
  1. Нет `pairs`/`next` там, где порядок влияет на результат: только массивы и циклы по индексу.
  2. Нет `#` на таблицах, где могут быть `nil`. Массивы доски имеют фиксированный размер W·H, пустота — `false` или 0.
  3. Каждый компаратор `table.sort` — строгий полный порядок, последний ключ — индекс клетки или id.
  4. Никаких сравнений строк в логике: только числовые id и перечисления (коды — 17.2).
  5. Нет `math.random`, `os.*`, `tostring` дробных чисел в логике.
  6. Числа ≥ 2^31 сериализуются через `string.format('%.0f', v)` (на wasm32 `%d` обрезается до 32 бит).
  7. Состояние — только простые данные (числа, булевы, массивы и таблицы из них), без замыканий и метатаблиц. Это нужно для `clone` и хеша.

### 0.1 Словарь

| Термин | Значение |
|---|---|
| подвижная фишка | `regular`, `special`, `mic` или `coconut` без проводов и не во льду (фишка на цепи тоже подвижная: она падает, но её нельзя свапнуть, 10.6; фишка во льду неподвижна, 10.11) |
| объект | содержимое одной клетки; колонка 2×2 — один объект на четыре клетки |
| ключ объекта | индекс его клетки; у колонки — индекс её левой верхней клетки |
| одноклеточный блокер | `record_box`, `concrete`, `noise`, `balloon`, `boombox`, `hay` |
| отрезок | максимальная вертикальная последовательность существующих клеток в одной колонке |
| верх / низ отрезка | его клетка с наименьшим / наибольшим `y` |
| открытый слот | пустой слот, либо фишка или блокер в состоянии `fall`, `swap`, `clear` или `armed` |
| дыра | существующая пустая клетка, которую гравитация не может заполнить (10.1) |
| источник | то, что наносит удары (раздел 7) |
| запись | элемент очереди планировщика (15.1, 15.2) |
| `now` | номер выполняемого тика (15.1) |
| открытая цель | цель с остатком > 0 |
| закрытая клетка | клетка занавеса, пока занавес закрыт (10.7): её содержимое не двигается, не матчится и не получает ударов |
| вход / выход портала | две клетки одной пары порталов (10.14): вход — низ своего отрезка, выход — верх своего; для гравитации выход — «клетка под входом» |

## 1. Модель поля

Клетка существует или нет (пустота `.`). У существующей клетки три слоя:

| Слой | Что хранит |
|---|---|
| Пол (`floor`) | Танцпол: прочность `hp` 1–2. Плитка «зажигается», когда `hp` падает до 0 |
| Слот (`slot`) | Одна фишка или блокер, либо ничего |
| Покрытие (`overlay`) | Провода: прочность 1–2, только поверх обычной фишки |

Статические свойства клетки: `spawner` (сюда сверху входят новые фишки), `exit` (стойка микрофона). Метка освобождения `vac` (1.3).

На уровне с ковром (10.8) у клетки есть ещё флаг `carpet` — клетка застелена. Это не слой с прочностью: ковёр лежит под слотом, никогда не убирается и ничему не мешает.

### 1.1 Виды содержимого слота (`kind`)

| kind | Примеры | Падает | Свап / тап | Матчится | Удар `effect` по ней |
|---|---|---|---|---|---|
| `regular` | 6 цветов | да | свап | да | уничтожается |
| `special` | riff, sub, bird, disco | да | свап и тап | нет | запуск (7.2) |
| `mic` | микрофон | да | свап | нет | ничего |
| `coconut` | кокос (10.5) | да | свап | нет | ничего |
| `blocker` | record_box, concrete, noise, balloon, column, boombox, hay | нет | нет | нет | по таблице 7.3 |

Обычная фишка под проводами не падает, не свапается, не бывает донором, но матчится на месте. Провода бывают только над `regular`.

Обычная фишка может стоять **во льду** (поле `ice` объекта, прочность 1–2; 10.11). Фишка во льду не падает, не свапается, не бывает донором и, в отличие от фишки под проводами, **не матчится**: цвета для поиска матчей у неё нет. Лёд снимают удары `adjacent` и `effect` по её клетке; когда прочность стала 0, это обычная свободная фишка на том же месте.

Обычная фишка может нести **цепь** (поле `chain` объекта, прочность 1–2; 10.6). Цепь — свойство фишки, а не клетки: фишка на цепи падает и бывает донором как свободная, но не свапается; матчится там, где стоит; удар `match` снимает единицу прочности цепи вместо фишки, все остальные удары её не трогают.

### 1.2 Состояния и флаги

| state | Значение | Матчится | Ввод | Удар |
|---|---|---|---|---|
| `idle` | покой | да (`regular`) | да | обычный |
| `fall` | летит в свою целевую клетку | нет | нет | открытый слот |
| `swap` | свап, откат, неудачный свап, обмен «Кроссфейдера» (5.3) или блокировка после перемешивания | нет | нет | открытый слот |
| `clear` | уничтожена или снята, исчезнет через `T.clear` | нет | нет | открытый слот |
| `armed` | спецфишка запущена и ждёт удара по своей клетке (7.2) | нет | нет | открытый слот |

- Целый (неразрушенный) блокер всегда `idle`. Разрушенный блокер переходит в `clear`, как фишка (стог сена с подарком стоит в `clear`, пока не кончатся все эффекты, и уступает клетку спецфишке, 10.12). У колонки 2×2 все четыре клетки переходят в `clear` и пустеют вместе.
- Фишка в `fall` уже записана в свою **целевую** клетку; отставание хранится смещениями `offy ≥ 0` и `offx` в единицах. Визуальный центр = центр целевой клетки минус смещение: `vis_y = y·3600 − offy`, `vis_x = x·3600 − offx`.
- У фишки есть `settle_tick` — тик, когда она последний раз стала `idle` (0 для стартовой доски).
- **Флаг `pinned`.** У фишки в `idle` есть множество источников `pins` (массив id источников по возрастанию). Фишка «закреплена», если оно не пусто. Закреплённая фишка:
  1. не свапается и не тапается;
  2. не падает и не бывает донором по диагонали (для гравитации — `wait`);
  3. не попадает в списки других диско-шаров и «Цвет X», в кандидаты Пташки и в подсчёт «самого частого цвета»;
  4. матчится как обычно и получает удары как обычно.

  Кто закрепляет: 7.2.7 (пути эффектов и прожекторов), 8.3 (цель Пташки), 8.4–8.5 (списки L). Источник снимает свою отметку, когда наносит удар по клетке фишки или когда его шаг для этой фишки пропускается. Когда фишка перестаёт быть `idle` (уничтожена, взведена, превращена), все её отметки снимаются.

### 1.3 Метки хода и волны

Метка — пара `(mv, wv)`: номер действия и волна. Сравнение лексикографическое, `max` — по нему.

1. **Действия.** Счётчик `act` растёт на 1 при каждом принятом свапе (кроме неудачного), тапе (включая свайп спецфишки, 5.1.5) и бустере. `continue`, `give_up`, `skip` и неудачный свап действий не создают. Свап и тап запоминают свой номер `a` = значение `act` сразу после увеличения.
2. **Начальные значения.** У каждой фишки и каждого блокера стартовой доски метка `(0, 0)`, у каждой клетки `vac = (0, 0)`.
3. **Свап.** При принятии свапа запоминаются метки обеих фишек. В тике подтверждения (5.1.3) обе получают `(a, 0)`, где `a` — номер **этого** свапа (не текущее значение `act`). При откате обе сразу получают обратно запомненные метки: номер возвращённого действия не остаётся ни в одной метке.
4. **Освобождение клетки не гравитацией.** Клетка получает `vac` = метка причины:
   - удар уничтожил содержимое — метка источника удара (для колонки 2×2 — все четыре клетки);
   - спецфишка или обе спецфишки комбо сняты при срабатывании (7.2.4) — метка активации;
   - микрофон доставлен — метка микрофона.
5. **Гравитация.** Фишка `P` переходит из клетки `S` в клетку `T`. При вертикальном переносе `P.метка = max(P.метка, T.vac, vac каждой клетки строго между S и T)`; при диагональном — `max(P.метка, T.vac)`. Затем `S.vac = P.метка`.
6. **Спавн.** Новая фишка в клетке `c` получает метку `max(c.vac, vac каждой клетки отрезка выше c)`.
7. **Провода и лёд.** Когда удар источника `s` снимает последний слой проводов или последний слой льда (10.11), `P.метка = max(P.метка, метка s)`.
8. **Метка группы** (раздел 6): `M` = max `mv` по фишкам группы; `W` = 1 + max `wv` по фишкам группы с `mv == M`. Новая спецфишка группы получает `(M, W)`.
9. **Метки источников.** `match` и `adjacent` — метка группы. Активация спецфишки (метка запуска):
   - свап и тап — `(a, 1)` со своим номером `a`; бустер — `(act, 1)` в момент принятия;
   - цепочка — метка удара, который её взвёл;
   - груз Пташки — метка Пташки; спецфишки, превращённые комбо «Цвет X», — метка комбо;
   - финальный концерт — `(A + 1, 1)`, где `A` — последний номер действия.
10. **Слияние ходов.** Если правило 5 или 7 поднимает `mv` фишки с `m` до `m' > m`, а действия `m` и `m'` оба стоят в очереди конца хода (раздел 11), то `merged[m] = max(merged[m], m')`: каскад хода `m` влился в каскад хода `m'`.

Волна `W` определяет очки (`20 × W` за фишку), высоту ноты (ступень `min(W−1, 10)` пентатоники) и похвалы (раздел 16). Удар, снявший `hp` с целой помехи (7.3), ставит флаг `noise_hit` действию `m` своей метки `(m, w)`, если оно есть в очереди конца хода; иначе флаг никуда не пишется. Слитые ходы получают зачёт по цепочке `merged` (раздел 11).

### 1.4 Идентификаторы

1. **Объекты.** У каждой фишки и каждого блокера есть id; у колонки 2×2 — один id. Счётчик `next_piece_id` начинается с 1; выдача id — взять текущее значение и увеличить счётчик на 1.
2. **Старт.** В пункте 4.4, когда стартовая доска окончательна (после 4.3 вместе с перемешиванием, до бустеров 4.5), все объекты получают id по возрастанию своего ключа. Неудачные заполнения 4.3 id не тратят.
3. **Новый id** получают только новые объекты: каждый спавн (в порядке прохода 10.1), каждая новая спецфишка группы (6.3) и каждый подарок стога сена (10.12, в порядке шага 4).
4. **id и метка сохраняются** при движении (гравитация, свап, перестановка перемешивания) и при превращении на месте: бустер перед уровнем, Рифф продолжения, Рифф концерта (его метка задана в 13), Рифф перемешивания (12.2, пункты 3–5), превращение «Цвет X», фишка, ставшая помехой.
5. **Источники.** Счётчик `next_source_id` начинается с 1. Источник создаётся:
   - при разрешении группы — сначала `match`, затем `adjacent`;
   - при каждой игре бумбокса, у которой есть хотя бы одна цель, — сразу после ударов `adjacent` группы (10.10);
   - при каждой состоявшейся активации — в начале её записи (у груза — внутри записи удара Пташки): одиночная спецфишка, комбо (один источник на эффект комбо), груз, каждая превращённая спецфишка, каждая активация концерта;
   - бустером — в начале его записи (5.3).
6. **Состояние источника:** id, вид (`match`, `adjacent`, `effect`), метка, цвет группы (или 0), флаг `all_layers` (8.5, «Гранд-финал»), флаг `carpet` (источник стелет ковёр, 10.8), `own` — id его собственных `armed` спецфишек (одна; у комбо две, первой — спецфишка в `to`; у груза, бустера, `match` и `adjacent` — ни одной; после снятия — ни одной), `centre` — клетка первой из `own` в момент активации, ключи дедупликации (7), резервы Пташек (9).
7. **Жизнь источника.** Источник активен, пока в очереди есть хотя бы одна его запись (записи видов 2–5 несут id источника первым полем, 15.2). `match` и `adjacent` живут только во время разрешения своей группы; источник игры бумбокса (10.10) — только пока идут её удары, внутри того же разрешения. Отметки `pins` и резервы всегда сопровождаются записью источника, поэтому у неактивного источника их нет.

```json

  "id": 42, "version": 1,

  "moves": 28,
  "difficulty": "hard",
  "colors": ["red", "orange", "yellow", "blue", "purple"],
  "goals": [
    {"type": "collect", "color": "red", "count": 30},
    {"type": "break", "item": "record_box", "count": 18},
    {"type": "light"},
    {"type": "deliver", "count": 3}
  ],
  "cells": ["..#####..", ".#######.", "#########", "..."],
  "spawners": "top",
  "exits": "bottom",
  "floor":   [{"at": [3, 4], "hp": 2}],
  "overlay": [{"at": [2, 6], "type": "wires", "hp": 1}],
  "slots":   [
    {"at": [4, 4], "type": "record_box", "hp": 3},
    {"at": [0, 5], "type": "concrete", "hp": 2},
    {"at": [1, 1], "type": "noise"},
    {"at": [6, 2], "type": "balloon", "color": "red"},

    {"at": [4, 0], "type": "riff", "axis": "h"},
```

### 2.0 Схема

Любой ключ, не описанный здесь, — ошибка. Все числа — целые. `null` равносилен отсутствию ключа; `null` внутри массивов запрещён.

| Поле | Обяз. | Значение |
|---|---|---|
| `id`, `version` | да | целые ≥ 1 |
| `size` | да | `[W, H]`, 6 ≤ W ≤ 9, 6 ≤ H ≤ 11 |
| `cells` | да | H строк по W символов: `#` — клетка, `.` — пустота; `cells[y]` — ряд y |
| `moves` | да | 5..60 |
| `difficulty` | да | `easy` \| `medium` \| `hard` \| `super_hard` |
| `colors` | да | 4–6 разных id из шести цветов; порядок в массиве не важен, везде используется глобальный порядок |
| `goals` | да | 1–3 цели, не больше одной на пару (тип, цвет/предмет); номер цели — её позиция в массиве, с 1 |
| `spawners` | нет, `"top"` | `"top"` — самая верхняя существующая клетка каждой колонки (кроме колонки, которая начинается выходом портала: в ней спавнера нет, 10.14); или список `[[x, y], …]` |
| `exits` | нет, `"bottom"` | `"bottom"` — низ каждого отрезка (кроме входов порталов, 10.14); или список. Используются только с целью `deliver` (стойки микрофонов) или `drop` (клетки, где кокос покидает поле) |
| `floor` | нет, `[]` | `{at, hp: 1..2}` |
| `overlay` | нет, `[]` | `{at, type: "wires" \| "chain" \| "ice", hp: 1..2}`: провода клетки, цепь на стартовой фишке этой клетки (10.6) или лёд вокруг стартовой фишки этой клетки (10.11) |
| `slots` | нет, `[]` | см. ниже |
| `mic` | только при `deliver` | `{total, on_board_max ≥ 1, gap_moves ≥ 0}`, `total == deliver.count` |
| `coconut` | только при `drop` | `{total ≥ 1, on_board_max ≥ 1, gap_moves ≥ 0, columns}`, `total ≥ drop.count`; `columns` — необязательный непустой список разных номеров колонок (с нуля), в которых кокос может войти сверху; без него — в любой колонке (10.5) |
| `curtain` | нет | `{covers, closed_moves: 1..9, open_moves: 1..9, start: "closed" \| "open"}` — занавес (10.7): `covers` — непустой список клеток `[x, y]` под занавесом; все занавесы уровня закрыты `closed_moves` ходов, потом открыты `open_moves` ходов, и так по кругу; `start` — с какой фазы начинается уровень. Все четыре поля обязательны |
| `carpet` | только при цели `carpet` | непустой список клеток `[x, y]`, застеленных ковром на старте (10.8) |
| `fog` | нет; обязательно при цели `fog` | непустой список клеток `[x, y]`, накрытых туманом на старте (10.13) |
| `conveyor` | нет | непустой список лент конвейера (10.9): `[{"path": [[x, y], …]}, …]`. `path` — не меньше трёх клеток в порядке движения ленты; других ключей у ленты нет |
| `portals` | нет | непустой список пар порталов (10.14): `[{"in": [x, y], "out": [x, y]}, …]`. `in` — клетка входа, `out` — клетка выхода; оба поля обязательны, других ключей у пары нет. Номер пары — её позиция в списке, с 1 |
| `spawn_weights` | нет, `null` | `null` — вес 1 у каждого цвета; иначе объект, ключи которого **ровно** цвета уровня, значения — целые 1..1000 |

- `at` = `[x, y]` с нуля: x — колонка слева направо, y — ряд сверху вниз.
- Типы `slots`: `record_box {hp 1..3}`, `concrete {hp 1..2}`, `noise {}`, `balloon {color}`, `column {hp 6..12}` (`at` — левая верхняя клетка, занимает 2×2), `boombox {hp 1..3}` (10.10), `hay {hp 1..2, gift: "none"|"riff"|"sub"|"bird"|"disco"|"random"}` (10.12; при `gift: "riff"` обязательно ещё `axis: "h"|"v"`, с любым другим подарком поле `axis` запрещено), `riff {axis: "h"|"v"}`, `sub {}`, `bird {}`, `disco {}`, `piece {color}`, `mic {}`, `coconut {}`.
- Все перечисленные поля элементов (`at`, `hp`, `type`, `color`, `axis`, `gift`) обязательны; значений по умолчанию у них нет. Поле `gift` бывает только у `hay` (`gift is only for a hay bale`).
- Цели: `collect {color, count ≥ 1}`, `break {item, count ≥ 1}`, `light {}` (зажечь все плитки уровня), `deliver {count ≥ 1}`, `drop {count ≥ 1}` (опустить N кокосов до низа, 10.5), `chains {count ≥ 1}` (разбить N цепей, 10.6), `carpet {}` (застелить ковром все клетки поля, 10.8; счётчик — число незастеленных клеток), `ice {count ≥ 1}` (растопить N фишек во льду, 10.11), `fog {}` (рассеять туман над всеми клетками поля `fog`, 10.13; счётчик — число клеток под туманом, поля `count` у цели нет).

### 2.1 Валидация (ошибка — уровень не загружается)

1. **Схема** по 2.0 и 2.2.
2. **Геометрия.** Все `at`, спавнеры и стойки — существующие клетки, без повторов. В одном слое у клетки не больше одного элемента. `column` занимает 4 существующие клетки без других элементов слота. Прямо над спавнером (`(x, y−1)`) — пустота или край поля.
3. **Провода, цепи и лёд** стоят только над клеткой, где будет обычная фишка: над клеткой случайного заполнения или над `piece` (не над спецфишкой, микрофоном, кокосом или блокером). В одной клетке — либо провода, либо цепь, либо лёд (один элемент слоя `overlay`, правило 2).
4. **Цвета** `balloon` и `piece` входят в `colors`.
5. **Цели.**
   - `collect.color` ∈ `colors`;
   - `break.item` ∈ {record_box, concrete, noise, balloon, column, boombox, hay}, `count` ≤ числу таких объектов на старте (колонка — один объект);
   - `light` — на уровне есть хотя бы одна плитка;
   - `deliver` — есть блок `mic` и хотя бы одна стойка;
   - `drop` — есть блок `coconut` и хотя бы одна клетка выхода (`exits`);
   - `chains` — `count` ≤ числу цепей на старте;
   - `ice` — `count` ≤ числу фишек во льду на старте;
   - `carpet` — есть поле `carpet` (правило 13);
   - `fog` — есть поле `fog` (правило 15).
6. **Разных элементов** не больше трёх. Считаются: record_box, dancefloor, wires, mic, concrete, noise, balloon, column, coconut (кокос считается при цели `drop`, блоке `coconut` или стартовом кокосе), chain (хотя бы одна цепь в `overlay`), curtain (блок `curtain`), carpet (поле `carpet` или цель `carpet`), conveyor (поле `conveyor`), boombox, ice (хотя бы один лёд в `overlay` или цель `ice`), hay (хотя бы один стог в `slots`, с подарком или без), fog (поле `fog` или цель `fog`), portal (поле `portals`).
7. **Заполнимость.** Проверка на двух досках:
   - `B0` — уровень, из которого убраны все подвижные фишки (случайные, `piece` без проводов и без льда, спецфишки, микрофоны, кокосы); блокеры, фишки под проводами и фишки во льду (10.11) остаются как неподвижное содержимое;
   - `B1` — то же, но убраны ещё все блокеры, фишки под проводами и фишки во льду (остаются только пустоты).

   На каждой доске, начиная с тика 1, выполняются только шаги 4–6 (раздел 15) в турбо-режиме бесцветными фишками: без матчей, микрофонов и стоек. Прогон идёт до первого тика без назначений (не больше 1000 тиков, иначе ошибка). Уровень проходит, если в конце заняты все существующие свободные клетки `B0` и все существующие клетки `B1`. Порталы (10.14) в прогоне работают как в игре: отрезок под выходом заполняется через свою пару.
8. **Микрофоны** (только при `deliver`; без `deliver` блок `mic` и фишки `mic` запрещены):
   - каждый низ отрезка, заполненный в проверке `B1`, — стойка (для явного списка тоже); вход портала (10.14) — исключение: он низ своего отрезка, но не стойка, микрофон едет через портал дальше;
   - стойки и спавнеры не пересекаются;
   - ни один стартовый микрофон не стоит на стойке;
   - число стартовых микрофонов ≤ min(`on_board_max`, `total`).
9. **Стартовые фишки** (`piece`, с проводами и без) не образуют между собой линию из 3 или квадрат 2×2 одного цвета.
10. **Стартовая доска** строится по разделу 4 для `seed = 1..10`, и ни в одном случае перемешивание 4.3 не доходит до пункта 3 раздела 12.2.
11. **Кокосы** (только при `drop`; без `drop` блок `coconut` и фишки `coconut` запрещены) — зеркало правила 8:
    - цели `drop` и `deliver` в одном уровне запрещены (у микрофонов и кокосов общие клетки выхода и общие счётчики, 10.5);
    - каждый низ отрезка, заполненный в проверке `B1`, — клетка выхода (для явного списка `exits` тоже); вход портала (10.14) — исключение, как в правиле 8;
    - клетки выхода и спавнеры не пересекаются;
    - ни один стартовый кокос не стоит на клетке выхода;
    - число стартовых кокосов ≤ min(`on_board_max`, `total`);
    - в каждой колонке из `columns` есть спавнер.
12. **Занавес** (блок `curtain`, 10.7). Клетки `covers` существуют и не повторяются (правило 2). Под занавесом на старте может стоять только обычная фишка — случайная или заданная `piece` — и плитка танцпола. Запрещено: любой блокер (и любая из четырёх клеток колонки), спецфишка, микрофон, кокос, провода, цепь, лёд (`ice under a curtain`); клетка-спавнер; при цели `deliver` или `drop` — стойка или клетка выхода. Проверки заполнимости (правило 7) считают занавесы открытыми.
13. **Ковёр** (поле `carpet` и цель `carpet`, 10.8):
    - поле и цель бывают только вместе: цель без поля и поле без цели — ошибка;
    - клетки `carpet` существуют и не повторяются (правило 2); под стартовым ковром не стоит блокер (ни одна из четырёх клеток колонки);
    - на уровне с ковром нет плиток танцпола (`floor`), значит, нет и цели `light`;
    - на старте не застелена хотя бы одна клетка;
    - **достижимость.** Каждую клетку поля можно застелить одними матчами. Проверка по геометрии: множество `S` — стартовый ковёр; пока множество растёт, любая тройка подряд идущих существующих клеток по горизонтали или вертикали и любой квадрат 2×2 существующих клеток, у которых хотя бы одна клетка в `S`, добавляются в `S` целиком. В конце `S` — все существующие клетки, иначе ошибка с координатой клетки. Блокеры и занавесы проверка не учитывает (блокер ломается, занавес открывается).
14. **Конвейер** (поле `conveyor`, 10.9):
    - клетки каждой ленты существуют; клетка входит не больше чем в одну ленту и не больше одного раза (правило 2: `two conveyor cells in one cell`);
    - соседние клетки списка `path` — соседи по стороне (`conveyor cells must be neighbours by a side`). Путь может быть прямым, ломаным или замкнутым; длина — не меньше трёх клеток (схема);
    - на клетке ленты на старте нет блокера (ни одной из четырёх клеток колонки), нет проводов и нет льда (`ice on a conveyor`: фишка во льду не едет, как и фишка под проводами). Обычные и заданные фишки, спецфишки, микрофоны, кокосы, цепи, плитки танцпола, ковёр, спавнеры, клетки выхода и занавес на ленте разрешены.
15. **Туман** (поле `fog` и цель `fog`, 10.13):
    - клетки `fog` существуют и не повторяются (правило 2: `fog is not on an existing cell`, `two fogs in one cell`);
    - цель `fog` без поля `fog` — ошибка (`fog goal without fogged cells (field fog)`); поле без цели разрешено: туман как помеха на уровне с другой целью;
    - под туманом на старте не стоит блокер — ни одна из четырёх клеток колонки (`fog over a blocker`): блокер неподвижен, а игрок должен видеть, что держит колонку;
    - туман не лежит на клетке-спавнере (`fog over a spawner`) и, при цели `deliver` или `drop`, на стойке или клетке выхода (`fog over an exit`);
    - клетка не может быть и под туманом, и под занавесом (`fog under a curtain`);
    - всё остальное под туманом разрешено: случайная и заданная фишка, спецфишка, микрофон, кокос, плитка танцпола, ковёр, провода, цепь, лёд, клетка ленты конвейера.
16. **Порталы** (поле `portals`, 10.14):
    - клетки `in` и `out` существуют (правило 2: `portal is not on an existing cell`); клетка входит не больше чем в одну пару и только в одной роли, вход и выход пары — разные клетки (`two portals in one cell`);
    - **вход — низ своего отрезка:** клетка прямо под ним — пустота или край поля (`the cell under a portal entrance is not a void or the edge`). **Выход — верх своего отрезка:** клетка прямо над ним — пустота или край поля (`the cell above a portal exit is not a void or the edge`);
    - клетка портала — не спавнер и не клетка выхода микрофонов и кокосов. Значения по умолчанию это учитывают сами: `"spawners": "top"` не ставит спавнер в колонку, которая начинается выходом портала, `"exits": "bottom"` пропускает входы. Явный список с клеткой портала — ошибка (`portal on a spawner`, `portal on an exit`);
    - на клетке портала на старте нет блокера — ни одной из четырёх клеток колонки (`blocker on a portal`), нет проводов (`wires on a portal`) и нет льда (`ice on a portal`): то, что не двигается, заперло бы пару с первого хода. Клетка портала не бывает клеткой занавеса (`curtain over a portal`), тумана (`fog over a portal`: игрок должен видеть, куда уходят фишки) и ленты конвейера (`portal on a conveyor`). Разрешено: случайная и заданная фишка, спецфишка, микрофон, кокос, цепь, плитка танцпола, ковёр;
    - **нет циклов** (`portals form a cycle`): путь «от выхода пары вниз по его отрезку; если низ отрезка — вход другой пары, через неё дальше» всегда кончается отрезком с настоящим низом. В частности, вход и выход одной пары не стоят в одном отрезке;
    - **у каждого входа есть источник** (`no spawner feeds the portal entrance`): верх отрезка входа — спавнер, либо выход пары, у входа которой есть источник (цепочка порталов начинается спавнером);
    - заполнимость отрезка под выходом проверяет правило 7 (прогон с порталами): клетка, до которой фишки не доходят, — ошибка `2.1.7 cell stays empty on board B0/B1`.

### 2.2 Загрузчик и каноническая форма

- `core.load_level(text)` принимает текст JSON и проверяет его по потоку токенов (стандартный декодер Lua теряет эту информацию): `null` внутри массива, число с дробной частью или экспонентой, повтор ключа в объекте — ошибка.
- **Каноническая форма** (для хеша уровня, 17.1): проверенный объект; ключи со значением `null` и отсутствующие ключи опускаются, значения по умолчанию **не** добавляются; ключи объектов отсортированы по байтам; без пробелов и переводов строк; порядок массивов сохраняется; строки — как во входе (все строки схемы — ASCII), экранируются только `"` и `\`; целые — `string.format('%.0f', v)`.

## 3. Случайность

### 3.1 Генератор

- Генератор **MRG32k3a** (L'Ecuyer). Эталонный код (оператор `%` Lua; все промежуточные значения по модулю меньше 2^53, частное меньше 2^21, поэтому результат точный на Lua 5.1 и LuaJIT):

```
m1 = 4294967087; m2 = 4294944443
a12 = 1403580; a13 = 810728; a21 = 527612; a23 = 1370589
-- s[1..3] — компонента 1 (от старого к новому), s[4..6] — компонента 2
next_int():
  p1 = (a12*s[2] - a13*s[1]) % m1
  p2 = (a21*s[6] - a23*s[4]) % m2
  s[1], s[2], s[3] = s[2], s[3], p1
  s[4], s[5], s[6] = s[5], s[6], p2
  return (p1 - p2) % m1          -- целое в [0, m1-1]
int(n) = next_int() % n + 1      -- целое в [1, n]
```

- **Потоки:** `init` (стартовая доска вместе с её перемешиванием, бустеры перед уровнем, Рифф продолжения), `spawn` (цвета новых фишек и помощь), `effects` (цели Пташки, рост помех, выбор фишек концерта, цели бумбокса 10.10, случайный подарок стога сена 10.12), `shuffle` (перемешивание в игре и Ремикс).
- **Инициализация потока** `k` (init=1, spawn=2, effects=3, shuffle=4):
  1. `x = (seed*7 + k*104729 + 12345) % 2147483647`; если `x == 0`, то `x = 1`.
  2. Шесть раз: `x = x*48271 % 2147483647`; результаты по порядку — `s[1]..s[6]`.
  3. Первые 8 выходов `next_int()` отбрасываются.
- **Сид попытки:** `h = 0; для v из (level_id, attempt, salt): h = (h*48271 + v + 1) % 2147483647`; `seed = h % 2147483646 + 1`. `salt` — целое в [0, 2^31−2], создаётся один раз при установке. `attempt` — номер начатой попытки на уровне, с 1. В реплее главный — записанный `seed`.

### 3.2 Случайный выбор

1. Любой случайный выбор из n ≥ 1 вариантов тратит ровно один `next_int` соответствующего потока и берёт вариант номер `int(n)` из списка, упорядоченного по индексу клетки (для цветов — по номеру цвета; для пар — по первому элементу, затем по второму). При n = 0 выбора и траты нет. Выбор «среди равных лучших» — тоже такой выбор: он тратит один `next_int`, даже если лучший вариант один.
2. **Взвешенный выбор цвета:** цвета перебираются в глобальном порядке; `r = next_int() % сумма_весов`; берётся первый цвет, у которого накопленная сумма весов > r.
3. **Самый частый цвет** `mf(filter)`: среди обычных фишек в `idle`, не закреплённых и подходящих под `filter`, цвет с наибольшим числом фишек; ничья — меньший номер; если таких фишек нет — «нет цвета». Фильтр по умолчанию включает фишки под проводами; для комбо «Цвет X» — только без проводов. Фишки на цепи не считаются никогда (10.6), фишки во льду — тоже (10.11).

## 4. Стартовая доска

1. Из файла уровня ставятся фиксированные элементы: пол, слоты, покрытия. Все фишки `idle`, `settle_tick = 0`, метки и `vac` — `(0, 0)`.
2. **Заполнение.** Свободные существующие клетки заполняются по возрастанию индекса обычными фишками из потока `init`:
   - «разрешённые» цвета — цвета уровня, которые не дают линию из 3 с двумя соседями слева или с двумя соседями сверху и не дают квадрат 2×2 с левым, верхним и левым верхним соседом. Соседом считается любая обычная фишка, включая стартовые, под проводами и во льду;
   - если разрешённых нет — разрешены все цвета уровня;
   - один взвешенный выбор (3.2) среди разрешённых с весами `spawn_weights`.
3. **Проверка:** на поле нет ни одного матча и число ходов (12.1) не меньше 3. Всего не больше 100 заполнений (первое и до 99 повторов шага 2 с теми же фиксированными элементами; поток `init` продолжается). Если ни одно не прошло — перемешивание 12.2 сотого заполнения из потока `init`, без блокировки и без событий. Если после него на поле остался матч (это возможно, только если перемешивание дошло до пункта 3 раздела 12.2 или дальше), поле стартует «грязным» и матч разрешится в шаге 7 тика 1 с метками `(0, 0)`.
4. **id** всем объектам (1.4.2).
5. **Бустеры перед уровнем** (Рифф, Сабвуфер, Диско-шар) ставятся в порядке их списка в реплее, каждый одним выбором из потока `init`:
   - кандидаты — обычные фишки без проводов, без цепи и не во льду, не на плитке танцпола и не цвета из цели `collect`; если таких нет — любые обычные фишки без проводов, без цепи и не во льду;
   - фишка заменяется спецфишкой (id и метка сохраняются); у Риффа ось `h`, если это первый, третий или пятый Рифф в списке, иначе `v`;
   - если кандидатов нет совсем, бустер не ставится и попадает в список `unplaced` (17.3), чтобы мета его вернула.
6. `rest_flag = true` (5.3), если поле не стартует «грязным»; иначе `false`.

**Занавес на старте (10.7).** Если уровень начинается с закрытого занавеса: в проверке пункта 3 «нет ни одного матча» считается так, будто занавесы открыты (под закрытым занавесом на старте не прячется готовый матч), а число ходов — по настоящей доске, где закрытые клетки ходов не дают. Перемешивание 4.3 и бустеры 4.5 закрытые клетки не трогают. На уровне без занавесов ничего не меняется.

## 5. Ввод и действия

### 5.0 Команды

- `game:input(cmd)` вызывается между тиками. Возвращает `true, 'ok'` (команда принята), `true, 'fail'` (принят неудачный свап) или `false, reason`. Команда только проверяется и меняет состояния фишек, счётчики и очередь; ударов она не наносит (15.1). У команды `now = tick + 1`; события команды получают `t = now`.
- В реплей пишутся только принятые команды (включая неудачный свап) как пара `(now, cmd)`. Команды одного окна применяются в порядке вызова.
- **Где разрешены:**

  | Команда | Состояния | Прочие условия |
  |---|---|---|
  | `swap`, `tap` | `playing` | `moves_left > 0`; при `input_lock` — ещё `rest_flag` |
  | `booster` | `playing`, `out_of_moves` | `rest_flag` |
  | `continue` | `out_of_moves` | нет флага `stuck` (12.2) |
  | `give_up` | `out_of_moves` | — |
  | `skip` | `won_wait`, `concert` | — |

- **Причины отказа** проверяются в этом порядке; возвращается первая:
  1. `bad_cmd` — неизвестный тип команды или бустера, нет обязательного поля или оно не того типа, координата не целая (у «Кроссфейдера» это `at` и `to`), `row`/`col` вне поля, `continue.moves` вне 1..60;
  2. `bad_state` — команда не разрешена в текущем состоянии;
  3. `no_moves` — `swap` или `tap` при `moves_left == 0`;
  4. `not_rest` — `booster` (или `swap`/`tap` при `input_lock`) при `rest_flag = false`;
  5. `bad_cell` — клетки нет или она не подходит (5.1.1, 5.2, 5.3);
  6. `not_movable` — в клетке нет подходящей фишки (5.1.1, 5.2);
  7. `no_candidates` — Ремикс при n < 2 (5.3); `continue` при флаге `stuck`;
  8. `same_piece` — «Кроссфейдер»: в двух клетках одинаковые фишки (5.3).
- **`input_lock`** — опция конструктора (17.3), по умолчанию `false`; пишется в заголовок реплея. При `true` свап и тап принимаются только при `rest_flag = true` — это запасной «блокирующий режим» из плана.

### 5.1 Свап `{type="swap", from={x,y}, to={x,y}}`

`from` — клетка, которую тянул игрок, `to` — соседняя по стороне клетка (координаты `to` могут быть вне поля).

**5.1.1 Проверки клеток** (после общих проверок 5.0, по порядку):
1. `from` не существует или `to` не соседняя по стороне с `from` — `bad_cell`.
2. В `from` спецфишка в `idle`, не закреплённая (и `from` — не закрытая клетка, 10.7), а `to` вне поля, пустота, пустой слот, целый блокер, фишка под проводами, фишка на цепи, фишка во льду или закрытая клетка — команда исполняется как тап по `from` (5.1.5).
3. `to` не существует — `bad_cell`.
4. В одной из клеток нет подвижной фишки (без проводов и не во льду, 10.11) в `idle`, не закреплённой, или фишка в ней на цепи (10.6), или клетка закрыта занавесом (10.7) — `not_movable`.

**5.1.2 Оценка.**
- Участвует спецфишка — свап принят.
- Иначе виртуальный обмен на **ожидаемой доске** должен дать матч через `from` или `to`: линию ≥ 3 или квадрат 2×2 одного цвета среди обычных фишек. Ожидаемая доска: обычная фишка в `idle` (с проводами и закреплённая тоже) стоит в своей клетке; в `fall` — в своей целевой клетке; в `swap` — в клетке, где она окажется по окончании своего таймера (у свапа, отката и обмена «Кроссфейдера» — в клетке партнёра, у неудачного свапа и блокировки — в своей). Фишки в `clear` и `armed`, спецфишки, микрофоны, кокосы и блокеры цвета не имеют; не имеет цвета и фишка в закрытой клетке (10.7), и фишка во льду (10.11). Есть матч — свап принят.
- Нет матча — **неудачный свап**: обе фишки в `swap` на `T.swap_fail` без обмена, потом снова `idle`. Действие не создаётся, ход не тратится. Событие `swap_fail`. Сюда же попадают свап двух обычных фишек одного цвета, свап двух микрофонов и свап двух кокосов: игрок видит отскок. Кокос (как и микрофон) свапается с соседней обычной фишкой, только если матч даёт эта фишка в клетке кокоса; сам кокос матча не образует.

В покое ожидаемая доска совпадает с доской фишек в `idle`, поэтому 12.1 и подсказка считаются по обычной доске.

**Принятый свап:** `act += 1`, свап запоминает `a = act`, `from`, `to` и метки обеих фишек; `moves_left -= 1`, `moves_made += 1`; действие `a` ставится в очередь конца хода (`noise_hit = false`, `merged = 0`). Обе фишки в `swap` на `T.swap`. События `swap`, `moves`.

**5.1.3 Окончание таймеров (шаг 2 тика).** Таймеры `swap`, `swap_fail`, `swap_back`, `exchange`, истекающие в `now`, обрабатываются в порядке их запуска, затем блокировки перемешивания — по индексу клетки:

```
для каждого истекающего таймера:
  swap:       фишки меняются клетками; обе получают (a, 0), где a — номер этого свапа;
              idle; settle_tick = now; есть спецфишка -> запуск (5.1.4)
  swap_fail:  обе фишки idle, settle_tick = now
  swap_back:  фишки меняются клетками обратно; idle; settle_tick = now
  exchange:   фишки меняются клетками; обе получают (a, 0), где a — номер действия бустера (5.3);
              idle; settle_tick = now; спецфишка не запускается
  блокировка: фишка idle, settle_tick = now
если истёк хотя бы один таймер:
  поиск и разрешение матчей по всему полю (раздел 6), правило 6.2.1 включено
  для каждого свапа без спецфишек, закончившегося в этом шаге (таймер swap; обмен не откатывается), по возрастанию a:
    если ни from, ни to не входят ни в одну группу, разрешённую этим поиском -> откат
```

**Откат** (решение 13 журнала — всегда в пользу игрока): обе фишки получают запомненные метки, переходят в `swap` на `T.swap` (таймер `swap_back`) и в конце меняются клетками обратно; `moves_left += 1`, `moves_made -= 1`; действие `a` помечается «возвращённым» и убирается из очереди конца хода. События `swap_back`, `moves`. Откатов после `swap_back` нет; поиск шага 2 в тике окончания `swap_back` проверяет и эти фишки, как все остальные.

**5.1.4 Свап со спецфишкой.** В шаге 2, сразу после обмена:
- **две спецфишки** — комбо (8.5) с центром в клетке `to`. Обе спецфишки переходят в `armed`; запись `activate` (15.2) ставится на `now` с меткой `(a, 1)`: фишка — спецфишка в `to`, партнёр — клетка `from`;
- **спецфишка + другая фишка** — спецфишка переходит в `armed`, запись её активации ставится на `now` с меткой `(a, 1)`. Диско-шар со свапа с обычной фишкой запоминает её цвет как X (поле X записи); со свапа с микрофоном X выбирается при активации (8.4). Вторая фишка участвует в поиске матчей шага 2 как обычно.

Свап со спецфишкой никогда не откатывается.

**5.1.5 Свайп спецфишки в никуда.** В случае 5.1.1.2 команда исполняется ровно как тап по `from` (5.2): тратит ход, создаёт действие, метка `(a, 1)`. В реплей пишется исходная команда `swap`; при воспроизведении она проверяется так же.

### 5.2 Тап `{type="tap", at={x,y}}`

Проверки клетки: клетки нет — `bad_cell`; в ней нет спецфишки в `idle`, не закреплённой, или клетка закрыта занавесом (10.7) — `not_movable`. Принятый тап: `act += 1`, тап запоминает `a = act`; `moves_left -= 1`, `moves_made += 1`; действие `a` ставится в очередь конца хода; спецфишка сразу переходит в `armed`, запись её активации ставится на `now` с меткой `(a, 1)`. Диско-шар от тапа выбирает X при активации. События `moves` (при принятии), `activate` (при активации).

### 5.3 Бустеры в уровне `{type="booster", booster=..., at={x,y} | row=y | col=x}`

- **Покой при вводе.** `rest_flag = true`, если поле было в покое в конце шага 8 последнего тика (после роста помех и перемешивания), и с тех пор не принято ни одной команды свапа (включая неудачный), тапа или бустера. Любая такая принятая команда ставит `rest_flag = false`.
- Бустер принимается в `playing` и `out_of_moves` при `rest_flag = true`. В `out_of_moves` принятый бустер переводит игру в `playing` (событие `state`); когда поле снова придёт в покой, шаг 8 при `moves_left == 0` вернёт `out_of_moves`, а выполненные цели — `won_wait`.
- Бустер создаёт действие (`act += 1`) для меток, но не тратит ход, не меняет `moves_made` и не ставится в очередь конца хода. Метка источника — `(act, 1)`.
- **Клетка с эффектом** — существующая клетка, не закрытая занавесом (10.7), в которой есть провода, или блокер, или обычная фишка без цепи (фишка во льду — тоже: удар снимет слой льда, 10.11), или спецфишка, или пустой слот над незажжённой плиткой. `stick` по клетке без эффекта и `row_light`/`col_light` по ряду/колонке, где нет ни одной клетки с эффектом, отклоняются с `bad_cell`. Так палочка не тратится впустую на микрофон, кокос, фишку на цепи или пустоту.
- Всё действие бустера — запись `booster` (15.2) на `now`, выполняется в шаге 3; в начале записи создаётся источник (1.4.5) и идёт событие `booster` (у Ремикса — после повторной проверки, см. ниже):
  - `stick` — один удар `effect` по клетке `at`;
  - `row_light` — удар `effect` по каждой существующей клетке `(x, row)` в тике `now + T.light_step·(x−1)`; пустоты пропускаются, но считаются в `x`. Один источник, пути закрепляются (7.2.7);
  - `col_light` — то же по колонке, тик `now + T.light_step·(y−1)`;
  - `remix` — перемешивание по 12.2 (пункты 1–3). Принимается, только если кандидатов перемешивания не меньше 2, иначе отказ `no_candidates`. При выполнении число кандидатов проверяется снова (свап в том же окне мог забрать фишки): если n < 2, Ремикс ничего не делает, событие `booster` с `ok = false`, предмет попадает в `unplaced`.
  - `swap` — «Кроссфейдер»: `{type="booster", booster="swap", at={x,y}, to={x,y}}`, обмен местами двух фишек в любых двух клетках поля, не только соседних. Обе клетки существуют (`bad_cell`; одна и та же клетка дважды — тоже `bad_cell`), в каждой подвижная фишка в `idle`, не закреплённая и без проводов, то есть всё, что вправе двигать обычный свап (5.1.1.4): обычные фишки, спецфишки, микрофоны, кокосы (иначе `not_movable`: блокеры всех видов, фишка под проводами, фишка на цепи, фишка во льду, пустой слот, фишка в движении). Две одинаковые фишки (тот же вид, цвет, спецфишка и ось: два красных, два микрофона, два Рифф `h`) отклоняются с `same_piece`: обмен ничего бы не изменил, и бустер не тратится. Отказ не создаёт действия, не пишется в реплей и ничего не меняет.
    - Принятая команда не ставит запись в очередь: обмен начинается сразу, как свап (5.1.2). Обе фишки уходят в `swap` на `T.exchange` (вид таймера `exchange`, 17.2), запись обмена попадает в список свапов в полёте (17.2); события `booster` (`at`, `to`, `ok = true`) и `exchange` (раздел 16). Ход не тратится, `moves_made` и очередь конца хода (раздел 11) не меняются, поэтому за обмен помехи не растут; `act += 1`, `rest_flag = false`. Так фишки обмена не может отнять другая команда в том же окне, повторной проверки нет, и «Кроссфейдер» никогда не попадает в `unplaced`.
    - В шаге 2 тика окончания таймера фишки меняются клетками и получают метку `(a, 0)`, где `a` — номер действия бустера (5.1.3). **Обмен ничего не запускает**: ни спецфишка с обычной фишкой, ни две спецфишки (комбо не бывает) не активируются, спецфишка просто оказывается в другой клетке. Затем идёт обычный поиск матчей по всему полю (раздел 6): обмен считается закончившимся свапом для правила 6.2.1 (новая спецфишка группы встаёт в клетку обмена), волна каскада начинается с 1. Обмен, не давший матча, остаётся (бесплатный обмен): откат 5.1.3 к нему не применяется.
    - Обмен идёт, пока игрок вправе вводить другие команды (неблокирующий ввод): свап и тап принимаются как обычно, фишки обмена для них занятые (`not_movable`), а ожидаемая доска (5.1.2) считает их уже обменянными. Бустер в `out_of_moves` возвращает игру в `playing`, как остальные.

### 5.4 Служебные команды

- `continue {moves=n, riff=bool}` — только в `out_of_moves` без флага `stuck`: `moves_left += n`; если `riff`, одна обычная фишка без проводов, без цепи и не во льду в `idle` (выбор из потока `init`) становится Риффом с осью `h` (id и метка сохраняются, событие `continue_riff`); если кандидатов нет — Риффа нет, предмет попадает в `unplaced`. Состояние `playing`, флаг `stuck` снимается.
- `give_up` — из `out_of_moves` в `lost`.
- `skip` — в `won_wait` и `concert`: режим таймингов становится турбо до конца уровня (15.1, правило 8).

### 5.5 Выделение фишек в клиенте (обязательно для клиента)

Режимы ввода — решение 6 журнала. Ядро выделения не знает; клиент обязан вести его так:
1. Выделение привязано к id фишки и снимается, когда эта фишка перестаёт быть `idle` или уходит из своей клетки, либо игра выходит из `playing`.
2. Если выделена фишка S, тап по соседу N по стороне отправляет `swap{from=S, to=N}`, кем бы ни была N.
3. Режим «свайп»: тап по спецфишке без выделения или при несоседнем выделении снимает выделение и отправляет `tap`; тап по обычной фишке или микрофону выделяет её вместо прежней; тап по выделенной фишке снимает выделение.
4. Режим «тап-тап»: первый тап по любой фишке выделяет её; тап по выделенной спецфишке отправляет `tap`; тап по несоседней фишке переносит выделение.

## 6. Матчи

**Когда искать.**
- В шаге 2, если в нём истёк хотя бы один таймер (5.1.3). Только здесь действует правило 6.2.1.
- В шаге 7, если поле «грязное».

**Флаг «грязное».** Поле становится «грязным», когда любая фишка становится `idle` (приземление, конец любого таймера) или с фишки снимаются провода. Каждый поиск (в шаге 2 или 7), разрешив все свои группы, ставит флаг в `false`. Во время разрешения групп флаг не ставится: разрешение не может создать новый матч (фишка группы, освобождённая от проводов, уже входила в свои линии, а соседи её цвета — в ту же группу; новая спецфишка не матчится; игра бумбокса 10.10 только уничтожает фишки). Исключение — цепи (10.6): если в этом поиске удар `match` пришёлся хотя бы по одной цепи, поиск оставляет флаг `true`, потому что уцелевшие фишки группы стоят в `idle` и могут сами составлять линию или квадрат; их найдёт следующий поиск (шаг 7 того же тика или следующего). Второе исключение — лёд (10.11): если удар `adjacent` этого поиска снял с фишки последний слой льда, поиск тоже оставляет флаг `true`: освобождённая фишка в группы этого поиска не входила и может стоять в готовой линии.

Поиск идёт **по всему полю** среди обычных фишек в `idle`, включая фишки под проводами и закреплённые, но без фишек в закрытых клетках (10.7) и без фишек во льду (10.11): линия или квадрат через фишку во льду — не матч. Реализация может проверять только линии и квадраты через клетки, изменившиеся с прошлого поиска, если результат тождественен полному поиску; это проверяет property-тест.

**Инвариант:** после поиска в шаге 2 и в шаге 7 среди фишек в `idle` нет ни одного матча.

**Группа.** Максимальные линии ≥ 3 одного цвета по горизонтали и вертикали плюс все квадраты 2×2 одного цвета. Линии и квадраты с общими клетками сливаются в одну группу. Все группы находятся на доске до начала разрешения, затем разрешаются по возрастанию наименьшего индекса своих клеток. Цвет группы — цвет её фишек.

### 6.1 Классификация (сверху вниз, первое совпадение)

| Условие в группе | Спецфишка |
|---|---|
| есть линия ≥ 5 | `disco` |
| есть горизонтальная линия ≥ 3 и вертикальная линия ≥ 3 | `sub` |
| есть линия ровно 4 | `riff`, ось = ось этой линии |
| есть квадрат 2×2 | `bird` |
| иначе | нет |

### 6.2 Клетка для спецфишки

Кандидаты — клетки группы **без проводов и без цепи**. Если кандидатов нет, спецфишка и бонус не создаются. Иначе первое подходящее правило:
1. (только в шаге 2) Клетка группы, которая была `from` или `to` свапа или обмена «Кроссфейдера» (5.3), закончившегося в этом шаге (таймер `swap` или `exchange`). Если в группе клетки нескольких свапов — берётся свап с наименьшим `a`. Откаты и неудачные свапы не считаются. (Клеток одного свапа в группе не бывает больше одной: цвета двух фишек свапа разные.)
2. Для `sub` — кандидаты, лежащие одновременно в горизонтальной и вертикальной линии группы. Если их несколько — выбор по правилу 3 среди них; если нет ни одного — правило 3 среди всех кандидатов.
3. Кандидат с наибольшим `settle_tick`; при равенстве — ниже (больше y), затем левее (меньше x).

### 6.3 Разрешение группы (метка `(M, W)`)

1. Создаются источники `match`, затем `adjacent` (1.4.5) с меткой `(M, W)` и цветом группы. Событие `match`.
2. Клетки группы по возрастанию индекса получают удар `match` (раздел 7). Фишка в клетке спецфишки уничтожается без состояния `clear` — слот пустеет сразу; пол получает урон, цель и очки засчитываются, событие `clear`.
3. После всех клеток группы в клетку спецфишки ставится новая спецфишка: новый id, `idle`, метка `(M, W)`, `settle_tick = now`. События `special_new`, затем `score` с бонусом (7.4) в этой клетке.
4. Источник `adjacent`: один удар по каждой клетке вне группы, соседней по стороне хотя бы с одной клеткой группы, по возрастанию индекса. Колонка 2×2 получает не больше одного удара (дедупликация).

   4а. **Бумбоксы** (10.10): каждый бумбокс, с которого удар пункта 4 снял `hp`, «играет» цвет группы — по возрастанию индекса своей клетки, после всех ударов пункта 4. На уровне без бумбоксов этого пункта нет.
5. Похвала — раздел 16.

## 7. Удары

Удар — `hit(клетка, источник)`. Состояние источника — 1.4.6.

**Дедупликация.** Ключ удара — (источник, ключ объекта); источник запоминает его при первом ударе. Удар с уже использованным ключом пропускается целиком: ни проводов, ни слота, ни пола. Исключение — источник с флагом `all_layers`: у него ключ относится только к слою слота, а провода и пол каждой клетки бьются всегда.

### 7.1 Порядок обработки удара

Удар по закрытой клетке (10.7) не делает ничего: ни проводов, ни слота, ни пола, ни ключа дедупликации; отметка `pins` источника с фишки при этом снимается, как при любом ударе. Это верно для всех источников, включая `all_layers`.

0. **Снятие своей спецфишки** (7.2.4): если удар источника пришёл в его клетку `centre`, а `own` не пуст, сначала снимаются все спецфишки из `own`, и `own` становится пустым.

   0а. **Ковёр** (10.8): если у источника флаг `carpet`, клетка не застелена и в ней нет целого блокера, клетка застилается: +50 очков, событие `carpet`, цель `carpet` −1. Этот пункт выполняется до дедупликации и до проводов: провода, цепь, микрофон, кокос, спецфишка и пустой слот ковру не мешают.

   0б. **Туман** (10.13): если клетка под туманом, туман с неё снимается навсегда: +50 очков, событие `fog`, цель `fog` −1. Этот пункт выполняется при ударе любого источника (`match`, `adjacent`, `effect`), до дедупликации и до проводов, что бы ни стояло в клетке (и в пустом слоте тоже); дальше удар идёт по обычным правилам. Удар `adjacent` по клетке с проводами после этого заканчивается, как всегда (пункт 2), но туман уже снят.
1. Открытость слота фиксируется здесь, **до** пункта 3, и дальше не пересчитывается.
2. **Провода.** Если на клетке провода: удар `adjacent` ничего не делает (удар закончен). Иначе `hp` проводов −1, событие `hit`; при 0 провода снимаются, событие `freed`, метка фишки по 1.3.7, поле «грязное» (кроме разрешения группы, раздел 6). Дальше обычный удар не идёт: фишка и пол защищены. Удар `all_layers` идёт дальше: к слоту — только если проводов больше нет, к полу — всегда.
3. **Слот** (для `all_layers` — только если ключ объекта ещё не использован этим источником):
   - открытый слот — ничего;
   - `regular` в `idle` без цепи и не во льду: `adjacent` — ничего; `match` или `effect` — уничтожается;
   - `regular` в `idle` во льду (10.11): `adjacent` или `effect` — `ice −= 1`, событие `hit` (слой `ice`), при 0 — событие `thawed`, метка фишки по 1.3.7, цель `ice` −1, поле «грязное» (внутри разрешения группы — по правилу раздела 6); фишка остаётся. Удар `match` по ней невозможен (она не в группе). Пол под ней обычный удар не трогает (фишка не уничтожена); удар `all_layers` бьёт пол, как всегда;
   - `regular` в `idle` на цепи (10.6): `match` — `chain −= 1`, событие `hit` (слой `chain`), метка фишки по 1.3.7, при 0 — событие `unchained` и цель `chains` −1; фишка остаётся. `effect` и `adjacent` — ничего. Пол под ней обычный удар не трогает (фишка не уничтожена); удар `all_layers` бьёт пол, как всегда;
   - `special` в `idle`: `effect` — запуск цепочкой (7.2.1); `match`, `adjacent` — ничего;
   - `mic`, `coconut` — ничего (ни матч, ни спецфишка, ни бустер их не уничтожают; пол под ними удар при этом не трогает);
   - блокер — по таблице 7.3.
4. **Пол.** Плитка с `hp > 0` получает −1, если:
   - в пункте 3 уничтожено содержимое слота (при любом виде удара), **или**
   - удар `effect`, а слот был открыт (по пункту 1), **или**
   - у источника флаг `all_layers`.

   Урон полу — не больше одного за удар. Запуск спецфишки и её снятие полу урона не наносят. Каждый урон — событие `hit` (слой `floor`); при `hp == 0` — ещё `floor_lit`. Колонка — особый случай (7.3).

**Уничтожение** фишки или блокера: состояние `clear` на `T.clear`, потом слот пустеет. В момент уничтожения клетке ставится `vac` (1.3.4), засчитываются цели и очки (7.4), снимаются все отметки `pins`.

### 7.2 Жизненный цикл спецфишки

1. **Запуск.** Спецфишку запускают свап (5.1.4), тап (5.2, 5.1.5), удар `effect` по ней в `idle` (цепочка), комбо «Цвет X» (превращение) и финальный концерт. При запуске она сразу переходит в `armed`. Цепочка ставит запись активации на `now + T.chain` с меткой ударившего источника.
2. **Один раз.** Каждая спецфишка активируется не больше одного раза. Запуск уже `armed` спецфишки игнорируется; удар по ней — удар по открытому слоту.
3. **Ожидание.** `armed` спецфишка стоит в своей клетке (для гравитации — `wait`) до первого удара своего источника по своей клетке (`centre`):

   | Эффект | Удар по своей клетке |
   |---|---|
   | riff, bird | `t0` |
   | sub | `t0 + T.sub_swell` (кольцо 0) |
   | disco | после своего списка, `t0 + T.disco_step·#L` |
   | комбо | первый удар комбо по центру `to` (8.5) |

4. **Снятие.** Этот удар сначала снимает спецфишку: она переходит в `clear` на `T.clear`, как уничтоженная фишка (для гравитации — `wait`, для ударов — открытый слот); событие `clear` с `cause = fired`; очков, целей и урона полу нет; клетке ставится `vac` = метка активации. Затем удар идёт по уже открытому слоту по 7.1 (удар `effect` по открытому слоту наносит полу −1). У комбо первый удар по центру снимает обе спецфишки (обе в `clear`, `vac` обеих клеток = метка комбо); клетку `from` комбо бьёт, когда до неё доходит его геометрия. У груза Пташки своей спецфишки нет: его удар по своей клетке — обычный удар.
5. **Время `t0`** — тик, в шаге 3 которого выполняется запись активации (у груза — запись удара Пташки).
6. **Список действий.** При активации эффект строит полный список своих действий (ударов, шагов, превращений, запусков) в естественном порядке (задан в разделе 8) и устойчиво сортирует его по тику. Если один объект (у источника `all_layers` — одна клетка) попадает в список ударов дважды, остаётся первое вхождение. Действия с тиком `now` выполняются сразу, по порядку, внутри записи активации. Остальные ставятся в очередь по одной записи на действие (15.2), в этом порядке. Исключение — Пташка: её цели выбираются после выполнения креста (8.3).
7. **Закрепление пути.** В момент активации эффект закрепляет (1.2) каждую подвижную фишку в `idle` в каждой клетке, по которой он ударит в тике > `now` (так же закрепляют пути бустеры `row_light` и `col_light`). Удар по клетке снимает отметку этого источника. Так фишки на пути разряда, кольца или Пташки не уходят из-под удара, а колонка над сработавшей спецфишкой не падает в её клетку раньше, чем её накроет эффект.

### 7.3 Блокеры

| Блокер | hp | Ломается от | Особенности |
|---|---|---|---|
| `record_box` | 1–3 | `adjacent`, `effect` | −1 за удар |
| `concrete` | 1–2 | только `effect` | Учит копить спецфишки |
| `noise` | 1 | `adjacent`, `effect` | Удар, снявший `hp`, ставит `noise_hit` (1.3). Растёт в конце хода (раздел 11) |
| `balloon` | 1 | `adjacent` источника своего цвета, `effect` | |
| `boombox` | 1–3 | `adjacent`, `effect` | −1 за удар, как `record_box`. Каждая единица `hp`, снятая ударом `adjacent`, — «игра» цвета группы (10.10); удар `effect` ничего не играет |
| `hay` | 1–2 | `adjacent`, `effect` | −1 за удар, как `record_box`. Разрушенный стог с подарком не оставляет пустую клетку: в ней появляется спрятанная спецфишка (10.12) |
| `column` (2×2) | 6–12 | `adjacent`, `effect` | Один удар на источник. При 0 все 4 клетки переходят в `clear`, получают `vac` = метка удара, и каждый из 4 полов получает ровно −1 (вместо урона полу по 7.1.4; у `all_layers` каждый пол бьётся своим ударом) |

Урон блокеру без разрушения — событие `hit` с остатком `hp`; разрушение — событие `destroy`. События колонки ставятся на её левую верхнюю клетку; урон её четырём полам — четыре события `hit` (слой `floor`) по индексу клеток.

| Что | Очки |
|---|---|

| бонус группы за спецфишку | riff и bird — 60, sub — 90, disco — 150 |
| обычная фишка, уничтоженная ударом `effect` | 30 |
| превращение фишки комбо «Цвет X» | 30 |
| каждая единица `hp`, снятая с блокера (колонки тоже), проводов, цепи, льда или плитки пола | 50 |
| Рифф финального концерта | 300 |
| собранный кокос (10.5) | 50 |
| клетка, застеленная ковром (10.8) | 50 |
| клетка, с которой снят туман (10.13) | 50 |
| всё остальное (доставка микрофона, активация и снятие спецфишки, рост помех, помеха перемешивания, появление подарка стога сена) | 0 |

Цели засчитываются в момент события:
- `collect` — обычная фишка цвета уничтожена (включая фишку в клетке новой спецфишки) или превращена комбо «Цвет X»;
- `break` — блокер разрушен (колонка — один объект); помеха, убранная перемешиванием (12.2.5), засчитывается, только если она была последней помехой на поле;
- `light` — плитка зажглась;
- `deliver` — микрофон доставлен;
- `drop` — кокос собран (10.5);
- `chains` — с фишки снята последняя единица цепи (ударом `match` или правилом 12.2.4а);
- `ice` — с фишки снят последний слой льда (ударом `adjacent` или `effect`, либо правилом 12.2.4б);
- `carpet` — клетка застелена ковром (10.8);
- `fog` — с клетки снят туман (10.13).

Остаток цели не опускается ниже 0. Когда выполнена последняя цель, игра сразу переходит в `won_wait` (раздел 13).

## 8. Спецфишки и комбо

Общее для всех эффектов (7.2): `t0` — тик активации; у каждого эффекта свой источник вида `effect` с меткой запуска; список действий строится в естественном порядке, указанном ниже; `R(d) = (15·d + 6) // 7` — тик разряда на расстоянии `d` (28 клеток в секунду; в турбо 0). Удары бьют только существующие клетки; пустоты разряды пролетают насквозь, до края поля.

### 8.1 Рифф (`riff`, ось h или v)

- `t0`: удар по своей клетке. События `activate`, `bolt` по каждому из двух направлений.
- Клетки на расстоянии `d` вдоль оси в обе стороны — в тике `t0 + R(d)`.
- Естественный порядок: своя клетка, затем по `d`, при равном `d` — меньший индекс.

### 8.2 Сабвуфер (`sub`)

- `t0`: «набухание», события `activate`, `ring` (r = 0..2).
- Кольцо `r` (расстояние Чебышёва, r = 0..2, квадрат 5×5) — в тике `t0 + T.sub_swell + T.ring·r`. Кольцо 0 — своя клетка.
- Естественный порядок: по `r`, затем по индексу.

### 8.3 Пташка (`bird`)

1. `t0`: «крест» — своя клетка и 4 соседа по стороне, по индексу. Все удары креста выполняются сразу внутри записи активации.
2. Сразу после креста выбирается цель по разделу 9. Цель резервируется до удара; подвижная фишка в `idle` в клетке цели закрепляется этим источником. Событие `bird_fly`.
3. **Удар** — запись `bird_impact` на `t0 + T.bird_flight` (в турбо — выполняется сразу после выбора, внутри записи активации). При выполнении резерв и отметка снимаются, затем:
   - без груза — удар по клетке цели тем же источником (что бы в ней ни было);
   - с грузом (Рифф или Сабвуфер; груз бывает только у комбо, 8.5) — эффект груза активируется здесь же, внутри этой записи: новый источник с меткой Пташки, `t0` груза = этот тик, своя клетка груза — клетка цели. Рифф-груз бьёт по оси, выбранной в разделе 9.
4. **Целей нет:** без груза — только крест, события `bird_fly` нет; с грузом — запись `bird_impact` с клеткой центра комбо `to` на `t0 + T.bird_flight`, груз активируется в `to`; Рифф-груз берёт ось Риффа-партнёра.

### 8.4 Диско-шар (`disco`)

1. **Цвет X:** запомненный при свапе с обычной фишкой (5.1.4), иначе `mf()` в момент `t0` (3.2).
2. **Список L** (`#L` — его длина): обычные фишки цвета X в `idle`, не закреплённые (с проводами тоже, на цепи и во льду — нет), и целые шарики (`balloon`) цвета X; по расстоянию Чебышёва от шара, затем по индексу. Если X нет — L пуст. Все фишки L закрепляются этим источником в `t0` (правило 7.2.7 для шара заменяется этим); шарики не двигаются и не закрепляются.
3. **Шаг k** (с нуля) — в тике `t0 + T.disco_step·k`: если фишка L[k] (по id) всё ещё закреплена этим источником, или шарик L[k] (по id) всё ещё цел, — удар по её клетке, событие `disco_ray`. Иначе шаг пропускается: удара нет, его время не сдвигает следующие шаги.
4. **Своя клетка** — в тике `t0 + T.disco_step·#L` (при пустом L — в `t0`). Этот удар снимает шар.
5. Естественный порядок: шаги по k, затем своя клетка.

Фишка L под проводами при своём шаге теряет слой проводов, как при любом ударе.

### 8.5 Комбо (свап двух спецфишек, центр — клетка `to`)

| | riff | sub | bird | disco |
|---|---|---|---|---|
| **riff** | «Крест» | «Тройной крест» | Пташка несёт Рифф | Цвет X → Риффы |
| **sub** | | «Бас-дроп» | Пташка несёт Сабвуфер | Цвет X → Сабвуферы |
| **bird** | | | «Трио» | Цвет X → Пташки |
| **disco** | | | | «Гранд-финал» |

**Общие правила.**
- Метка комбо — `(a, 1)` свапа. Один комбо-эффект — один источник (`own` — обе спецфишки, `centre` — `to`); груз Пташки и превращённые спецфишки — новые источники с меткой комбо.
- Обе спецфишки стоят `armed` до первого удара комбо по центру; этот удар снимает обе (7.2.4).
- Пути закрепляются по 7.2.7, кроме «Цвет X» (там закрепляет список L).
- Если клетка попадает в геометрию несколько раз — остаётся самое раннее попадание (7.2.6).

**Геометрия и время** (естественный порядок везде — по тику, затем по индексу, если не сказано иное):

| Комбо | Удары | Первый удар по центру |
|---|---|---|
| «Крест» (riff+riff) | как Рифф из центра сразу по двум осям: клетки ряда и колонки центра на расстоянии `d` — в `t0 + R(d)` | `t0` |
| «Тройной крест» (riff+sub) | разряды по рядам y−1, y, y+1 и колонкам x−1, x, x+1. Разряд ряда `y+k` выходит из клетки `(x, y+k)`, разряд колонки `x+k` — из `(x+k, y)`. Клетка на расстоянии `d` от точки выхода вдоль разряда — в `t0 + T.sub_swell + R(d)` | `t0 + T.sub_swell` |
| «Бас-дроп» (sub+sub) | как Сабвуфер, но r = 0..3 (7×7) | `t0 + T.sub_swell` |
| Пташка с грузом (bird+riff, bird+sub) | крест в центре в `t0`, затем выбор цели «С грузом» (раздел 9) и удар с грузом по 8.3 | `t0` |
| «Трио» (bird+bird) | крест в центре в `t0`, затем три цели по разделу 9, выбранные по очереди (резерв и закрепление — как в 8.3). Выбор без кандидатов отменяет этот и все следующие удары (без трат случайности). Удары — записи `bird_impact` источника комбо на `t0 + T.bird_flight` в порядке выбора (в турбо — сразу после выборов). Естественный порядок: крест по индексу, выборы, удары в порядке выбора | `t0` |
| «Гранд-финал» (disco+disco) | пауза, затем каждая существующая клетка поля: клетка на расстоянии Чебышёва `r` от центра — в `t0 + T.finale_pause + T.ring·r`. Источник с флагом `all_layers`: каждый удар бьёт все слои клетки — провода, слот и пол (7.1), как в плане | `t0 + T.finale_pause` |
| «Цвет X → спецфишки» (disco + riff/sub/bird) | см. ниже | `t0 + T.transform_step·#L` |

**«Цвет X → спецфишки».**
1. X = `mf(без проводов)`. L — обычные фишки цвета X в `idle` без проводов, без цепи и не во льду, не закреплённые, по расстоянию Чебышёва от центра, затем по индексу (шарики сюда не входят). Все фишки L закрепляются источником комбо в `t0`.
2. Превращение k (с нуля) — в тике `t0 + T.transform_step·k`: если L[k] всё ещё закреплена этим источником, она превращается (id и метка сохраняются) в спецфишку вида партнёра в состоянии `armed`. Риффы получают ось `h` при чётном k и `v` при нечётном. Засчитывается сбор фишки цвета X, +30 очков, событие `transform`. Иначе превращение пропускается, его время сохраняется.
3. В тике `t_end = t0 + T.transform_step·#L` источник комбо бьёт клетку `to` (этот удар снимает обе спецфишки комбо), затем `from` (открытый слот).
4. Пусть `t_last = t0 + T.transform_step·(#L − 1)`. Запуск k — запись `activate` на тик `t_last + T.fire_step·(k+1)`: если превращение k состоялось (фишка L[k] — `armed` спецфишка), она активируется внутри этой записи с меткой комбо; иначе запись ничего не делает.
5. Естественный порядок: превращения по k, удары по `to` и `from`, запуски по k.
6. Превращённые спецфишки стоят `armed` и цепочкой не запускаются (7.2.2).

### 8.6 Цепочки

- Спецфишка в `idle`, получившая удар `effect`, запускается (7.2.1): `armed` сейчас, активация через `T.chain` с меткой ударившего источника, в той клетке, где стоит.
- Рифф сохраняет свою ось (кроме Риффа-груза, 8.3). Диско-шар от цепочки выбирает X при активации.

## 9. Цели Пташки

Цель выбирается в момент выбора (после креста) по текущей доске.

**Уровень клетки** — наибольший из подходящих строк. «Фишка» в таблице — фишка в `idle`, не закреплённая; фишка в другом состоянии ничего не даёт сама, её слот считается открытым. Если в клетке закреплённая фишка, уровень клетки — 0 целиком (её и так ударит другой источник).

| Уровень | Что в клетке |
|---|---|
| 5 | целый `concrete`, пока открыта цель `break concrete` |
| 4 | целый блокер другого вида из открытой цели `break`; фишка во льду при открытой цели `ice` (10.11); обычная фишка без проводов и не во льду цвета открытой цели `collect`; незажжённая плитка при открытой цели `light`, если этот удар её повредит: проводов нет и либо слот открыт, либо в нём обычная фишка не во льду, либо одноклеточный блокер с `hp` 1; незастеленная клетка при открытой цели `carpet`, если выбирающий источник стелет ковёр (10.8) и в клетке нет ни целого блокера, ни фишки на цепи (пустой слот, микрофон, кокос — тоже годятся) |
| 3 | клетка прямо под микрофоном в `idle`, пока открыта цель `deliver` (или прямо под кокосом в `idle`, пока открыта цель `drop`), если удар её освободит: в ней обычная фишка без проводов и не во льду или одноклеточный блокер с `hp` 1. Клетка «под» фишкой, стоящей во входе портала, — выход его пары (10.14) |
| 2 | любой другой целый блокер; обычная фишка под проводами; фишка во льду без открытой цели `ice`; спецфишка |
| 0 | клетка с фишкой на цепи (10.6): целиком, вместе с плиткой под ней, — удар Пташки ничего бы там не сделал |
| 1 | любая другая обычная фишка |
| 0 | всё остальное: пустой или открытый слот без плитки уровня 4, микрофон, кокос |

- Колонка 2×2 даёт уровень по строкам блокеров только в своей левой верхней клетке; остальные три её клетки — уровень 0. Плитки под колонкой строкой 4 не учитываются: колонка — не одноклеточный блокер.

**Кандидаты** — существующие клетки с уровнем ≥ 1, кроме:
- клеток объектов, уже задетых текущим источником (его ключи дедупликации, включая крест);
- клеток объектов, зарезервированных любой летящей Пташкой.

Если кандидатов нет — «целей нет» (8.3.4).

**Одиночный удар.** Максимальный уровень → максимальная «плотность» (число существующих клеток с уровнем ≥ 3 в квадрате 3×3 с центром в кандидате, сам кандидат включён) → выбор из потока `effects` среди равных лучших (3.2.1: одна трата, даже если лучший один).

**С грузом.** Площадь груза: Сабвуфер — 5×5 с центром в кандидате; Рифф — весь ряд или вся колонка через кандидата. Объект входит в площадь, если в неё попадает хотя бы одна его клетка; колонка входит один раз с уровнем своей левой верхней клетки. Для кандидата считается кортеж `(A, B, C, D)` — число объектов площади с уровнем 4–5, 3, 2 и 1. Побеждает лексикографически наибольший кортеж («больше всего элементов цели», как в плане); у Риффа сначала выбирается лучшая из двух осей (при равенстве `h`), и эта ось используется при ударе. Среди равных лучших — выбор из потока `effects` (одна трата).

**«Трио».** Три цели выбираются по очереди, каждая — с учётом резервов предыдущих; каждый выбор с кандидатами тратит один `next_int`.

## 10. Гравитация, спавн, микрофоны, кокосы, цепи, занавес, ковёр, конвейер, бумбокс, лёд, стог сена, туман, портал

### 10.1 Назначение падений (шаг 5 тика)

```
counter[x] = 0 для каждой колонки
для y = H..1, для x = 1..W:
  c = (x, y)
  если c существует и её слот пуст:
    r = scan(c)
    piece(Q)  -> перенос Q в c
    spawn     -> новая фишка в c
    wait      -> ничего
    blocked   -> диагональ для c

scan(c):
  k = y_c
  пока k > верх отрезка c:
    k = k - 1
    e = содержимое слота (x, k)
    если e пусто: продолжить
    1. e (фишка или блокер) в clear, swap или armed   -> wait
    2. e закреплена                                   -> wait
    3. e — целый блокер, фишка под проводами или во льду -> blocked
    4. e — подвижная фишка в idle или fall              -> piece(e)
  -- все клетки отрезка над c пусты
  если верх отрезка — спавнер -> spawn
  если верх отрезка — выход портала -> through(вход этой пары, c — сам выход?)   -- 10.14
  иначе -> blocked
```

Ветка `through` есть только на уровне с порталами и описана в 10.14; её результаты — `wait`, `blocked` и `hop` (прыжок через портал, тоже назначение). На уровне без порталов `scan` тот же, что был.

**Перенос Q** из клетки S в c: `offy += (y_c − y_S)·3600`, `offx` не меняется; метки по 1.3.5 (с учётом клеток между S и c). Если Q была `idle`: `state = fall`, `vy = T.fall_v0`, `delay = counter[x]`, `counter[x] += 1`. Если Q уже падала — `vy` и `delay` сохраняются, счётчик не растёт. S пустеет и будет обработана позже в этом же проходе.

**Спавн** под спавнером в ряду `y_s`: новая фишка (микрофон по 10.4, кокос по 10.5 или обычная по 10.3) получает новый id и записывается прямо в c в состоянии `fall`: `vy = T.fall_v0`, `delay = counter[x]`, `counter[x] += 1`, `offx = 0`, метка по 1.3.6, событие `spawn`.
- `offy = max((y_c − y_s + 1)·3600, y_c·3600 − top + 3600)`, где `top` — наименьший `vis_y` среди падающих фишек этого отрезка (включая заспавненные раньше в этом проходе); если таких нет — только первый член. То есть фишка стартует на клетку выше спавнера, но не ближе чем на клетку к самой высокой падающей фишке.
- Пока фишка целиком выше верхнего края своего спавнера (`vis_y ≤ (y_s − 1)·3600`), `pieces()` отдаёт её с `hidden = true`; клиент обрезает её рисование по верхнему краю спавнера.

**Диагональ** для клетки c со статусом `blocked`:
1. Если в отрезке c ниже неё есть падающая фишка, чей визуальный центр выше центра c (`vis_y < y_c·3600`), — c в этом проходе считается `wait`.
2. Доноры — клетки `(x−1, y−1)` и `(x+1, y−1)`; в чётных тиках сначала левый, в нечётных — правый. Донор D подходит, если в его клетке подвижная фишка в `idle`, не закреплённая, и клетка под D не существует или её слот не пуст. Если D — вход портала, «клетка под D» — выход его пары (10.14): донор подходит, только когда слот выхода не пуст.
3. Первый подходящий D переносится в c: `offx = +3600` (донор слева) или `−3600` (справа), `offy = 3600`, `state = fall`, `vy = T.fall_v0`, `delay = counter[x]`, `counter[x] += 1`; метки по 1.3.5. Фишка, которая в этом же проходе займёт освободившуюся клетку D, получает `vy = min(vy, vy_D)` и `delay = max(delay, delay_D + 1)`.
4. Подходящих доноров нет — c остаётся **дырой**. Дыры допустимы в покое; `has_move`, перемешивание и подсказка их просто пропускают (в них нет фишек). Дыра заполнится, когда исчезнет препятствие.

Назначение — любой перенос, спавн или диагональ. Их число за проход нужно для покоя (раздел 11).

### 10.2 Движение (шаг 6)

Обычный режим:

```
для x = 1..W:
  для каждой фишки P в fall с целевой колонкой x, по убыванию целевого y:
    если P.delay > 0: P.delay -= 1; следующая
    vy = min(vy + T.fall_acc, T.fall_vmax)
    new = offy - vy
    B = ближайшее содержимое ниже целевой клетки P в том же отрезке
        (если B падает, она уже сдвинута в этом тике)
    если B в fall:
      lim = y_P·3600 - vis_y(B) + 3600        -- не ближе клетки к B
      если lim > new:                        -- упёрлась (строго больше)
        new = min(lim, offy)                 -- упор не поднимает фишку
        vy = min(vy, B.vy)
    d = offy - new; offy = new
    если offx ≠ 0: |offx| уменьшается на d, не ниже 0 (знак сохраняется)
    если offy <= 0:
      offy = 0, offx = 0, vy = 0, state = idle, settle_tick = now
      поле «грязное», событие land
```

Турбо: каждая фишка в `fall` (колонки слева направо, в колонке снизу вверх) сразу приземляется: `offy = offx = vy = delay = 0`, `idle`, `settle_tick = now`, поле «грязное», событие `land`.

### 10.3 Цвет новой фишки

Для каждого спавна в порядке прохода 10.1:
1. Решение о микрофоне (10.4), затем о кокосе (10.5). Микрофон или кокос — случайность не тратится.
2. Если уровень помощи > 0: `p = int(100)` из потока `spawn`. При `p ≤ 5` (уровень 1: 3–4 поражения подряд на уровне) или `p ≤ 10` (уровень 2: 5 и больше) — принудительный цвет, больше выборов нет.
3. Иначе — взвешенный выбор цвета уровня (3.2) с весами `spawn_weights` из потока `spawn`.

**Принудительный цвет** — первое подходящее:
1. цвет открытой цели `collect` с наибольшим остатком (ничья — меньший номер);
2. при открытой цели `break balloon` — цвет, у которого на поле больше всего целых шариков (ничья — меньший номер);
3. `mf()`;
4. наименьший цвет уровня.

Помощь работает только в пользу игрока, покупки на неё не влияют. Уровень помощи записывается в реплей.

### 10.4 Микрофоны

- **Счётчики:** `released` — выпущено (стартовые считаются), `on_board` — на поле и не доставлены, `moves_made` — принятые свапы и тапы минус откаты (5.1, 5.2; бустеры и `continue` не считаются), `last_mic` — `moves_made` в момент последнего выпуска. На старте `last_mic = 0`, если есть стартовые микрофоны, иначе `−gap_moves`.
- **Выпуск.** Спавн ставит микрофон вместо цветной фишки, если одновременно:
  - есть цель `deliver` и `released < total`;
  - `on_board < on_board_max`;
  - `moves_made − last_mic ≥ gap_moves`;
  - в этом проходе 10.1 микрофон ещё не выпускался.

  Тогда `released += 1`, `on_board += 1`, `last_mic = moves_made`.
- **Доставка** проверяется в шаге 7 **каждого** тика, после поиска матчей: каждый микрофон в `idle` на стойке, по индексу, переходит в `clear` на `T.clear`; `vac` = его метка; `on_board -= 1`; цель `deliver` −1; событие `mic_delivered`.

### 10.5 Кокосы

Кокос (`kind = coconut`) — бесцветная подвижная фишка района «Босса-Бич»: падает вместе с фишками (10.1–10.2, включая диагональ), свапается по 5.1, не матчится и не получает урона ни от какого удара (7.1.3). Цель `drop {count}` — опустить `count` кокосов до клетки выхода. Клетки выхода — `exits` уровня (по умолчанию низ каждого отрезка, то есть нижняя клетка колонки, а в колонке с разрывом — нижняя клетка каждой её части).

- **Счётчики** — те же, что у микрофонов (в одном уровне не бывает и микрофонов, и кокосов, правило 2.1.11): `released` — выпущено (стартовые считаются), `on_board` — на поле и не собраны, `last_mic` — `moves_made` в момент последнего выпуска. На старте `last_mic = 0`, если есть стартовые кокосы, иначе `−gap_moves` (первый кокос может войти сразу).
- **Выпуск.** Спавн в колонке `x` ставит кокос вместо цветной фишки, если одновременно:
  - есть блок `coconut` и `released < total`;
  - `on_board < on_board_max`;
  - `moves_made − last_mic ≥ gap_moves`;
  - колонка `x` входит в `columns` (или списка нет);
  - в этом проходе 10.1 кокос ещё не выпускался.

  Тогда `released += 1`, `on_board += 1`, `last_mic = moves_made`. Случайность не тратится. Проход 10.1 идёт снизу вверх и слева направо, поэтому кокос получает первый подходящий спавн прохода.
- **Сбор** проверяется в шаге 7 **каждого** тика, после поиска матчей и доставки микрофонов: каждый кокос в `idle` на клетке выхода, по индексу, переходит в `clear` на `T.clear` (потом слот пустеет, и колонка над ним падает); `vac` = его метка; `on_board -= 1`; +50 очков; цель `drop` −1; событие `coconut_collected`. Покоя поля сбор не ждёт: кокос уходит в том же тике, в котором приземлился на выход. Кокос собирается и после выполнения цели (если `total > count`): очки начисляются, события `goal` уже нет.

### 10.6 Цепи

Цепь — замок на обычной фишке района «Карнавал» (с уровня 121): поле `chain` объекта, прочность 1 или 2. Задаётся только стартовой раскладкой (`overlay` с `type: "chain"`): цепь получает стартовая фишка этой клетки — заданная `piece` или случайная. Во время игры новые цепи не появляются. В отличие от проводов (1.1) цепь — свойство **фишки**, а не клетки, и снимается **только матчем**.

- **Движение.** Фишка на цепи — подвижная фишка для гравитации: падает, соскальзывает по диагонали, бывает донором, закрепляется на пути эффекта (10.1–10.2, 7.2.7) — всё как у свободной. Цепь едет вместе с ней. Колонок она не запирает.
- **Ввод.** Игрок её не двигает: свап, в котором фишка на цепи стоит в `from` или в `to`, отклоняется с `not_movable` (5.1.1.4); спецфишка, свайпнутая на неё, исполняется как тап (5.1.1.2); «Кроссфейдер» её не берёт (`not_movable`). В списке пар 12.1 её нет.
- **Матч.** Она сохраняет цвет и входит в группы там, где стоит (раздел 6). Удар `match` по ней: `chain −= 1`, +50 очков, событие `hit` (слой `chain`), метка фишки поднимается до метки группы; при `chain = 0` — событие `unchained`, цель `chains` −1, и фишка с этого момента обычная свободная. Сама фишка этим ударом **не уничтожается** (очков `20 × W` за неё нет, в цель `collect` она не идёт); остальные фишки группы уничтожаются как всегда. Клетка фишки на цепи не бывает клеткой новой спецфишки (6.2); если в группе все клетки на цепях, спецфишка не создаётся.
- **Повторный поиск.** Уцелевшие фишки остаются в `idle`, поэтому поиск, в котором была задета хотя бы одна цепь, оставляет поле «грязным» (раздел 6): следующий поиск — отдельная волна (`W + 1`) с новыми источниками. Обычно он ничего не находит (соседи по группе уже в `clear`). Линия или квадрат целиком из уцелевших фишек получает по одному удару за поиск: цепи hp 2 — два поиска, затем освобождённые фишки матчатся как обычные. Прочность конечна, поэтому каскад заканчивается.
- **Всё остальное её не трогает.** Удары `effect` (Рифф, Сабвуфер, Пташка, Диско-шар, все комбо, бустеры) и `adjacent` не снимают цепь и не уничтожают фишку — проходят мимо, как мимо кокоса; плитка пола под ней от них не зажигается (кроме «Гранд-финала», чей удар `all_layers` бьёт пол всегда). Диско-шар не выбирает цвет по фишкам на цепи и не включает их в список L; «Цвет X» их не превращает.
- **Бустеры.** `stick` по фишке на цепи — `bad_cell` (клетка без эффекта, 5.3), как по кокосу; `row_light`/`col_light` проходят сквозь неё и отклоняются, если в ряду или колонке нет ни одной клетки с эффектом; `remix` её не трогает; `swap` («Кроссфейдер») — `not_movable`.
- **Пташка** никогда не выбирает клетку с фишкой на цепи (уровень 0 в таблице раздела 9, вместе с плиткой под ней) и клетку под микрофоном или кокосом не считает «освобождаемой», если в ней фишка на цепи.
- **Никто не превращает её в другое.** Кандидатами не бывают фишки на цепи: пред-уровневые бустеры (4.5), Рифф продолжения и подарок бонус-шкалы (5.4), Риффы финального концерта (13.3), рост помех (11), перемешивание и Ремикс (12.2: она остаётся в своей клетке со своим цветом).
- **Тупик.** `has_move` не считает ходы самой фишкой на цепи, но считает ход, матч которого её включает. Если ходов нет, работает обычное перемешивание 12.2 среди свободных фишек; если свободных фишек и фишек под проводами нет вовсе — правило 12.2.4а: одна фишка на цепи теряет цепь и становится Риффом, цель её засчитывает.
- **Цель** `chains {count}` — разбить `count` цепей (`count` ≤ числу цепей на старте). Цепь засчитывается в момент, когда её прочность стала 0; hp 2 даёт 100 очков за две единицы и одну единицу цели.
- **Хеш:** прочность цепи входит в поле `hp` объекта (17.2).

### 10.7 Занавес

Занавес — элемент района «Кинотеатр» (с уровня 141) и первый элемент, которым управляет **счётчик ходов**. Блок `curtain` уровня перечисляет клетки под занавесом (`covers`; соседние клетки выглядят одной портьерой) и задаёт общий ритм: занавесы закрыты `closed_moves` ходов, затем открыты `open_moves` ходов, и так по кругу; `start` — стартовая фаза. Сам занавес не разрушается и своей цели не имеет: задача — успеть сделать работу под ним, пока он открыт. Уровень сочетает его с обычными целями.

Состояние: `cur_closed` (занавесы закрыты) и `cur_left` (сколько ходов осталось до смены фазы). На старте `cur_left` = `closed_moves` или `open_moves` по стартовой фазе. **Закрытая клетка** — клетка из `covers`, пока `cur_closed` истинно. На уровне без блока `curtain` закрытых клеток нет, и ни одно правило этого раздела не действует.

- **Счёт ходов.** Фаза меняется только в шаге 8, когда поле в покое и игра в `playing` (раздел 11), сразу после роста помех: для каждого действия очереди конца хода (принятый свап или тап, кроме возвращённых) `cur_left −= 1`; при `cur_left = 0` фаза меняется на противоположную, `cur_left` получает длину новой фазы, событие `curtain` (`reason = move`); иначе событие `curtain_left`. Каскады, неудачные и возвращённые свапы, бустеры и `continue` счёт не двигают. Несколько ходов, успокоившихся вместе, считаются по очереди в одном шаге (занавес может открыться и закрыться в одном шаге — два события `curtain`).
- **Закрытая клетка заморожена.** Что бы в ней ни стояло (и пустой слот тоже):
  - игрок её не двигает: свап из неё или в неё — `not_movable`, тап по спецфишке в ней — `not_movable`; спецфишка, свайпнутая на закрытую клетку, исполняется как тап (5.1.1); в списке пар 12.1 и в подсказке её нет;
  - фишка в ней не имеет цвета (раздел 6, 5.1.2): в матчи не входит, линию через неё не образует;
  - ни один удар по ней ничего не делает (7.1): `match`, `adjacent`, `effect`, удар `all_layers` «Гранд-финала», бустеры. Защищены и провода, и содержимое слота, и плитка пола под занавесом; спецфишка под занавесом цепочкой не запускается; пути эффектов её не закрепляют;
  - гравитация её не трогает: содержимое не падает и не бывает донором по диагонали; пустая закрытая клетка не заполняется; для `scan` (10.1) закрытая клетка — `blocked` (как целый блокер), пустая она или нет. Поэтому фишки над закрытой клеткой лежат на ней, а клетки под ней заполняются по правилу диагонали 10.1 или остаются дырами, пока занавес не откроется; для правила диагонали пустая закрытая клетка под донором считается занятой;
  - её не выбирают: диско-шар и «Цвет X» (списки L, 8.4–8.5), `mf()` (3.2.3), Пташка (уровень клетки 0, раздел 9), рост помех (ни помеха под занавесом не растёт, ни фишка под ним не становится помехой), перемешивание и Ремикс (12.2: кандидатами бывают только фишки вне закрытых клеток), Рифф продолжения и подарок бонус-шкалы (5.4), пред-уровневые бустеры (4.5).
- **Открытая клетка** — обычная клетка без каких-либо особенностей: в неё падают фишки, спецфишки, микрофоны и кокосы, по ней идут удары, в неё растут помехи. Поэтому под закрывшимся занавесом может оказаться что угодно; правила выше не зависят от содержимого.
- **Открытие.** В шаге 8 тика `t`: событие `curtain` (`phase = open`), поле становится «грязным», остальная часть шага 8 (конец ходов, проверка тупика) в этом тике не выполняется. В тике `t + 1`: шаг 5 возвращает клетки гравитации, шаг 7 ищет матчи по всему полю. Линии и квадраты, сложившиеся под занавесом или вместе с соседями, пока он был закрыт, разрешаются как обычный каскад: метка группы по 1.3.8 (номер действия — из меток её фишек), очки и цели засчитываются, ход не тратится и счёт занавеса не двигается (очередь конца хода уже пуста). Когда поле снова придёт в покой, шаг 8 выполнит проверки `moves_left == 0` и `has_move`.
- **Закрытие.** Событие `curtain` (`phase = closed`); больше ничего не происходит: поле в покое, под занавес ничего не летит и ничто в нём не закреплено. Шаг 8 продолжается как обычно.
- **Бустеры** (5.3): `stick` по закрытой клетке — `bad_cell` (клетка без эффекта); `row_light` и `col_light` проходят над закрытыми клетками, не задевая их, и отклоняются с `bad_cell`, если в ряду или колонке нет ни одной клетки с эффектом; `remix` переставляет только фишки вне закрытых клеток; `swap` («Кроссфейдер») с закрытой клеткой — `not_movable`.
- **Тупика не бывает.** Если в шаге 8 `has_move()` ложно, а занавесы закрыты, перемешивания нет: занавесы сразу открываются — `cur_closed = false`, `cur_left = open_moves` (полная открытая фаза), событие `curtain` с `reason = deadlock`, дальше как при открытии. Это покрывает и случай, когда вне занавесов нет ни одной фишки. Если ходов нет и при открытых занавесах, работает обычное перемешивание 12.2 (следующий покой). Поэтому пункты 4–6 раздела 12.2 при закрытых занавесах не выполняются никогда.
- **Конец ходов.** `out_of_moves` наступает как обычно; фаза и счёт сохраняются, `continue` продолжает с них.
- **Победа.** При переходе в `concert` (13.2) закрытые занавесы открываются (событие `curtain`, `reason = concert`) и остаются открытыми до конца уровня.
- **События:** `curtain {phase, cells, left, reason}` и `curtain_left {phase, left}` (раздел 16). `game:status().curtain = {phase, left}`, `game:cells()[i].curtain`, `game:pieces()[k].veiled` (17.3).
- **Хеш:** `cur_closed` и `cur_left` пишутся в конец хеша только на уровне с блоком `curtain` (17.2).

### 10.8 Ковёр

Ковёр — элемент района «Восточный базар» (с уровня 161) и первое покрытие, которое расстилает **сам игрок**. Плитки танцпола (раздел 1) ставит уровень, и каждая зажигается отдельно, ударом по своей клетке; помехи (раздел 11) растут сами. Ковёр — наоборот: уровень даёт несколько застеленных клеток (поле `carpet`), а дальше ковёр идёт туда, куда его ведут матчи игрока. Цель `carpet` — застелить все клетки поля.

Состояние: флаг `carpet[i]` у каждой клетки (застелена или нет). На уровне без поля `carpet` флагов нет, и ни одно правило этого раздела не действует: такие уровни играются, считаются и хешируются как раньше.

- **Источник стелет ковёр.** У источника удара (1.4.6) есть флаг `carpet`. Удар источника с этим флагом застилает клетку (7.1, пункт 0а); больше ковёр не появляется ниоткуда. Флаг ставится при создании источника и потом не меняется:
  1. **Матч.** Источник `match` группы стелет ковёр, если в момент разрешения группы **хотя бы одна её клетка застелена**. Тогда ковёр ложится под **все** клетки группы. Группа, целиком стоящая вне ковра (даже вплотную к нему), ничего не стелет. Источник `adjacent` не стелет никогда: соседи группы ковра не получают.
  2. **Спецфишка.** Источник активации стелет ковёр, если в момент активации (`t0`, 7.2.5) **клетка спецфишки застелена**. Он застилает каждую клетку, по которой бьёт: ряд Риффа, квадрат Сабвуфера, крест и цель Пташки, каждую фишку списка L Диско-шара. Спецфишку можно свапнуть на ковёр: она срабатывает в клетке `to`. Спецфишка, созданная матчем на ковре, стоит на застеленной клетке (группа её застелила).
  3. **Цепочка** отдельного правила не имеет: удар источника с ковром сначала застилает клетку задетой спецфишки (пункт 0а раньше запуска), поэтому она сработает уже с ковра; спецфишка на ковре, задетая источником без ковра, тоже стелет; спецфишка вне ковра, задетая источником без ковра, — нет.
  4. **Комбо.** Источник комбо стелет ковёр, если застелена клетка `to` **или** клетка `from` (обе спецфишки — «начало» эффекта). Груз Пташки (новый источник, 8.3) стелет, если стелет источник Пташки или застелена клетка, в которой груз активируется. Спецфишки, превращённые комбо «Цвет X», активируются каждая в своей клетке по пункту 2.
  5. **Бустеры.** `row_light` и `col_light` стелют ковёр, если в момент выполнения в их ряду (колонке) есть **хотя бы одна застеленная клетка**; тогда ковёр ложится вдоль всего ряда (колонки). `stick` не стелет никогда (удар по одной клетке). «Кроссфейдер» и Ремикс ударов не наносят; матч после обмена — обычный матч по пункту 1.
  6. **Финальный концерт** — обычные активации по пункту 2 (цель к этому времени выполнена).
- **Блокер — стена.** Клетка, в которой в момент удара стоит целый блокер (любая из четырёх клеток колонки 2×2 тоже), не застилается — даже тем ударом, который блокер разрушает. Блокер нужно сначала убрать; застелет клетку следующий удар источника с ковром (матч через эту клетку или эффект). Блокер в `clear` — уже открытый слот, клетка под ним застилается.
- **Всё остальное ковру не мешает.** Клетка с проводами и клетка с фишкой на цепи — обычные клетки группы: ковёр ложится под них, хотя сами фишки остаются на месте (удар `match` снимает слой проводов или цепи, как всегда). Удар эффекта с ковром застилает клетку с проводами, фишкой на цепи, микрофоном, кокосом, спецфишкой и пустую клетку (дыру, 10.1), хотя содержимое этих клеток он не трогает или трогает по обычным правилам 7.1.
- **Закрытая клетка занавеса** (10.7) не получает ничего, как от любого удара: ковёр под закрытый занавес не ложится.
- **Ковёр не убывает.** Застеленная клетка остаётся застеленной до конца уровня: ни один удар, ни рост помех, ни перемешивание, ни спавн ковёр не снимают. Помеха может вырасти на застеленную клетку; ковёр под ней остаётся.
- **Пустоты** (несуществующие клетки) ковра не имеют и в цель не входят.
- **Ковёр и танцпол** в одном уровне не встречаются (правило 2.1.13).
- **Очки.** +50 за каждую новую застеленную клетку (как единица прочности плитки, 7.4); очки входят в событие `score` того же удара.
- **Цель** `carpet {}`: остаток — число существующих незастеленных клеток; на старте это все клетки поля минус список `carpet`. Каждая новая застеленная клетка — −1. Последняя клетка выигрывает уровень сразу (раздел 13).
- **Пташка** источника, который стелет ковёр, при открытой цели считает незастеленную клетку клеткой цели (уровень 4, раздел 9). Остальные Пташки ковра не видят.
- **Подсказка** (12.3): свап, виртуальная группа которого стоит и на ковре, и вне его, — ход с прогрессом цели.
- **Тупика ковёр не создаёт:** он не занимает слот и не меняет ни ходы, ни гравитацию. Правило 2.1.13 гарантирует, что каждую клетку можно застелить матчем.
- **События:** `carpet {x, y}` — клетка застелена (раздел 16). `game:cells()[i].carpet` (17.3).
- **Хеш:** флаги клеток и флаги `carpet` активных источников пишутся в конец хеша только на уровне с ковром (17.2).

### 10.9 Конвейер

Конвейер — элемент района «Небесный клуб» (с уровня 181) и первый элемент, который **двигает фишки**. Поле `conveyor` уровня — список лент. Лента — путь из клеток (`path`, не меньше трёх; соседние клетки списка — соседи по стороне, правило 2.1.14), порядок списка — направление движения. Путь может быть прямым отрезком, ломаной или **кольцом** (последняя клетка — сосед первой). Все ленты замкнуты: содержимое последней клетки переходит в первую. У кольца это обычный шаг в соседнюю клетку, у открытого пути — «прыжок» с конца в начало. Лент без замыкания (фишка уходит с поля, в начале появляется новая) нет. Своей цели у конвейера нет: он добавляет движение к обычным целям.

Ленты — статические данные уровня: в состоянии игры у них нет ничего своего, поэтому в хеше нового нет (17.2). На уровне без поля `conveyor` ни одно правило этого раздела не действует.

- **Когда.** Ленты двигаются только в шаге 8, когда поле в покое и игра в `playing` (раздел 11): после роста помех и после счёта ходов занавеса, по одному шагу за каждое действие очереди конца хода (принятый свап или тап, кроме возвращённых). Каскады, неудачные и возвращённые свапы, бустеры и `continue` ленту не двигают. Если вместе успокоились несколько ходов, сначала за все эти ходы растут помехи, затем за все считается занавес, затем за каждый ход по очереди все ленты делают по шагу.
- **Шаг.** Для каждой ленты в порядке списка уровня: содержимое слота каждой клетки переходит в следующую клетку списка, содержимое последней — в первую. Едет то, что двигается: обычная фишка, спецфишка, микрофон, кокос, фишка на цепи (цепь едет вместе с ней) и пустой слот (дыра переезжает как пустота). id, метка и все свойства объекта сохраняются; `vac` клеток не меняется.
- **Что остаётся.** Всё, что принадлежит клетке: плитка танцпола, ковёр, спавнер, клетка выхода, занавес, провода.
- **Затор.** Лента не двигается за этот ход целиком, если хотя бы на одной её клетке стоит то, что не едет: клетка закрыта занавесом (10.7), в ней блокер (на ленту могла вырасти помеха; остальные блокеры на ленту не попадают, правило 2.1.14) или на ней провода. Событие `conveyor` с `jam = true`. Остальные ленты уровня двигаются как обычно. Когда препятствие исчезает (помеха разбита, занавес открыт), лента снова едет со следующего хода. Порядок шага 8 делает правило точным: помеха, выросшая на ленту в этом же шаге, уже останавливает её; занавес, закрывшийся этим ходом, останавливает; открывшийся этим ходом — уже нет.
- **Блокировка.** Переехавшие объекты сразу стоят в новых клетках и на `T.conveyor` тиков уходят в `swap` без обмена (блокировка, как после перемешивания 12.2): игрок их не берёт, гравитация ждёт (`wait`), ожидаемая доска (5.1.2) считает их в новой клетке. Событие `conveyor` со списком переездов. В шаге 2 тика, в котором блокировка кончается, они становятся `idle` (`settle_tick = now`), и идёт поиск матчей по всему полю.
- **Каскад.** Матчи, сложившиеся сдвигом, разрешаются как обычный каскад: метка группы по 1.3.8 (номер действия — из меток её фишек), очки и цели засчитываются, ход не тратится, лента второй раз не двигается (очередь конца хода уже пуста). Новая спецфишка группы встаёт по правилу 6.2.3 (приехавшая фишка успокоилась последней). Дыра, приехавшая под фишку, заполняется гравитацией.
- **Остаток шага 8.** Если хотя бы одна лента что-то перевезла, пункты 2–3 шага 8 (конец ходов, проверка тупика) в этом тике не выполняются: их выполнит следующий покой, после каскада сдвига. Поэтому последний ход сначала двигает ленту, и её каскад ещё может выиграть уровень; `out_of_moves` наступает после него. Если ни одна лента ничего не перевезла (все в заторе или пусты), шаг 8 продолжается как обычно.
- **Микрофоны и кокосы.** Доставка и сбор (10.4, 10.5) идут по обычному правилу — объект в `idle` на клетке выхода, шаг 7. Объект, приехавший на клетку выхода, собирается в тике, в котором кончилась блокировка (шаг 2 делает его `idle`, шаг 7 того же тика собирает), а не во время переезда. Лента может и увезти объект от выхода.
- **Ввод, ходы, подсказка.** Фишки на ленте в покое — обычные фишки: свапаются, матчатся, получают удары, входят в `moves()`, `has_move()` и подсказку; все они считаются по доске как она стоит, без взгляда на шаг вперёд. Перемешивание и Ремикс переставляют клетки ленты как любые другие. Тупик — обычное перемешивание 12.2.
- **Старт.** Стартовая доска строится по разделу 4 без оглядки на ленты; первый шаг — после первого хода.
- **Победа.** В `won_wait` и `concert` ленты стоят (очередь конца хода очищается, 13.2).
- **События:** `conveyor {belt, moves, duration, jam}` (раздел 16). `game:cells()[i].conveyor = {belt, pos, dir, last}` (17.3).

### 10.10 Бумбокс

Бумбокс — элемент района «Хип-хоп квартал» (с уровня 201) и первый блокер, который **отвечает**. Сам по себе это одноклеточный блокер `boombox` с прочностью 1–3 (`slots`, `{"type": "boombox", "hp": 1..3}`): стоит на месте, не падает, не свапается, получает удары ровно как `record_box` (7.3) — −1 от удара `adjacent` и −1 от удара `effect`, удар `match` по нему невозможен (он не в группе). Новое — то, что происходит после удара: каждый раз, когда бумбокс теряет `hp` от **соседнего матча**, он «играет» цвет этого матча, и несколько свободных фишек того же цвета в других местах поля уничтожаются. Матч у бумбокса стоит больше своих трёх фишек, а какие именно фишки лопнут — решает случай.

Своего состояния у бумбокса нет: это обычный объект-блокер (код 6, 17.2), прочность лежит в `hp`. На уровне без бумбоксов ни одно правило этого раздела не действует: источники не создаются, поток `effects` не тратится, хеш тот же, что был.

- **Когда играет.** Только удар `adjacent` (соседний матч, пункт 4 раздела 6.3), который снял с целого бумбокса единицу `hp`. Удар `effect` (спецфишка, комбо, груз Пташки, бустер, концерт) снимает `hp` так же, но цвета не имеет и **ничего не играет**. Удар, пропущенный дедупликацией, и удар по уже разрушенному бумбоксу (открытый слот) `hp` не снимают и ничего не играют. Под закрытым занавесом бумбокс не оказывается никогда: на старте его там нет (2.1.12), а с места он не сходит.
- **Сколько.** Одна игра — `BLAST = 3` фишки. Если этот удар разрушил бумбокс (`hp` стал 0) — последняя, большая игра: `BLAST_LAST = 5` фишек. Кандидатов меньше — уничтожаются все, какие есть; кандидатов нет — игра состоялась (событие есть), но ничего не уничтожено.
- **Шаг в порядке ударов** — пункт 4а раздела 6.3. Группа разрешается как всегда: удары `match` по её клеткам, новая спецфишка и бонус, затем **все** удары `adjacent` по соседям (вместе с событиями, очками и целями каждого удара; если разрушение бумбокса выполнило последнюю цель, событие `state` стоит здесь же). Только после последнего удара `adjacent` играют бумбоксы, задетые этой группой, — по возрастанию индекса своей клетки, каждая игра целиком: выбор целей, событие `boombox`, удары по целям. Затем похвала (пункт 5), затем следующая группа того же поиска. Всё это — один шаг одного тика (шаг 2 или шаг 7): задержек нет, в обычном режиме и в турбо результат один.
- **Кандидаты** одной игры строятся по доске в момент этой игры (то есть после ударов группы и после предыдущих игр): обычные фишки (`regular`) цвета группы в состоянии `idle`, у которых одновременно:
  - нет проводов, нет цепи и нет льда (10.11);
  - клетка не закрыта занавесом (10.7);
  - фишка не закреплена (`pins`, 1.2: её и так ударит другой источник);
  - клетка не входит ни в одну группу **этого поиска** — ни в свою (уцелевшие фишки группы: освобождённая от проводов, фишка на цепи), ни в уже разрешённую, ни в ещё не разрешённую. Фишки матча, который сейчас разрешается, бумбокс не трогает.

  Фишки в `fall`, `swap`, `clear` и `armed`, шарики, спецфишки и всё остальное кандидатами не бывают. Клетка может быть где угодно: рядом с бумбоксом, на ленте конвейера, на плитке, на ковре, под микрофоном.
- **Случайность.** Список кандидатов упорядочен по индексу клетки. Цели выбираются по одной: каждая — один выбор 3.2.1 из потока `effects` среди **оставшихся** кандидатов (выбранный вычёркивается). Одна цель — одна трата `next_int`, даже если кандидат остался один; всего трат `min(n, BLAST)` (или `min(n, BLAST_LAST)`), при `n = 0` трат нет. Другие потоки игра не трогает.
- **Удары.** Если целей хотя бы одна, создаётся новый источник вида `effect` (1.4.5) с меткой группы `(M, W)` и её цветом; он бьёт выбранные клетки по возрастанию индекса обычным ударом 7.1 и сразу после этого перестаёт существовать. Каждая цель — обычная свободная фишка, поэтому удар её уничтожает: состояние `clear`, `vac` клетки = `(M, W)`, **+30 очков** (как фишка, уничтоженная спецфишкой, 7.4), цель `collect` этого цвета −1, событие `clear` с `cause = effect`. Плитка танцпола под уничтоженной фишкой получает −1 по общему правилу 7.1.4 (уничтожено содержимое слота): +50, событие `hit` слоя `floor`, при 0 — `floor_lit` и цель `light`.
- **Ковёр.** Источник игры **никогда не стелет ковёр** (флаг `carpet` ложен, 10.8): его начало — клетка блокера, а клетку с целым блокером ковёр не покрывает. Группа, стоящая на ковре, стелет его под собой как обычно; клетки, где лопнули фишки бумбокса, остаются как были.
- **Каскад.** Клетки уничтоженных фишек освобождаются через `T.clear`, как после любого удара; фишки, упавшие в них, получают метку по 1.3.5–1.3.6 от `vac = (M, W)`, поэтому их матчи — следующая волна того же хода (`W + 1`, очки `20 × W`, похвалы). Эти матчи могут снова задеть бумбокс, и он сыграет ещё раз: каскад конечен, потому что каждая игра стоит бумбоксу единицы `hp`, а разрушенный бумбокс молчит.
- **Несколько бумбоксов и несколько групп.**
  - Одна группа задела несколько бумбоксов — играет каждый, по возрастанию индекса клетки; кандидаты второй игры строятся заново, без фишек, уничтоженных первой.
  - Один бумбокс соседствует с двумя группами одного поиска — у каждой группы свой источник `adjacent`, поэтому он получает по удару от каждой (как `record_box`) и играет **один раз за каждую реально снятую единицу `hp`**: при `hp ≥ 2` — два раза, цвет каждой группы, в порядке разрешения групп; при `hp = 1` первая группа разрушает его (последняя игра), а вторая попадает в открытый слот и ничего не играет.
  - Колонки 2×2 это не касается: бумбокс занимает одну клетку.
- **Победа.** Если разрушение бумбокса выполнило последнюю цель, игра уже в `won_wait`, но игра бумбокса всё равно выполняется (каскады в `won_wait` доигрываются, раздел 13). В концерте бумбоксы, задетые матчами каскада, тоже играют; удары Риффов концерта — `effect` и ничего не играют.
- **Всё остальное — как у `record_box`.** Гравитация: целый бумбокс — `blocked` для `scan` (10.1). Ввод: не свапается, спецфишка, свайпнутая на него, исполняется как тап (5.1.1.2); «Кроссфейдер» — `not_movable`; `stick` и прожекторы бьют его (клетка с эффектом, 5.3). Рост помех на его клетку невозможен (в клетке нет фишки). Перемешивание его не трогает. Ковёр: стена (10.8). Занавес: под занавесом на старте не стоит (2.1.12). Конвейер: на ленте на старте не стоит (2.1.14). Пташка: бумбокс открытой цели `break` — клетка уровня 4, иначе уровень 2; бумбокс с `hp = 1` считается «одноклеточным блокером с `hp` 1» в строках 3 и 4 раздела 9.
- **Цель** — обычная `break {item: "boombox", count}` (`count` ≤ числу бумбоксов на старте): −1 в момент разрушения. Каждая снятая единица `hp` — +50 очков (7.4).
- **Подсказка** (12.3): свап, виртуальная группа которого соседствует по стороне с целым бумбоксом при открытой цели `break boombox`, — ход с прогрессом цели (как у `record_box`).
- **Событие** `boombox {x, y, id, color, cells, last}` (раздел 16) — в начале каждой игры, перед ударами по её целям.
- **Хеш:** нового нет. Бумбокс — блокер с кодом 6 в полях объекта; источник игры не доживает до конца шага.

### 10.11 Лёд

Лёд — элемент района «Регги-остров» (с уровня 221) и первое покрытие, под которым фишка **не матчится**. Провода (раздел 1) держат фишку на месте, но она матчится там, где стоит, и свой матч снимает с неё провода. Цепь (10.6) падает вместе с фишкой, и снимает её тоже только свой матч. Фишка во льду — наоборот: она видна (цвет просвечивает), но в матчи не входит вовсе, и растопить её можно только **снаружи** — матчем по соседству или ударом спецфишки и бустера.

Лёд — поле `ice` объекта, прочность 1 или 2 (2 — целый лёд, 1 — треснувший). Задаётся только стартовой раскладкой (`overlay` с `type: "ice"`): в лёд вмерзает стартовая фишка этой клетки — заданная `piece` или случайная. Во время игры новый лёд не появляется. На уровне без льда ни одно правило этого раздела не действует: такие уровни играются, считаются и хешируются как раньше.

- **Неподвижна.** Фишка во льду — не подвижная фишка (0.1): не падает, не соскальзывает по диагонали и не бывает донором; для `scan` (10.1) она — `blocked`, как целый блокер и фишка под проводами. Фишки над ней лежат на ней; клетки под ней заполняются по правилу диагонали или остаются дырами, пока лёд не растает. Пути эффектов её не закрепляют (7.2.7 закрепляет только подвижные фишки). Правило 2.1.7 считает её неподвижным содержимым доски `B0`.
- **Ввод.** Игрок её не двигает: свап, в котором фишка во льду стоит в `from` или в `to`, отклоняется с `not_movable` (5.1.1.4); спецфишка, свайпнутая на неё, исполняется как тап (5.1.1.2); «Кроссфейдер» её не берёт (`not_movable`). В списке пар 12.1 её нет.
- **Не матчится.** У фишки во льду нет цвета ни для поиска матчей (раздел 6), ни для ожидаемой доски (5.1.2): три одинаковых цвета в ряд, один из которых во льду, — не матч, квадрат 2×2 с ледяным углом — не квадрат; свап, который «дополнил бы» линию ледяной фишкой, — неудачный свап. Поэтому удар `match` по ней невозможен, и её клетка не бывает клеткой новой спецфишки.
- **Что снимает лёд.** Удар `adjacent` (матч по соседству по стороне, пункт 4 раздела 6.3) и удар `effect`, дошедший до клетки: разряд Риффа, кольцо Сабвуфера, крест и удар Пташки, геометрия любого комбо, груз Пташки, бустеры `stick`, `row_light`, `col_light`, Риффы концерта. (Лучи Диско-шара и игра бумбокса в ледяную фишку не попадают: они бьют только выбранные фишки, а её не выбирают — см. ниже.) Каждый такой удар снимает ровно **одну** единицу: `ice −= 1`, +50 очков (7.4), событие `hit` (слой `ice`, `id` фишки, остаток `hp`). Сама фишка ударом не уничтожается, плитка пола под ней не зажигается (как под фишкой на цепи); удар `all_layers` «Гранд-финала» снимает одну единицу льда и бьёт пол, как всегда.
- **Сколько за один раз** — как у `record_box` (7.3): один удар на источник (дедупликация по ключу объекта). Одна группа, касающаяся льда двумя клетками, снимает одну единицу; две группы одного поиска — у каждой свой источник `adjacent` — снимают по единице каждая; эффект, прошедший через клетку, — одну единицу, сколько бы раз клетка ни попала в его геометрию.
- **Освобождение.** Когда `ice` стал 0: событие `thawed` (сразу за `hit`), метка фишки поднимается до метки источника (1.3.7), цель `ice` −1. С этого момента это **обычная свободная фишка в своей клетке**: падает, свапается, матчится, получает удары, идёт в кандидаты всех выборов.
- **Порядок, если освобождённая фишка стоит в готовой линии.** Группы поиска находятся на доске до начала разрешения (раздел 6), поэтому фишка, освобождённая ударом `adjacent` в этом поиске, ни в одну его группу не входит: в этой волне она не уничтожается и очков не даёт. Удар `adjacent` следующей группы того же поиска по ней — уже удар по обычной фишке (ничего). Поиск, в котором растаял хотя бы один лёд, оставляет поле «грязным»: следующий поиск (шаг 7 того же тика; после поиска шага 7 — шаг 7 следующего тика) находит линию или квадрат с освобождённой фишкой и разрешает их как обычную группу. Её метка — `(M, W + 1)`: освобождённая фишка несёт метку `(M, W)` растопившей её группы, значит, это следующая волна того же хода (очки `20 × (W + 1)`, похвалы), ход не тратится. Лёд, растопленный ударом `effect` вне поиска (шаг 3), просто ставит флаг «грязное»: линию найдёт шаг 7 того же тика; волна считается от метки эффекта.
- **Каскад конечен.** Повторный поиск вызывает только растаявший лёд, а льда на поле конечное число, и новый не появляется.
- **Никто не выбирает её по цвету.** Фишка во льду — не свободная фишка, поэтому её нет: в `mf()` (3.2.3), в списках L Диско-шара и «Цвет X» (8.4–8.5; шар, свапнутый с фишкой её цвета, её не трогает), среди целей игры бумбокса (10.10), среди кандидатов роста помех (помеха на неё не растёт, раздел 11), пред-уровневых бустеров (4.5), Риффа продолжения и подарка бонус-шкалы (5.4), Риффов финального концерта (13.3), перемешивания и Ремикса (12.2: она остаётся в своей клетке со своим цветом и льдом). Стартовое заполнение 4.2 считает её соседом, как любую обычную фишку: случайная фишка рядом не дополняет её до линии.
- **Пташка** (раздел 9): фишка во льду при открытой цели `ice` — клетка цели (уровень 4); без такой цели — уровень 2, как фишка под проводами. Плитка под ней клетку целью не делает (удар её не зажжёт), и клетка под микрофоном или кокосом с ледяной фишкой не считается «освобождаемой».
- **Бустеры** (5.3): клетка с фишкой во льду — клетка с эффектом: `stick` принимается и снимает одну единицу льда, `row_light` и `col_light` — по единице с каждой ледяной фишки ряда или колонки; `remix` её не трогает; `swap` («Кроссфейдер») — `not_movable`.
- **Ковёр** (10.8): лёд — не блокер, клетка с ледяной фишкой — обычная клетка. Удар источника с ковром застилает её (пункт 0а раздела 7.1 выполняется до слота) и тем же ударом снимает единицу льда. Группа ледяную фишку не включает, а источник `adjacent` ковёр не стелет никогда, поэтому соседний матч лёд снимает, но ковра под ним не оставляет: клетку застелет матч через освобождённую фишку или эффект с ковром.
- **Занавес и конвейер.** Под занавесом на старте лёд не стоит (2.1.12), на ленте конвейера — тоже (2.1.14); с места ледяная фишка не сходит, поэтому ни под закрывшимся занавесом, ни на ленте она не окажется.
- **Тупик.** `has_move` считает только ходы свободных фишек; матч рядом со льдом — обычный ход. Если ходов нет, работает обычное перемешивание 12.2 среди свободных фишек: пункты 1–3 всегда дают ход, пока есть хотя бы одна свободная обычная фишка (в крайнем случае она становится Риффом). Если свободных фишек, фишек под проводами и фишек на цепи нет вовсе — правило 12.2.4б: одна случайная фишка во льду теряет лёд целиком и становится Риффом `h`, цель `ice` её засчитывает (иначе цель стала бы невыполнимой), очков нет. Поэтому поле, замёрзшее целиком, не запирается: Рифф тапается, его разряд снимает лёд по ряду.
- **Цель** `ice {count}` — растопить `count` фишек (`count` ≤ числу фишек во льду на старте). Фишка засчитывается в момент, когда прочность льда стала 0; лёд hp 2 даёт 100 очков за две единицы и одну единицу цели. Лёд тает и после выполнения цели: очки начисляются, события `goal` уже нет.
- **Подсказка** (12.3): свап, виртуальная группа которого соседствует по стороне с фишкой во льду при открытой цели `ice`, — ход с прогрессом цели.
- **События:** `hit {layer = ice, id, x, y, hp}` и `thawed {id, x, y}` (раздел 16); `shuffle.riff.from = ice` у правила 12.2.4б. `game:pieces()[k].ice` — прочность льда (17.3).
- **Хеш:** прочность льда каждой клетки пишется в конец хеша только на уровне со льдом (17.2, пункт 14).

### 10.12 Стог сена

Стог сена — элемент района «Кантри-ранчо» (с уровня 241) и первый блокер, который **прячет спецфишку** («иголка в стоге сена»). Сам по себе это одноклеточный блокер `hay` с прочностью 1–2 (`slots`, `{"type": "hay", "hp": 1..2, "gift": …}`; 2 — целый стог, 1 — поредевший): стоит на месте, не падает, не свапается, получает удары ровно как `record_box` (7.3) — −1 от удара `adjacent` и −1 от удара `effect`, один удар на источник, удар `match` по нему невозможен (он не в группе). `record_box` после разрушения оставляет пустую клетку; бумбокс (10.10) отвечает на удар, но тоже исчезает без следа. Новое у стога — его **конец**: разрушенный стог с подарком пустой клетки не оставляет, в его клетке появляется спрятанная спецфишка — свободная, в `idle`, готовая к тапу, свапу и комбо, как любая спецфишка поля.

У стога одно своё поле — `gift` объекта (код подарка, 17.2). На уровне без стогов ни одно правило этого раздела не действует: поток `effects` не тратится, событий `gift` нет, хеш тот же, что был.

- **Что внутри.** Поле `gift` слота, обязательное: `"riff"` (тогда обязательно и `axis`: `"h"` или `"v"` — как у стартового Риффа в `slots`), `"sub"`, `"bird"`, `"disco"` — именно эта спецфишка; `"random"` — случайная (см. ниже); `"none"` — ничего: обычный стог, после которого остаётся пустая клетка. Полные и пустые стоги выглядят одинаково: `game:pieces()` подарка не отдаёт, события до разрушения его не называют.
- **Случайный подарок.** Вид подарка `"random"` выбирается в момент разрушения стога, внутри разрушающего удара (сразу после события `destroy`): один выбор 3.2.1 из потока `effects` среди четырёх вариантов в порядке «Рифф `h`, Рифф `v`, Сабвуфер, Пташка» — вариант номер `int(4)`, шансы равные. Диско-шар случайно не выпадает никогда (его можно только задать явно). Выбор тратит ровно один `next_int` и происходит только здесь: стог, который ещё цел (удар снял `hp` с 2 до 1), ничего не тратит и остаётся «неизвестным»; подарок, заданный уровнем, и пустой стог не тратят ничего. Другие потоки стог не трогает.
- **Удар, разрушающий стог,** — обычный удар 7.1 по блокеру: событие `destroy`, +50 очков за единицу `hp` (7.4), цель `break hay` −1, `vac` клетки = метка источника, плитка пола под стогом получает −1 по правилу 7.1.4, стог переходит в `clear` на `T.clear`. У стога с подарком в этот же момент метка объекта становится меткой источника (её получит подарок). С этого момента клетка — **открытый слот** (0.1): удары `match` и `adjacent` в ней ничего не делают, удар `effect` бьёт только пол; гравитация считает стог в `clear` как `wait` (клетки под ним и над ним ждут); поле не в покое.
- **Появление подарка — шаг 4 тика.** Объект в `clear` обычно исчезает в шаге 4 тика, в котором истёк его таймер. Стог с подарком исчезает в шаге 4 **первого тика, в котором одновременно**:
  1. его таймер `clear` истёк (`now ≥` тик разрушения `+ T.clear`), и
  2. очередь планировщика пуста после шага 3 этого тика — в ней нет ни одной записи (15.2): ни ударов и шагов эффектов, ни активаций (в том числе цепочек, которые ещё ждут своего `T.chain`), ни ударов Пташек в полёте, ни записей бустеров-прожекторов, ни записей концерта.

  В этом шаге стог убирается, и в его клетку ставится **новая** спецфишка: новый id (1.4.3), вид и ось — по подарку, состояние `idle`, метка — метка разрушившего удара, `settle_tick = now`; поле становится «грязным» (фишка стала `idle`, раздел 6), событие `gift`. Очков, целей и урона полу нет. Несколько стогов, готовых в одном тике, обрабатываются по возрастанию индекса клетки (в этом порядке выдаются id). Шаг 5 того же тика уже видит спецфишку: она падает, если под ней пусто.
- **Удар, открывший стог, подарок не запускает — никогда.** Это следует из двух пунктов выше, а не из особого случая:
  - источник, разрушивший стог, эту клетку второй раз не бьёт (дедупликация по ключу объекта, раздел 7; у источника `all_layers` повторный удар бьёт только пол);
  - любой другой удар, пока стог стоит в `clear`, приходит в открытый слот;
  - подарок появляется только при пустой очереди, то есть когда не осталось ни одного эффекта: ни того, что разрушил стог, ни запущенных им цепочек (8.6), ни грузов, ни превращённых спецфишек. Пример в обычном режиме: Рифф разрушает стог в тике `t` и на том же разряде взводит Сабвуфер рядом; кольцо Сабвуфера накрывает клетку стога в тике `t + 13`, когда таймер `clear` стога (`t + 9`) уже истёк. Подарок появится только после последнего удара Сабвуфера и останется целым.

  Матчи каскада подарку не страшны и без этого: удары `match` и `adjacent` спецфишку не трогают (7.1.3). Запустить подарок может только то, что началось **после** его появления: тап и свап игрока, бустер, удар `effect` более позднего эффекта (обычная цепочка, 8.6), фаза B концерта.
- **Турбо.** Правило то же, меняется только `T.clear` (1 тик): стог, разрушенный в шаге 3 тика `t`, открывается в шаге 4 тика `t + 1`, если очередь пуста. Виды подарков, их клетки и id в обычном режиме и в турбо совпадают.
- **Пустой стог** (`gift: "none"`) — в точности `record_box`: исчезает в шаге 4 по одному таймеру, клетка пустеет, её заполняет гравитация.
- **Цвет.** У спецфишек в ядре цвета нет (1.1): Рифф, Сабвуфер и Пташка бесцветны, Диско-шар выбирает цвет X при свапе или активации (8.4). Поэтому у подарка цвет не выбирается и не хранится, кто бы ни разрушил стог — матч любого цвета или эффект.
- **После появления это обычная спецфишка,** без памяти о стоге: падает и соскальзывает по диагонали (10.1), свапается, тапается, даёт комбо со второй спецфишкой (8.5), запускается цепочкой от удара `effect`, выбирается Пташкой как уровень 2 (раздел 9), идёт в `has_move()` и подсказку (12.1, 12.3: тап по ней — ход), едет на ленте конвейера (10.9), замирает под закрывшимся занавесом (10.7), запускается фазой B концерта (13.4).
- **Гравитация.** Целый стог — `blocked` для `scan` (10.1), как любой блокер: клетки под ним заполняются по диагонали или остаются дырами. Разрушенный стог в `clear` — `wait`, пока не появится подарок (или, у пустого, пока не истечёт таймер).
- **Ковёр** (10.8): целый стог — стена: его клетка не застилается, даже тем ударом, который его разрушает. Стог в `clear` — уже открытый слот, поэтому более поздний удар источника с ковром (ещё до появления подарка) клетку застилает; иначе подарок появляется на незастеленной клетке, и застелет её любой следующий удар источника с ковром (ковру спецфишка не мешает). Подарок, активированный на незастеленной клетке, ковёр не стелет; на застеленной — стелет (пункт 2 раздела 10.8). Под стартовым ковром стог не стоит (2.1.13).
- **Занавес и конвейер.** Под занавесом на старте стог не стоит (2.1.12: `only a regular piece may stand under a curtain`), на ленте конвейера — тоже (2.1.14: `blocker on a conveyor`); с места он не сходит, поэтому ни под закрывшимся занавесом, ни на ленте целого стога не бывает. Подарок — подвижная фишка: он может упасть на ленту и под открытый занавес.
- **Бумбокс** (10.10): игра бумбокса выбирает только обычные фишки, поэтому ни стог, ни подарок ей не попадаются. Если один матч задел и стог со случайным подарком, и бумбокс, порядок трат потока `effects` — порядок 6.3: сначала все удары `adjacent` по возрастанию индекса клетки (в своём ударе стог выбирает подарок), затем игры бумбоксов (пункт 4а).
- **Лёд, провода, цепи** со стогом не связаны: стог — содержимое слота, они — свойства обычной фишки. Подарок, свайпнутый на фишку во льду, под проводами или на цепи, исполняется как тап (5.1.1.2).
- **Пташка** (раздел 9): целый стог открытой цели `break hay` — клетка цели (уровень 4), иначе уровень 2; стог с `hp = 1` считается «одноклеточным блокером с `hp` 1» в строках 3 и 4 таблицы (полный и пустой стог — одинаково: ядро не подсказывает, что внутри).
- **Бустеры** (5.3): клетка со стогом — клетка с эффектом: `stick`, `row_light`, `col_light` снимают с него единицу `hp`; `remix` его не трогает; `swap` («Кроссфейдер») — `not_movable`.
- **Тупик.** Стог ходов не даёт и не отнимает. Появившийся подарок — спецфишка в `idle`, значит, `has_move()` истинно (тап). Поле, на котором остались одни стоги, запирается так же, как поле из одних коробок (12.2, пункт 6).
- **Победа.** Цель `break hay` засчитывается в момент разрушения, до появления подарка. Если последний стог выполнил последнюю цель, игра уже в `won_wait`, а подарок появляется как обычно: переход в `concert` ждёт покоя (13.2), а поле со стогом в `clear` не в покое. Поэтому все подарки появляются до концерта и запускаются его фазой B (13.4).
- **Цель** — обычная `break {item: "hay", count}` (`count` ≤ числу стогов на старте, полных и пустых вместе): −1 в момент разрушения.
- **Подсказка** (12.3): свап, виртуальная группа которого соседствует по стороне с целым стогом при открытой цели `break hay`, — ход с прогрессом цели (как у `record_box`); полный стог или пустой — не важно.
- **События:** `hit {layer = blocker, item = hay, x, y, hp}` и `destroy {id, x, y, item = hay}` — как у любого блокера; `gift {id, x, y, special, axis, from}` (раздел 16) — подарок появился: `id` — id новой спецфишки, `from` — id разрушенного стога. У пустого стога события `gift` нет.
- **Хеш:** код подарка объекта в каждой клетке пишется в конец хеша только на уровне со стогами (17.2, пункт 15).

### 10.13 Туман

Туман — элемент района «Блюз-клуб» (с уровня 261) и первый элемент со **скрытой информацией**: сценический дым лежит на клетке и прячет от игрока всё, что в ней стоит. Занавес (10.7) тоже накрывает клетку, но он её *замораживает* по счётчику ходов; лёд (10.11) держит фишку; помехи растут. Туман не замораживает ничего и ничего не держит: **он только прячет**. Для ядра клетка под туманом — обычная клетка.

Туман — флаг клетки (`s.fog[i]`), один слой, без прочности. На уровне без поля `fog` ни одно правило этого раздела не действует: флагов нет, событий `fog` нет, хеш тот же, что был.

- **Что под туманом.** Всё в клетке под туманом ведёт себя ровно так же, как без него: фишки падают, въезжают в клетку и покидают её, свапаются, матчатся, получают удары; спецфишка тапается и запускается цепочкой; провода, цепь и лёд работают по своим правилам; плитка танцпола зажигается; лента конвейера везёт. Туман привязан к **клетке**, а не к содержимому: фишка, упавшая или приехавшая в клетку под туманом, становится скрытой, покинувшая её — видимой. Разница только для игрока: клиент не рисует содержимое такой клетки (фишку, её цвет, спецфишку, провода, цепь, лёд) и рисует поверх клетки облако, которое закрывает и плитку пола с ковром.
- **Что снимает туман.** Любой удар 7.1, дошедший до клетки (пункт 0б): удар `match` (клетка входит в группу), удар `adjacent` (клетка соседствует по стороне с клеткой группы) и удар `effect` (спецфишка, комбо, груз Пташки, игра бумбокса, бустер `stick` / `row_light` / `col_light`, Риффы концерта). Это те же условия «рядом или прямо», которыми ломается `record_box`, но цель удара — покров клетки, а не её содержимое: содержимое получает тот же удар по обычным правилам **вдобавок** (фишка группы уничтожается, фишка рядом с группой остаётся, лёд тает, спецфишка от удара `effect` запускается). Пустой слот и провода туману не мешают. Клетки, соседние только по диагонали, туман сохраняют.
- **Навсегда.** Снятый туман не возвращается и не растёт: число клеток под туманом за уровень только уменьшается. Перемешивание, шаг ленты и падение фишек флаги клеток не меняют.
- **Очки и цель.** Каждая клетка, с которой снят туман, — +50 очков (как единица плитки пола, 7.4), событие `fog {x, y}` и −1 цели `fog`.
- **Цель** — `fog {}`: рассеять туман над всеми клетками поля `fog`; счётчик — число клеток под туманом на старте, поля `count` нет. Туман можно ставить и без цели — как помеху на уровне с другой целью.
- **Слепой ход.** Игрок может свапнуть видимую фишку **в** клетку под туманом, вытащить скрытую фишку **из** неё или обменять две скрытые; тап по клетке под туманом — тоже команда. Ядро обрабатывает их по обычным правилам раздела 5: свап удаётся, только если даёт матч (или участвует спецфишка), иначе фишки возвращаются (`swap_fail`) и ход не тратится; свап с неподвижным содержимым или пустым слотом отклоняется (`not_movable`); тап запускает спецфишку, а по обычной фишке отклоняется. **Неудача не выдаёт ничего, кроме самой неудачи:** событие `swap_fail` несёт только клетки и id, а отказ `not_movable` клиент показывает так же, как неудачный свап (видимая фишка делает то же движение туда и обратно, тот же звук, без подсказки о виде препятствия). Удачный слепой свап двух обычных фишек даёт матч в клетке под туманом или в соседней с ней клетке пары, значит, туман с этой клетки снимается тем же матчем (ударом `match` или `adjacent`).
- **`has_move`, тупик и перемешивание — по настоящей доске** (12.1, 12.2). Скрытый ход — ход: пока на поле есть хотя бы один ход, пусть и такой, для которого нужен скрытый цвет, перемешивания нет. Перемешивание переставляет и скрытые фишки; туман остаётся на своих клетках. Запереть уровень туман не может: он не отнимает ни одного хода (каждая пара 12.1 принимается и под туманом), а когда ходов нет совсем, работает обычное перемешивание 12.2.
- **Подсказка — только по видимому** (12.3). Для подсказки фишка под туманом не имеет цвета, а клетка под туманом не бывает концом показанного свапа и клеткой показанного тапа. Показанный свап — свап двух видимых фишек, матч которого складывается из одних видимых фишек; прогресс цели считается тоже только по видимому (соседняя клетка под туманом — это «туман, который рассеется» при открытой цели `fog`, а не то, что под ним стоит). Если такого хода нет, подсказка показывает первый по порядку 12.1 ход настоящей доски, у которого хотя бы один конец в тумане, с полем `blind = true`; затем — тап по первой спецфишке под туманом (тоже `blind`). Клиент при `blind` покачивает видимую фишку пары и облако, ничего не открывая. Ход двух видимых фишек, который удаётся только благодаря скрытому цвету, не показывается никогда (покачивание двух видимых фишек выдало бы этот цвет): если остались только такие ходы, подсказка молчит (`nil`), а игрок пробует свапы сам — неудачный свап бесплатен.
- **Слепой клон** `game:clone({blind = true})` (17.3) — доска, какой её видит игрок: содержимое каждой клетки под туманом (фишка любого цвета, спецфишка, микрофон, кокос, одноклеточный блокер) заменено бесцветной обычной фишкой без цепи и льда, провода и плитка пола этой клетки убраны; флаги тумана сохранены. Бесцветная фишка падает и уничтожается ударами, но не входит ни в один матч (цвет 0) и не считается ни в одном подсчёте цвета. `moves()` такого клона — ровно ходы, видимые игроку. Боты выбирают и оценивают ходы только на слепых клонах (`tools/README.md`).
- **Спецфишки, Диско-шар, Пташка, бумбокс** считают по настоящей доске: цвет X Диско-шара (самый частый цвет поля), цели Пташки (раздел 9) и цели игры бумбокса (10.10) выбираются с учётом скрытых фишек. Их удар по клетке под туманом — удар `effect`, он снимает и туман.
- **Бустеры** (5.3): клетка под туманом — клетка с эффектом (`stick`, `row_light`, `col_light` принимаются и снимают туман, что бы под ним ни стояло); `remix` перемешивает и скрытые фишки; `swap` («Кроссфейдер») клетку под туманом не берёт — `not_movable` (игрок не видит, что меняет). **Бустеры перед уровнем** (4.5) под туман не кладутся: клетка под туманом — не кандидат, пока есть другие (купленная спецфишка должна быть видна).
- **Занавес.** Клетка не бывает сразу под туманом и под занавесом (2.1.15). На одном уровне они совместимы: удар по закрытой клетке не делает ничего (7.1), а клетки тумана — другие.
- **Ковёр** (10.8): пункт 0а удара идёт раньше 0б; ковёр под туманом стелется и считается как обычно, игрок увидит его, когда туман уйдёт.
- **Конвейер** (10.9): туман остаётся на клетке ленты, содержимое едет под ним; объект, съехавший из-под тумана, становится видимым.
- **Блокеры.** На старте под туманом блокера нет (2.1.15). Позже помеха (`noise`) может вырасти в клетку под туманом: ядро этого не запрещает, она скрыта, как всё остальное, и ломается обычными ударами (первый же удар снимает и туман).
- **Микрофоны и кокосы** под туманом падают как обычно; на стойке и клетке выхода тумана нет (2.1.15), поэтому доставка и сбор всегда видны.
- **Победа и концерт.** Цель `fog` засчитывается в момент снятия тумана. Риффы концерта (раздел 13) бьют ударами `effect` и снимают оставшийся туман.
- **События:** `fog {x, y}` — туман снят с клетки (раздел 16); за ним, в конце того же удара, `score` и `goal`. Клиент по нему убирает облако и начинает рисовать содержимое клетки.
- **API:** `game:cells()[i].fog = true` у клетки под туманом; `game:pieces()` отдаёт содержимое таких клеток **как есть**, с флагом `fogged = true` (прятать — дело клиента; честный бот смотрит на слепой клон).
- **Хеш:** флаг `fog` каждой клетки пишется в конец хеша только на уровне с полем `fog` (17.2, пункт 16).

### 10.14 Портал

Портал — элемент района «Аркада» (с уровня 281) и первый элемент, который **меняет путь падения**. Поле `portals` уровня — список пар. У пары две клетки: **вход** (`in`) и **выход** (`out`). Вход — низ своего отрезка (под ним пустота или край поля), выход — верх своего отрезка (над ним пустота или край поля), и спавнера на выходе нет (правило 2.1.16). Для гравитации **выход — это «клетка под входом»**: колонка входа — донор отрезка под выходом. Фишка, дошедшая до входа, ныряет в него и выпадает из выхода, а дальше падает по отрезку выхода как обычно. Конвейер (10.9) двигает фишки по счётчику ходов; портал ничего не двигает сам — он только продолжает колонку в другом месте поля. Своей цели у портала нет.

Пары — статические данные уровня: в состоянии игры у них нет ничего своего, поэтому в хеше нового нет (17.2). На уровне без поля `portals` ни одно правило этого раздела не действует: `scan` (10.1) не доходит до ветки `through`, событий `portal` нет, уровень играется, считается и хешируется как раньше.

- **Клетка портала — обычная клетка.** Фишка в ней свапается, матчится, получает удары, закрепляется эффектами; на клетке может лежать плитка танцпола и ковёр; `moves()`, `has_move()`, подсказка, перемешивание и Ремикс берут её как любую другую. Помеха может вырасти на клетку портала (раздел 11): тогда она стоит там как блокер, пока её не разобьют.
- **Прыжок (`hop`).** В проходе 10.1 пустая клетка выхода `E` (её отрезок начинается ею самой, спавнера нет) смотрит на вход `N` своей пары. Если в `N` стоит подвижная фишка в `idle`, не закреплённая, она переносится в `E`: `state = fall`, `offy = 3600`, `offx = 0`, `vy = T.fall_v0`, `delay = counter[x_E]`, `counter[x_E] += 1` — ровно как фишка, упавшая на одну клетку (тики те же: в обычном режиме 7 тиков полёта плюс задержка волны, в турбо — приземление в том же тике). Метки — как у вертикального переноса без промежуточных клеток (1.3.5): `P.метка = max(P.метка, E.vac)`, затем `N.vac = P.метка`. id и все свойства сохраняются. Событие `portal`. Прыжок — назначение (раздел 11): поле не в покое.
- **Только в клетку выхода и только из покоя.** Фишка прыгает только в саму клетку `E` и только стоя в `N` в `idle`. Фишка, которая ещё летит ко входу (`fall`), сначала приземляется в `N` (шаг 6), и прыгает не раньше шага 5 следующего тика; в шаге 7 тика приземления она стоит в `idle` и участвует в поиске матчей как любая приземлившаяся фишка (линия, сложившаяся на входе, разрешается раньше прыжка). Поэтому **за один шаг гравитации фишка проходит не больше одного портала**: выпав из выхода, она в `fall`, а через следующий портал цепочки пройдёт, только приземлившись в его входе. Пустая клетка ниже `E` в том же отрезке фишку со входа сама не берёт: она ждёт (`wait`), пока фишка выйдет в `E`, и в следующем проходе получает её обычным переносом (фишка в `fall` сохраняет `vy` и `delay`, 10.1).
- **`through(N, прямой)`** — ответ входа `N` пустому отрезку под его выходом; `прямой` — спрашивает сама клетка выхода. Правила — те же строки, что у `scan`:
  1. в `N` содержимое в `clear`, `swap` или `armed`, либо закреплённое — `wait`;
  2. в `N` целый блокер, фишка под проводами или во льду — `blocked`;
  3. в `N` подвижная фишка в `fall` — `wait` (она ещё летит);
  4. в `N` подвижная фишка в `idle`: `прямой` — `hop`, иначе `wait`;
  5. `N` пуст — отвечает его собственная колонка, по клеткам вверх от `N`: закрытая клетка занавеса (10.7) — `blocked`; первое непустое содержимое — `wait` или `blocked` по пунктам 1–2, а подвижная фишка (в `idle` или `fall`) — `wait`: её принесёт во вход обычная гравитация колонки. Если все клетки пусты: верх отрезка — спавнер — `wait` (вход заполнит спавн); верх отрезка — выход другой пары — `through(её вход, не прямой)` (цепочка порталов; циклов нет, 2.1.16); иначе `blocked`.
- **Что едет.** Всё, что падает: обычная фишка, спецфишка, фишка на цепи (цепь едет с ней, 10.6), микрофон, кокос — в том числе фишка, которую ко входу принесла лента конвейера или диагональ.
- **Что не едет и запирает вход.** Блокер (помеха, выросшая на вход), фишка под проводами и фишка во льду стоят на входе, как стояли бы в любой колонке: отрезок под выходом для `scan` — `blocked`. Он заполняется по правилу диагонали 10.1 (доноры — обычные соседние клетки `(x±1, y−1)` пустой клетки) или остаётся дырами, пока препятствие не исчезнет, — ровно как клетки под блокером. Второй модели заполнения нет.
- **Донор на входе.** Фишка, стоящая во входе, для правила диагонали «висит над» выходом своей пары: она бывает диагональным донором, только когда слот выхода не пуст (10.1, пункт 2). Иначе её путь — через портал.
- **Порядок.** Отдельного прохода у порталов нет: прыжки назначаются в общем проходе 10.1 (`y = H..1`, `x = 1..W`), когда проход доходит до клетки выхода. Несколько пар срабатывают в порядке клеток своих выходов (снизу вверх, слева направо). Каждый вход принадлежит одной паре, поэтому за фишку порталы не спорят. Вход, освобождённый прыжком, заполняется в этом же проходе, если он стоит выше выхода или в том же ряду правее (проход до него ещё не дошёл), иначе — в проходе следующего тика; результат от этого не зависит, сдвигается только тик.
- **Спавнеры.** В отрезке под выходом спавнера нет: его единственный источник — портал (и диагональ, когда вход заперт). Колонка входа заполняется своим спавнером или, в цепочке, выходом предыдущей пары.
- **Микрофоны и кокосы** (10.4, 10.5). Вход — **не** клетка выхода: микрофон или кокос, дошедший до входа, не собирается, а едет через портал и падает по отрезку выхода; собирается он только на настоящей клетке выхода (`exits`), то есть в конце пути. Пока вход заперт или отрезок под выходом полон, он стоит на входе как обычная фишка. Правила 2.1.8 и 2.1.11 требуют стойку в каждом настоящем низу, поэтому путь всегда кончается выходом с поля.
- **Пташка и подсказка.** «Клетка под микрофоном (кокосом)» для фишки, стоящей во входе, — клетка выхода пары: уровень 3 раздела 9 и «прогресс цели» раздела 12.3 считают её так же, как клетку прямо под фишкой.
- **Занавес, туман, конвейер.** Клетка портала не бывает клеткой занавеса, тумана и ленты (2.1.16). На одном уровне они совместимы: закрытая клетка занавеса в колонке входа запирает её, как любую колонку (пункт 5 выше); лента приносит фишки в колонку входа; туман лежит на других клетках.
- **Ковёр** (10.8) через портал не переходит: он стелется матчами и эффектами по клеткам поля. Правило достижимости 2.1.13 считает только соседство клеток, поэтому поле из частей, соединённых одними порталами, с целью `carpet` не проходит валидацию.
- **Покой.** В покое не бывает пары, у которой выход пуст, а во входе стоит подвижная фишка: прыжок — назначение. Дыра под запертым входом допустима, как дыра под блокером.
- **Тупик.** Портал не отнимает ходов. Тупик — обычное перемешивание 12.2.
- **События:** `portal {id, fx, fy, x, y, pair}` (раздел 16): фишка `id` ушла из входа `(fx, fy)` и стоит (в `fall`) в выходе `(x, y)` пары номер `pair`. Клиент вместо скольжения сверху показывает «сжалась во входе, выросла из выхода»; `land` этой фишки придёт как обычно.
- **API:** `game:cells()[i].portal = {role, pair, x, y}` у клетки портала: `role` — `"in"` или `"out"`, `pair` — номер пары, `x, y` — второй конец пары (17.3).
- **Хеш:** нового нет (17.2, пункт 17).

## 11. Покой и конец хода

**Поле в покое**, если одновременно:
- нет фишек и блокеров в `fall`, `swap`, `clear`, `armed`;
- очередь планировщика пуста (значит, нет закреплённых фишек и резервов Пташек);
- поле не «грязное»;
- в последнем проходе 10.1 не было ни одного назначения.

**Очередь конца хода** — принятые свапы и тапы в порядке `a`, кроме возвращённых; у каждого флаг `noise_hit` и поле `merged` (1.3.10).

**Шаг 8**, если поле в покое, — по состоянию игры:
- `playing`:
  1. **Рост помех.** Сначала для действий очереди по убыванию номера: `credited[a] = noise_hit[a]` или (`merged[a]` стоит в очереди и `credited[merged[a]]`). Затем для каждого действия очереди по возрастанию номера, если `credited` ложно и на поле сейчас есть хотя бы одна помеха:
     - список пар строится заново по текущей доске: (помеха, соседняя по стороне обычная фишка в `idle` без проводов, без цепи и не во льду, не в клетке-спавнере), по индексу помехи, затем фишки;
     - пустой список — ничего; иначе одна пара выбирается из потока `effects` (3.2), фишка становится помехой (id и метка сохраняются), событие `noise_spread`.

     Затем — счёт ходов занавеса (10.7) по действиям очереди. Затем — шаги лент конвейера (10.9): по одному шагу каждой ленты за каждое действие очереди. Очередь очищается. Если занавес при этом открылся и остался открытым или хотя бы одна лента что-то перевезла, пункты 2–3 в этом тике не выполняются (поле «грязное» или фишки ленты заблокированы; их выполнит следующий покой).
  2. Если `moves_left == 0` — состояние `out_of_moves`.
  3. Иначе, если `has_move()` ложно: при закрытых занавесах они открываются (10.7), иначе — перемешивание (12.2).
- `out_of_moves`, `lost`, `complete` — ничего.
- `won_wait` — переход в `concert` (13).
- `concert` — фаза C (13).

После этого `rest_flag` = «поле всё ещё в покое» (5.3).

## 12. Ходы, перемешивание, подсказка

### 12.1 `has_move` и число ходов

- **Пары:** для каждой клетки по индексу — пара с правым соседом, затем с нижним. Пара годится, если в обеих клетках подвижные фишки в `idle` (фишка во льду неподвижна, 10.11), не закреплённые и не на цепи, ни одна из клеток не закрыта занавесом (10.7), и либо участвует спецфишка, либо виртуальный обмен даёт матч через одну из двух клеток (5.1.2).
- `moves()` — список годных пар в этом порядке. **Число ходов** стартовой доски (4.3) — длина этого списка.
- `has_move()` истинно, если есть спецфишка в `idle`, не закреплённая и не в закрытой клетке (тап), или список пар не пуст.
- Туман (10.13) на пары, `moves()` и `has_move()` не влияет: они считаются по настоящей доске, со скрытыми фишками. Ходы, видимые игроку, — `moves()` слепого клона (17.3).

### 12.2 Перемешивание (поток `shuffle`; на старте — `init`)

Кандидаты — обычные фишки в `idle` без проводов, без цепи и не во льду (10.11), не закреплённые и не в закрытых клетках (10.7), по индексу; `n` — их число, их клетки — клетки перемешивания. Каждая попытка начинается с исходной расстановки и проходит, если на доске нет матча и список пар 12.1 не пуст (тап спецфишки не в счёт: так Ремикс всегда даёт свап).

1. До 50 попыток перестановки: `for i = n, 2, -1 do j = int(i); a[i], a[j] = a[j], a[i] end`. Фишки переезжают с id и метками.
2. Иначе до 50 попыток перекраски: клетки перемешивания по индексу получают цвета по правилу 4.2 с весами `spawn_weights`. Фишки сохраняют id и метки.
3. Иначе исходная расстановка возвращается, и кандидат `int(n)` становится Риффом с осью `h` (при n ≥ 1).
4. Если кандидатов нет: случайная (`int`) обычная фишка под проводами теряет провода (событие `freed`) и становится Риффом `h`.

   4а. Если нет и таких: случайная (`int`) обычная фишка в `idle` на цепи теряет цепь целиком (событие `unchained`, очков нет) и становится Риффом `h`; в цель `chains` она засчитывается всегда, иначе цель стала бы невыполнимой.

   4б. Если нет и таких: случайная (`int`) обычная фишка в `idle` во льду теряет лёд целиком (событие `thawed`, очков нет) и становится Риффом `h`; в цель `ice` она засчитывается всегда (10.11).
5. Если нет и таких: случайная помеха поля убирается и заменяется Риффом `h` (id сохраняется, событие `destroy`, очков нет). В цель `break noise` она засчитывается, только если была последней помехой на поле: иначе цель стала бы невыполнимой.
6. Если нет ничего — состояние `out_of_moves` с флагом `stuck` (событие `state` с `reason = stuck`). `continue` в нём отклоняется (`no_candidates`): продолжение не продаётся, когда оно не может помочь; остаются бустеры и `give_up`. Флаг снимается при выходе из `out_of_moves`.

- Каждая фишка, у которой изменились клетка или цвет, и новый Рифф уходят в `swap` без обмена на `T.shuffle` (блокировка: игрок успевает увидеть новую расстановку). В конце блокировки (шаг 2) — `idle`, `settle_tick = now`, поле «грязное».
- Ход не тратится. Событие `shuffle`.
- `remix` (5.3) выполняет пункты 1–3.
- На старте (4.3) перемешивание идёт без блокировки и без события; пункты 4–6 на старте ничего не делают (первый покой повторит перемешивание по правилам игры).

### 12.3 Подсказка `game:hint()`

Чистая функция. Считается по списку `moves()` и тапам по спецфишкам в `idle`, не закреплённым:

| Ярус | Ход | Порядок внутри яруса |
|---|---|---|
| 4 | свап двух спецфишек | ранг комбо: disco+disco, disco+sub, disco+riff, disco+bird, sub+sub, riff+sub, bird+sub, bird+riff, riff+riff, bird+bird |
| 3 | свап, после которого виртуальная группа создаёт спецфишку (6.1); свап Диско-шара с обычной фишкой | ранг лучшей спецфишки (disco > sub > riff > bird; свап Диско-шара — disco), затем больше суммарный размер групп (у свапа Диско-шара — число обычных фишек цвета X в `idle`) |
| 2 | свап с прогрессом цели; свап Риффа, Сабвуфера или Пташки с обычной фишкой или микрофоном; свап Диско-шара с микрофоном; тап по спецфишке | сначала свапы с прогрессом (больше размер групп), затем ходы спецфишкой по рангу sub > riff > bird > disco, свап раньше тапа |
| 1 | любой другой ход | больше размер групп |

- Последний ключ везде — меньший индекс первой клетки пары (у тапа — его клетка).
- **Прогресс цели:** в виртуальной группе есть фишка цвета открытой цели `collect`; или клетка группы на незажжённой плитке при цели `light`; или клетка группы соседствует по стороне с блокером открытой цели `break`, который ломается от `adjacent` (record_box, noise, column, boombox, hay, balloon цвета группы); или клетка группы стоит прямо под микрофоном при открытой цели `deliver`; или клетка группы стоит прямо под кокосом при открытой цели `drop` (для микрофона и кокоса во входе портала клетка «под ним» — выход пары, 10.14); или в группе есть фишка на цепи при открытой цели `chains`; или клетка группы соседствует по стороне с фишкой во льду при открытой цели `ice` (10.11); или при открытой цели `carpet` в группе есть и застеленная, и незастеленная клетка (10.8).
- Возвращает `{from, to}` (from — клетка с меньшим индексом), `{at}` для тапа или `nil`, если ходов нет. Показ подсказки (5 с бездействия, покачивание) — забота клиента.
- **Туман** (10.13). На уровне с туманом подсказка считает только по видимому:
  1. цвет фишки под туманом для неё — «нет цвета»; пара годится, только если обе её клетки без тумана и виртуальный обмен даёт матч и без скрытых цветов (либо участвует видимая спецфишка); тап — только по спецфишке вне тумана;
  2. в «прогрессе цели» сосед группы под туманом не рассматривается (ни блокер, ни лёд, ни микрофон или кокос над клеткой группы); вместо этого сосед под туманом при открытой цели `fog` — сам прогресс цели; число фишек цвета X у свапа Диско-шара считается без клеток под туманом;
  3. если по пунктам 1–2 нет ни одного хода: первая по порядку 12.1 пара настоящей доски, у которой хотя бы одна клетка под туманом, — `{from, to, blind = true}`; если нет и такой — первая по индексу спецфишка под туманом, `{at, blind = true}`; ранжирования в этом пункте нет (оно выдавало бы скрытое);
  4. иначе `nil`, даже если `has_move()` истинно: остались только ходы двух видимых фишек, которым нужен скрытый цвет.

  На уровне без тумана подсказка та же, что была, поля `blind` нет.

## 13. Победа, финальный концерт, поражение

1. **`won_wait`.** Игра переходит сюда в момент выполнения последней цели (событие `state` сразу после события `goal`). Ввод закрыт, кроме `skip`. Каскады и свапы в полёте доигрываются, включая откаты с возвратом хода.
2. **Переход в `concert`** — в шаге 8 первого тика покоя в `won_wait`, тик `tc = now`:
   - `moves_at_win = moves_left`; `n = moves_left`; `A = act`; `rounds = 0`; очередь конца хода очищается;
   - закрытые занавесы открываются до конца уровня (10.7);
   - ставятся записи фазы A `concert_a`: `k = 1..n` на `tc + T.concert_step·k`;
   - ставится запись начала фазы B `concert_b` на `tc + T.concert_step·n + T.fire_step`.

   (Записи из шага 8 с тиком ≤ `now` выполняются в шаге 3 следующего тика, 15.1.)
3. **Фаза A, шаг k:** `moves_left -= 1` (событие `moves`). Одна обычная фишка в `idle` без проводов, без цепи и не во льду, не закреплённая (поток `effects`), становится Риффом (id сохраняется) с осью `h` при нечётном k и `v` при чётном, с меткой `(A+1, 0)`; +300 очков; событие `concert_riff`. Если кандидатов нет — Риффа нет.
4. **Фаза B** (тик `t_B` записи начала): `rounds += 1`; S — все спецфишки в `idle`, не закреплённые, по индексу. Все они сразу переходят в `armed`; активация `S[i]` (с нуля) — запись `activate` на тик `t_B + T.fire_step·i` с меткой `(A+1, 1)`.
5. **Фаза C** — в шаге 8 каждого тика покоя в `concert`: если есть спецфишка в `idle` и `rounds < 20` — запись начала фазы B на `now + T.fire_step`; иначе состояние `complete`.

**Итог уровня:** очки, `moves_at_win` (мета платит +5 монет за каждый), звёзды по сложности (`easy` и `medium` — 1, `hard` — 2, `super_hard` — 3), список `unplaced` (17.3).

- **`out_of_moves`**: клиент предлагает продолжение (`continue`, кроме флага `stuck`), бустеры или сдачу (`give_up` → `lost`).
- **`skip`**: включает турбо до `complete` (решение архитектора). Итог может отличаться очками от просмотренного концерта — это допустимо и записывается в реплей.

## 15. Тик

```
step():
  tick += 1; now = tick
  1. (команды окна now уже применены, 5.0)
  2. таймеры swap / swap_fail / swap_back / exchange (в порядке запуска), затем блокировки,
     истекающие в now; если хоть один истёк: поиск и разрешение матчей (6, с 6.2.1),
     откаты (5.1.3)
  3. очередь: все записи с due <= now в порядке (due, seq),
     включая поставленные во время шага 3
  4. фишки и блокеры в clear с истёкшим таймером исчезают; стог сена с подарком
     исчезает, только когда к тому же пуста очередь, и в его клетке появляется
     спецфишка (10.12)
  5. назначение падений и спавн (10.1)
  6. движение падающих (10.2)
  7. если поле «грязное»: поиск и разрешение матчей (6);
     затем доставка микрофонов (10.4) и сбор кокосов (10.5) — в каждом тике
  8. если поле в покое: раздел 11 (и 13); обновить rest_flag
```

### 15.1 Время и планировщик

1. `now` — номер выполняемого тика. Команда, применённая между тиками N и N+1, имеет `now = N+1` (этот тик пишется в реплей).
2. Команды никогда не наносят ударов: они проверяют условия, меняют состояния, счётчики и ставят записи на `now`. Тап ставит активацию, бустер — своё действие.
3. Длительность D, начатая в `now`, истекает в тике `now + D` в шаге-владельце: таймеры свапов и блокировок — шаг 2; `clear` — шаг 4; записи — шаг 3. Пример: свап, принятый перед тиком N+1, заканчивается в шаге 2 тика N+11; фишка, уничтоженная в шаге 7 тика t, исчезает в шаге 4 тика t+9.
4. **Очередь** — записи из простых данных `{due, seq, kind, data}` (15.2), упорядоченные по `(due, seq)`. `seq` — счётчик постановок: новая запись получает `seq + 1`, и счётчик растёт. Замыканий в записях нет.
5. Запись с `due ≤ now`, поставленная командой, в шаге 2 или во время шага 3, выполняется в шаге 3 тика `now` (во время шага 3 — дописывается в текущий проход). Запись с `due ≤ now`, поставленная в шагах 4–8, получает `due = now + 1`.
6. `t0` активации — тик, в шаге 3 которого выполняется её запись. Действия эффекта с тиком `t0` выполняются сразу внутри записи активации (7.2.6).
7. Защита от зацикливания: больше 100 000 записей за один тик — ошибка ядра (баг). Результат никогда не обрезается молча.
8. **Переключение в турбо** (`skip`, `set_timing` у клона) происходит между тиками, при `now = N+1`:
   - каждый таймер: срок = min(срок, `now` + турбо-значение своего вида);
   - каждая запись: `due = min(due, now)`; затем записи получают `seq = 1..k` в прежнем порядке `(due, seq)`, и счётчик `seq` становится равен `k`;
   - у падающих фишек `delay = 0`; они приземлятся в ближайшем шаге 6;
   - все новые длительности — турбо.

| `fog` | `x`, `y` | с клетки снят туман (10.13): пункт 0б удара; за ним (в конце того же удара) `score` и `goal` |
| `curtain` | `phase` (`closed` \| `open`), `cells` (клетки занавеса по индексу), `left` (ходов до следующей смены), `reason` (`move` \| `deadlock` \| `concert`) | занавесы закрылись или открылись (10.7), шаг 8 |
| `curtain_left` | `phase`, `left` | ход засчитан, фаза не сменилась (10.7), шаг 8 |
| `conveyor` | `belt` (номер ленты с 1), `moves` (переезды по порядку клеток ленты: {`id`, `fx`, `fy`, `x`, `y`}; у прыжка с конца открытой ленты в начало ещё `wrap = true`, `ox`, `oy` — клетка за концом ленты, в сторону которой объект уезжает, и `ix`, `iy` — клетка перед началом, откуда он въезжает; эти две клетки могут лежать вне поля), `duration`, `jam` (`true` — затор: `moves` пуст, `duration` 0) | шаг ленты (10.9), шаг 8; лента, на которой нет ни одного объекта, события не даёт |
| `portal` | `id`, `fx`, `fy` (клетка входа), `x`, `y` (клетка выхода), `pair` (номер пары с 1) | фишка прошла через портал (10.14), шаг 5: она уже стоит в клетке выхода в `fall` и падает одну клетку; `land` придёт как обычно |
| `shuffle` | `moves` ({id, fx, fy, x, y}), `recolors` ({id, color}), `riff` ({id, x, y, from: `piece`/`wires`/`chain`/`ice`/`noise`} или нет), `duration` | перемешивание и Ремикс (не на старте) |
| `concert_riff` | `id`, `x`, `y`, `axis` | фаза A |
| `continue_riff` | `id`, `x`, `y` | Рифф продолжения |
| `booster` | `booster`, `at` \| `row` \| `col`, `to` (только `swap`), `ok` | начало выполнения бустера (шаг 3); `ok = false` — Ремикс ничего не сделал. «Кроссфейдер» (`swap`): сразу при принятии команды, `at` и `to` — клетки обмена, `ok = true` |
| `state` | `state` (`playing`, `won_wait`, `concert`, `out_of_moves`, `lost`, `complete`), `reason` (`stuck` у `out_of_moves` из 12.2.6) | каждое изменение состояния игры |

**Похвала.** Для каждого действия `m` хранится `praise_best[m]` (сначала 0). Когда разрешается группа с меткой `(M, W)`, берётся наибольший порог `p ∈ {3, 5, 7, 9, 12}` с `p ≤ W`. Если `p > praise_best[M]` — событие `praise {act = M, wave = W, word}` со словом `juicy`, `hit`, `drive`, `vibe`, `legend` для порогов 3, 5, 7, 9, 12, и `praise_best[M] = p`. Так каждое слово звучит не больше раза на действие, при скачке волны звучит только старшее слово, а `legend` — один раз. В концерте `M = A + 1`.

**Порядок событий** — причинный:
- команда: `swap` | `swap_fail` → `moves` → `state`; «Кроссфейдер»: `state` (из `out_of_moves`) → `booster` → `exchange`;
- удар: снятие своей спецфишки (`clear` с `fired`) → ковёр (`carpet`) → туман (`fog`) → провода (`hit` → `freed`) → слот (`clear` | `hit` | `destroy` | `hit` слоя `chain` → `unchained` | `hit` слоя `ice` → `thawed`) → пол (`hit` → `floor_lit`) → `score` → `goal` (по номеру цели) → `state`;
- группа: `match` → удары `match` по клеткам → `special_new` → `score` бонуса → удары `adjacent` → игры бумбоксов (10.10; у каждой `boombox` → удары по её целям) → `praise`;
- активация: `activate` → `bolt` | `ring` → действия тика `t0` в естественном порядке; у Пташки — крест → `bird_fly`;
- превращение: `transform` → `score` → `goal`; фаза A: `moves` → `concert_riff` → `score`;
- откат: `swap_back` → `moves`;
- сбор кокоса: `coconut_collected` → `score` → `goal` → `state`;
- стог сена: `destroy` (в ударе, как у любого блокера) … `gift` — в шаге 4 более позднего тика, когда таймер `clear` стога истёк и очередь пуста (10.12); между ними идут все события эффектов, которые ещё были в полёте;
- шаг 8 в `playing`: `noise_spread` → `curtain` | `curtain_left` (по одному на засчитанный ход) → `conveyor` (по одному на ленту за каждый засчитанный ход; матчи сдвига — события тика, в котором кончается блокировка) → `state` (`out_of_moves`) | `curtain` (`deadlock`) | `shuffle`; матчи открывшегося занавеса — события следующего тика;
- событие `state` идёт сразу за событием, которое его вызвало.

## 17. Реплей, хеш, API

### 17.1 Реплей

- **Заголовок:** `core_version`; уровень `{id, version, hash}` (свёртка 17.2 по байтам канонической формы 2.2); `seed` (главный), `attempt`, `salt`; бустеры перед уровнем (упорядоченный список); уровень помощи (0–2); режим таймингов на старте; `input_lock`; `final_tick`; `final_hash`.
- **Команды:** список `{tick, cmd}` принятых команд в порядке применения (неудачный свап тоже записывается).
- **Воспроизведение** применяет команды в их тиках и идёт до `final_tick`; события и хеш обязаны совпасть.
- Золотые реплеи в `tests/golden/` проверяются на каждом прогоне тестов. Отдельный золотой тест — первые 5 выходов каждого потока при `seed = 1`.

### 17.2 Хеш состояния

- **Свёртка:** `h = 0`; для каждого значения `v`: `v = v % 4294967296`; `h = (h*65599 + v + 1) % 2147483629`. Все значения — целые; булевы — 0/1; отсутствие — 0. `tostring` и `string.format` в хеше запрещены.
- **Коды перечислений:**

  | Перечисление | Коды |
  |---|---|
  | вид содержимого | 0 нет, 1 regular, 2 special, 3 mic, 4 blocker, 5 coconut |
  | цвет | 0 нет, 1–6 (раздел 0) |
  | спецфишка | 0 нет, 1 riff, 2 sub, 3 bird, 4 disco |
  | ось | 0 нет, 1 h, 2 v |
  | блокер | 0 нет, 1 record_box, 2 concrete, 3 noise, 4 balloon, 5 column, 6 boombox, 7 hay |
  | подарок стога (10.12) | 0 нет, 1 riff h, 2 riff v, 3 sub, 4 bird, 5 disco, 6 random (ещё не выбран) |
  | состояние | 1 idle, 2 fall, 3 swap, 4 clear, 5 armed |
  | таймер | 0 нет, 1 swap, 2 swap_fail, 3 swap_back, 4 блокировка, 5 clear, 6 exchange |
  | вид источника | 1 match, 2 adjacent, 3 effect |
  | предмет (бустеры, `unplaced`) | 1 stick, 2 row_light, 3 col_light, 4 remix, 5 Рифф перед уровнем, 6 Сабвуфер перед уровнем, 7 Диско-шар перед уровнем, 8 Рифф продолжения, 9 swap («Кроссфейдер»; в `unplaced` не бывает) |
  | состояние игры | 1 playing, 2 won_wait, 3 concert, 4 out_of_moves, 5 lost, 6 complete |
  | тайминги | 1 normal, 2 turbo |
  | вид записи | 15.2 |

- Счётчики `released`, `on_board`, `last_mic` на уровне с кокосами считают кокосы (10.5); раскладка хеша от этого не меняется.
- Прочность цепи (10.6) пишется в поле `hp` объекта: значение поля — `hp + chain` (у блокера `chain = 0`, у обычной фишки `hp = 0`, вид объекта различает их). На уровнях без цепей хеш тот же, что был.
- **Правила раскладки.** Каждое поле пишется всегда (отсутствующее — 0); каждый список предваряется своей длиной; клетки — индексом `i`. Колонка 2×2 пишется в каждой из своих 4 клеток одинаково.
- **Порядок значений:**
  1. по клеткам `i = 1..W·H`:
     - существует, спавнер, стойка, `hp` пола, `hp` проводов, `vac` (mv, wv);
     - содержимое слота (17 полей): вид, цвет (обычной фишки или шарика), спецфишка, ось, блокер, `hp` блокера, состояние, id, метка (mv, wv), `offx`, `offy`, `vy`, `delay`, `settle_tick`, вид таймера, срок таймера;
     - отметки `pins`: длина, id по возрастанию;
  2. счётчики: `tick`, `act`, `seq`, `next_piece_id`, `next_source_id`, `moves_left`, `moves_made`, очки, остатки целей (длина, по порядку), `released`, `on_board`, `last_mic`, состояние игры, `stuck`, режим таймингов, `input_lock`, `rest_flag`, «грязный» флаг, число назначений последнего прохода, `tc`, `rounds`, `moves_at_win`;
  3. свапы в полёте (таймеры `swap`, `swap_fail`, `swap_back`, `exchange`) в порядке запуска: вид таймера, `a` (у неудачного — 0), `from`, `to`, запомненные метки (4 числа; у неудачного свапа и обмена — 0), срок. Блокировки перемешивания здесь не пишутся — только в своих клетках;
  4. записи очереди в порядке `(due, seq)`: due, seq, код вида, поля данных (15.2);
  5. активные источники по возрастанию id: id, вид, метка (mv, wv), цвет, `all_layers`, `own` (длина, id), `centre`, ключи дедупликации (длина, по возрастанию), резервы (длина, клетки по возрастанию);
  6. очередь конца хода: `a`, `noise_hit`, `merged`;
  7. похвалы: пары (`m`, `praise_best[m]`) с ненулевым значением, по возрастанию `m`;
  8. `unplaced`: коды предметов по порядку;
  9. 4 потока × 6 слов состояния генератора;
  10. только на уровне с блоком `curtain` (10.7): `cur_closed`, `cur_left`. На уровнях без занавесов этих значений нет, и хеш тот же, что был.
  11. только на уровне с ковром (10.8): флаг `carpet` каждой клетки `i = 1..W·H`, затем флаг `carpet` каждого активного источника по возрастанию id. На уровнях без ковра этих значений нет, и хеш тот же, что был.
  12. Ленты конвейера (10.9) — данные уровня: в хеш состояния они не входят, уровень с лентами хешируется той же раскладкой (блокировка переехавших фишек — обычный таймер 4 в полях объекта).

  13. Бумбокс (10.10) своих значений не добавляет: это блокер с кодом 6 в обычных полях объекта, а списки его игр живут только внутри разрешения группы. Уровень без бумбоксов хешируется как раньше.

  14. только на уровне со льдом (10.11; в `overlay` есть хотя бы один элемент `ice`): прочность льда объекта в каждой клетке `i = 1..W·H` (0 — льда нет или слот пуст). На уровнях без льда этих значений нет, и хеш тот же, что был.

  15. только на уровне со стогами сена (10.12; в `slots` есть хотя бы один элемент `hay`): код подарка объекта в каждой клетке `i = 1..W·H` (0 — подарка нет, это не стог или слот пуст), после значений пункта 14. Сам стог — блокер с кодом 7 в обычных полях объекта; у разрушенного стога, который ждёт в `clear`, в полях метки объекта стоит метка разрушившего удара. На уровнях без стогов этих значений нет, и хеш тот же, что был.

  16. только на уровне с туманом (10.13; есть поле `fog`): флаг `fog` каждой клетки `i = 1..W·H`, после значений пункта 15 — и тогда, когда туман уже снят со всех клеток. На уровнях без поля `fog` этих значений нет, и хеш тот же, что был.

  17. Порталы (10.14) — данные уровня: в хеш состояния они не входят, уровень с порталами хешируется той же раскладкой (фишка после прыжка — обычная фишка в `fall` в клетке выхода).

### 17.3 API, клоны и боты

| Вызов | Результат |
|---|---|
| `core.load_level(text)` | `level` или `nil, errors`; `errors` — массив строк `"<правило 2.x> <что> [at x,y]"` |
| `core.new(level, opts)` | игра на тике 0 после раздела 4. `opts`: `seed` (обяз.), `attempt`, `salt` (для заголовка), `help` 0..2 (0), `boosters` — список бустеров перед уровнем (`{}`), `timing` `'normal'`/`'turbo'` (`'normal'`), `input_lock` (`false`). Неверные `opts` — `nil, errors` |
| `game:step()` | один тик (раздел 15) |
| `game:input(cmd)` | `true, 'ok'` \| `true, 'fail'` \| `false, reason` (5.0) |
| `game:can_swap(from, to)` | `'ok'` \| `'fail'` \| `'reject'` — что сделал бы `input` со свапом сейчас (свайп в никуда — `'ok'`) |
| `game:has_move()`, `game:moves()` | 12.1; элемент `moves()` — `{from={x,y}, to={x,y}}` |
| `game:hint()` | 12.3 |
| `game:is_stable()` | поле в покое (раздел 11) |
| `game:pieces()` | массив объектов слота по возрастанию ключа: `id, x, y` (у колонки — левая верхняя клетка), `kind, color, special, axis, item, hp, state, offx, offy, hidden, pinned`, `chain` (прочность цепи; поля нет, если цепи нет), `ice` (прочность льда; поля нет, если фишка не во льду, 10.11), `veiled` (`true` у объекта в закрытой клетке, 10.7; иначе поля нет). Подарка стога сена (10.12) здесь **нет**: `pieces()` отдаёт стог как блокер `hay` с `hp`, и полный стог неотличим от пустого. `fogged` (`true` у объекта, чья клетка под туманом, 10.13; иначе поля нет): содержимое такой клетки отдаётся как есть, прятать его — дело клиента |
| `game:cells()` | массив `1..W·H`: `exists, spawner, exit, floor` (hp), `wires` (hp), `curtain` (`true` у клетки занавеса, открыт он или закрыт; иначе поля нет), `carpet` (`true` у клетки, застеленной ковром, 10.8; иначе поля нет), `conveyor` (у клетки ленты, 10.9: `{belt, pos, dir, last}` — номер ленты, место клетки в ней с 1, направление движения `r`/`l`/`u`/`d` и `last = true` у последней клетки открытой ленты; иначе поля нет), `fog` (`true` у клетки под туманом, 10.13; иначе поля нет), `portal` (у клетки портала, 10.14: `{role, pair, x, y}` — роль `"in"` или `"out"`, номер пары с 1 и клетка второго конца пары; иначе поля нет) |
| `game:status()` | `state, stuck, tick, moves_left, score, goals` (остатки по порядку); на уровне с занавесами — ещё `curtain = {phase, left}` (10.7) |
| `game:result()` | в `complete` и `lost`: `score, moves_at_win, stars, unplaced` (коды предметов 17.2, которые мета возвращает игроку); иначе `nil` |
| `game:drain_events()` | накопленные события (раздел 16); очищает буфер |
| `game:hash()` | 17.2 |
| `game:replay()` | 17.1 |

- Запросы (`can_swap`, `has_move`, `moves`, `hint`, `is_stable`, `pieces`, `cells`, `status`, `result`, `hash`, `replay`) чистые: не тратят случайность, не меняют состояние и события.
- `game:clone(opts)` — независимая глубокая копия с пустым буфером событий.
- `opts.reseed = k` — потоки `spawn`, `effects` и `shuffle` клона инициализируются заново (3.1) сидом, свёрнутым из (`seed`, `act`, `k`) той же формулой, что сид попытки. Просмотр ходов ботами идёт только на таких клонах: будущие цвета и выборы настоящей игры ботам недоступны.
- `opts.blind = true` — слепой клон (10.13): на уровне с туманом содержимое каждой клетки под туманом (объект в `idle` или `fall`, кроме колонки) заменяется бесцветной обычной фишкой (цвет 0: не матчится, не считается ни одним подсчётом цвета) без цепи и льда; провода и плитка пола такой клетки обнуляются; флаги тумана остаются. Остатки целей не меняются. На уровне без тумана и там, где туман уже снят, это обычный клон. Слепой клон — не игра: его хеш и реплей смысла не имеют, он нужен только для выбора и оценки ходов. Сочетается с `reseed`.
- `clone:set_timing('turbo')` — переключение по 15.1.8.
- `game:run_to_rest(max_ticks = 20000)` — вызывает `step()`, пока `is_stable()` ложно, и возвращает число сделанных тиков (0, если поле уже в покое); превышение лимита — ошибка.
