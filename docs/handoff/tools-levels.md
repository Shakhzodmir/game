# Инструменты уровней: проверка, боты, подбор ходов — передача

Файлы: `tools/levels.lua`, `tools/bot/*.lua`, `tools/README.md`, `tests/tools/*` (кроме `tutorials_test.lua`). Ядро и `content/levels` не менялись.

## Что сделано
- **README сверен с кодом** построчно. Найдено и исправлено:
  - `--write` клал `tuning.json` в `content/levels/`, а весь `/content` входит в сборку Defold (`custom_resources`): теперь JSON всегда в `docs/levels/`;
  - опечатка в ключе (`--level 5`) молча выбирала все уровни, с `--write` переписала бы их все; `--n 0`, `--n abc`, `--jobs abc` давали мусор или падение; теперь строгий разбор, код выхода 2;
  - `--quiet` не доходил до рабочих процессов; рабочий процесс, умерший посреди прогона, ронял весь прогон без результатов;
  - `--write` записывал устаревший ответ в файл, который успели изменить, и принимал `--n 3`;
  - `preview` падал на пустом/нечитаемом JSON и ломал сетку у колонки с hp ≥ 10; `stats` не считал `mic` при цели `deliver` (в отличие от правила 2.1.6 ядра); `entry_from_text` падал на `null`;
  - `run.lua` падал трассировкой на `--budget 3`/`--seed 0`/`--bot foo`.
- **Новое:** кэш результатов (`--work`, ключ — текст уровня без `moves`, бот, бюджет и контрольная сумма `core/` и `tools/bot/`; N в ключ не входит, партия k зависит только от сида k, поэтому пробный `--n 100` достраивается до `--n 300`); файлы результатов уровней вместо одного JSON из рабочего процесса; `--write` проверяет контрольную сумму файла, пишет атомарно и требует N ≥ 100 (или `--force`); флаг `stuck_games` и счётчики исходов партий в JSON; в тексте ошибки партии — сид и команда для повтора; `validate` на всём каталоге называет отсутствующие уровни из 1–100; код выхода 1/2.
- Отчёт для `--dir` не по умолчанию не пишется, если не указаны `--md`/`--json` (репетиция на копии не затирает настоящий отчёт).
- Тесты в `tests/tools`: было 33, стало 92 на обеих ВМ. Новые: `common_test.lua`, `cli_test.lua` (подмножество и `--write` на копии каталога, рабочие процессы, умерший рабочий, кэш, отчёты, опечатки; `run.lua`, `levels.lua`), кэш и флаги в `tune_test.lua`, инвариант «лимит M = начало партии без лимита» и границы клонов в `bot_test.lua`.

## Цифры (подробно в `tools/README.md`)
- 70 существующих уровней, жадный бот: все 2100 партий (N = 30) кончились победой, тупиков и зависаний нет. 0,03–0,38 с на партию (в среднем 0,14 с), около 18 клонов на ход, 47% времени — `deepcopy` внутри `clone()`.
- Полный прогон 100 уровней, N = 300: около 74 минут процессорного времени, 24–26 минут настенного при `--jobs 3` (19 при 4). Пробный `--n 100`: 8–9 минут. Порог в 90 минут не достигнут, ускорять ботов не пришлось.
- На 70 уровнях при N = 30: easy попадают в 87–97%, medium 63–70%, hard 37–43%, super_hard 20–27%; `outside_band` у 23 уровней (у 1–10 M равен 7–15).

## Решения для decisions.md (оркестратор вносит)
1. Результат подбора кэшируется по содержимому: уровень, бот, бюджет, исходники ядра и ботов.
2. `--write` только при N ≥ 100 (в обход — `--force`), только для файла, не менявшегося после игры.
3. Отчёты подбора лежат в `docs/levels/`; в `content/` ничего не пишется.

## Что осталось и риски
- Ядро: `Game:clone()` (универсальный `deepcopy`) — почти половина времени подбора. Специализированное копирование (объекты поля одним конструктором таблицы) ускорило бы подбор в 1,5–2 раза; универсальные приёмы (`table.new`, быстрый путь массивов) выигрыша не дали. Не сделано: `core/` не мой.
- Жадный бот, вероятно, сильнее обычного игрока: подобранные M — оценка снизу. Для 1–10 и ещё дюжины уровней M < 20 (`outside_band`): цели малы для правила плана «20–35 ходов».
- Для 71–100 прогона ещё не было (файлов нет). Первый полный прогон — по порядку из README (пробный `--n 100` → правка флагованных → `--n 300` → `--write`).
- Время зависит от нагрузки машины: при нагрузке около 10 на 4 ядра было втрое дольше.
- Два падения полного набора не мои: `tests/client/meta_town_gui_test.lua` (в содержимом нужны hard/super_hard) и `meta_windows_test.lua` (ширина строки 'Watch a video').
